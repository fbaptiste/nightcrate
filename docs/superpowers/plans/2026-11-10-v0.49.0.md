# v0.49.0 — Object search: implementation plan

> **For agentic workers:** Codex implements one phase at a time under
> `docs/agent-collaboration.md` §4; Claude reviews each phase. Steps use
> checkbox (`- [ ]`) syntax. Never stage, commit or push.

**Goal:** the Gallery's search finds an object by exact designation or by
name, in projects' main targets and, when asked, anywhere in their
plate-solved images, and marks it on each picture; the Messier page shows
objects caught only in a solved picture; every catalog ring is drawn at
the right tilt.

**Architecture:** membership and ring geometry come from one pure
function, `project_dsos`, fixed for the ring angle and applied at query
time to every stored solve (no stored lists, no migration). The Gallery
endpoint gains exact-designation matching, per-item match facts and marks;
a suggestion endpoint lists objects with the user's project counts. The
frontend draws marks in the solve image's own pixel space over the
stored solve renderings, in tiles, the list and the viewer, and the
Messier page gains an "In a solved picture" state.

**Tech stack:** Python 3.14, FastAPI, Pydantic, aiosqlite, astropy
(backend); React, TypeScript, MUI, TanStack Query, Zustand (frontend). No
new dependency.

**Spec:** [v0.49.0 design](../specs/2026-11-10-v0.49.0-design.md), approved
by Fred on 2026-11-10 ("approved, go ahead with the plan"), with the
mockup `.superpowers/mockups/v0.49.0/search.html` (local) as the visual
reference.

**Base:** `06d4cc3` on `v0.49.0/object-search`. Codex works in the
worktree `.superpowers/wt-v0.49.0` (Fred's `make dev` runs from the main
checkout, and any backend edit there would reload it on his database).

**High-stakes** (`docs/agent-collaboration.md` §5): backend–frontend
contracts (the Gallery and Messier responses, a new route) and a
scientific calculation that changes what the user sees on every solved
picture (the ring angle and in-image membership). Each gets a fresh
independent review and checks that execute the changed path.

## Global constraints

- Main targets only from `project_target`; retired means
  `project.active = 0` and follows the Gallery's "Show retired" there,
  counts nowhere on the Messier page.
- One designation normaliser: `catalog_loader/designations.py`
  `normalize_designation`. Exact means `dso_designation.search_key ==
  normalize_designation(text)` (and `dso_group.search_key` for groups).

  `project_dsos` (after Task A1). The Gallery, the suggestions, the Messier

  main targets match whatever their state.
- `project_dso` stays as it is and is no longer read by the Gallery.

- Solve images: `GET /api/projects/{id}/solve/image/{variant}` (`thumb_sm`
  180, `thumb_md` 400, `thumb_lg` 800, `full` 4000 px long side). Gallery
  URLs add the workspace key (`ws`) besides `_v=<solve id>`.
- Colours (from the mockup and the Plate Solve tab; six-digit hex):

## Review focus

1. **Mirror-imaged and bottom-up solutions:** ring tilt and membership
   right for a solution with a negative determinant and for a FITS solve
   in bottom-up rows. Pinned in Tasks A1 and A2.
2. **A field near a pole or across RA 0°/360°:** the pre-filter must not
   drop objects (today's `query_dsos_in_cone` box is wrong when its RA
   half-width reaches 180°). Pinned in Task A2.
3. **A solve whose rendering is missing (204):** the tile falls back to
   the usual picture with the chips and no mark, never an empty frame
   with floating rings. Pinned in Task B1.
4. **A broad name ("galaxy") with the box ticked on a large library:**
   stays within the speed budget. Pinned in Task A3.
5. **The persistent Gallery opened from a Messier pill** while it is
   already mounted with other filters: the search and the box apply; other
   filters stay. Pinned in Task B3.

### Task A1: Ring angle in `project_dsos`

**Files:**
- Modify: `backend/src/nightcrate/services/image_annotations.py`
- Test: `backend/tests/test_image_annotations.py`

**Interfaces:**
- `project_dsos(params: WcsParams, dsos: list[dict]) -> list[AnnotatedDso]`
  keeps its signature, membership rule and fields. `ellipse_angle_deg`
  becomes the SVG rotation (degrees, clockwise on screen, y down) that
  turns an ellipse whose long axis starts along +x onto the object's long
  axis in this image's pixels.
- Compute the pixel ellipse from the solution's local Jacobian at the
  object (Codex round 1, finding 8; a local approximation, exact in the
  limit of small objects): offset the position by a small
  separation (for example 1′) to the east and to the north
  (`SkyCoord.directional_offset_by` or `spherical_offsets_by`), project
  the three points with the same WCS, and form the 2 × 2 matrix J (pixels
  per arcminute east and north). Map the catalog ellipse (semi-axes a, b
  in arcminutes, long axis at the position angle, measured from north
  through east) through J and take its principal axes (SVD):
  `ellipse_semi_major_px`, `ellipse_semi_minor_px`, and the angle of the
  long axis as `atan2(dy, dx)` in pixels. This is exact for rotated,
  mirrored, bottom-up, unequal-scale and skewed solutions. A missing
  position angle uses 0°; a missing minor axis equals the major, as today.
- The membership rule and its scalar margin stay exactly as today.

    (all mod 180);

### Task A2: Object search service

**Files:**
- Create: `backend/src/nightcrate/services/object_search.py`
- Modify: `backend/src/nightcrate/api/dso.py` (exact variant of the clause)
- Test: `backend/tests/test_object_search.py`, `backend/tests/test_dso_api.py`

**Interfaces (produces):**
- `dso_search_clause(q: str, *, alias: str = "d", exact_designations: bool
  = False) -> tuple[str, list[str]]` in `api/dso.py`: with
  `exact_designations=True`, every designation test (direct, group, whole)
  becomes `search_key = ?` with `normalize_designation(q)`; names stay
  `LIKE %q%`. Default behaviour unchanged for every existing caller.
- `class SolveGeometry(BaseModel)` in `services/object_search.py`:
  `project_id: int`, `solve_id: int`, `wcs: WcsParams`, `image_width: int`,
  `image_height: int`.
- `solve_reach(solve: SolveGeometry) -> tuple[float, float, float]` —
  centre RA, Dec and radius (degrees) of a circle holding the whole image
  (from `compute_fov`'s diagonal radius).
- `objects_near(solve: SolveGeometry, dsos: list[dict]) -> list[dict]` —
  a provable superset of `project_dsos`'s membership (Codex round 1,
  finding 1). Centre: the sky position of the image's centre pixel (not
  CRVAL, which can be elsewhere). Per object, keep it when its
  great-circle separation from that centre is at most
  `(h + √2·m) · σmax`, where `h` is the half-diagonal in pixels, `m` the
  object's margin in pixels exactly as `project_dsos` computes it, and
  `σmax` the larger singular value of the CD matrix (degrees per pixel).
  The TAN projection's angles never exceed pixel distance × σmax, so
  nothing `project_dsos` would keep is dropped. Great-circle separation
  means poles and RA 0°/360° need no special case.
- **Cost** (finding 6): no astropy WCS construction per solve in the
  pre-filter. Compute each solve's centre and `σmax` from its stored
  columns with plain numpy (TAN deprojection of one pixel), once per
  request; run `project_dsos` only on the objects that pass.
- `marks_in_solve(solve: SolveGeometry, dsos: list[dict]) ->
  list[AnnotatedDso]` — `project_dsos(solve.wcs, objects_near(solve,
  dsos))`.
- `async def load_solves(conn, project_ids: Iterable[int] | None = None) ->
  list[SolveGeometry]` (in `api/` or a DB helper module, not in the pure
  service) — every `project_solve` row, or those of the given projects.
