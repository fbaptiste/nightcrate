# v0.54.0 — Installers and updates: implementation plan

> **For agentic workers:** Codex implements this plan phase by phase in the
> main checkout on `v0.54.0/installers-and-updates`; Claude reviews each
> phase (`docs/agent-collaboration.md`). Steps use checkbox (`- [ ]`)
> syntax. Codex never stages, commits, pushes or opens PRs.

**Goal:** installable NightCrate on macOS (Apple Silicon), Windows x64 and
Linux x64, with a production backend, safe workspace upgrades, update and
catalog notices in the sidebar, self-update on request, and a GitHub
release pipeline that Fred publishes by hand.

**Architecture:**
- A production entrypoint (`nightcrate.serve`) runs the existing FastAPI app
  without Vite. It serves the built frontend and talks to its parent over
  stdin and stdout.
- One guarded activation path refuses newer databases, backs up, migrates,
  and restores on failure, and it survives being interrupted.
- The update state lives in `APP_DIR/updates.json`. The backend computes
  notices with a pure service, and the frontend shows them.
- A Tauri 2 shell (`packaging/shell/`) starts the frozen backend, shows the
  window and installs updates. cx_Freeze freezes the backend. GitHub
  Actions builds and tests on all three systems, and drafts releases.

**Tech stack:** FastAPI, Pydantic, sqlite3 (backup API, read-only URIs),
yoyo, uvicorn; React, TypeScript, MUI, TanStack Query; Tauri 2 (Rust) with
the updater, single-instance and window-state plugins and `dynamic-acl`;
cx_Freeze 8.7.4; GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-14-v0.54.0-installers-and-updates-design.md`
(approved, then amended by the plan review on 2026-11-15; read it all
first). The mockups are `.superpowers/mockups/v0.54.0/updates.html` and
`icons.html`. The throwaway packaging test's code is in
`.superpowers/wt-v0.54.0-spike/spike/` and
`.superpowers/wt-v0.54.0-spike/.github/workflows/packaging-spike.yml`.
Start from it, but it is not a pattern for error handling or tests.

**Order.** Phase 1 makes the backend safe. Phase 2 proves a bare installed
app, with no update UI, on all three systems through test-branch builds.
Then come licences (3), the update UI (4) and the updater with releases
(5). Claude's checks run between phases (6). This follows Codex's advice:
platform risks show up before the UI is built on top of them.

## Review focus

- **No published release yet.** Until Fred publishes v0.54.0, the manifest
  URL returns 404. The check must record "no update", not an error, and
  Admin says "You have the latest version" (Task 4.1).
- **Offline at start, then focus changes.** A failed check counts as an
  attempt. The next automatic check waits 24 h from the attempt, not from
  the last success, so returning to the window doesn't retry (Task 4.1).
- **Paths with spaces and non-ASCII characters** (Windows user folders
  with accents, "My NightCrate"): backups, the lock, the workspace file,
  the marker and the app-data override all work in such a folder (Tasks
  1.2 and 1.3).
- **Every port taken (8765–8775):** the backend exits with its own code,
  and the loading window says so instead of "couldn't start" (Tasks 1.1
  and 2.2).
- **A crash while writing `updates.json`:** writes are atomic, and a
  truncated file reads as defaults without breaking startup or the
  notices (Task 4.1).

- `WorkspaceProblem` dataclass:
  - `kind: Literal["newer", "unreadable", "backup_failed",
    "upgrade_failed", "restore_failed"]`;
  - `workspace_path: str`, `workspace_name: str`;

- `@dataclass ActivationResult(backup_path: Path | None,
  migrations_applied: int)`.
- **`read_applied_hashes(db_path: Path) -> list[str] | None`** opens
  `sqlite3.connect(f"file:{quoted path}?mode=ro", uri=True)` and never
  touches yoyo. It reads `migration_hash` from yoyo's migrations table;
  confirm the table name in `yoyo/backends/base.py`.
  - The table is absent, or the database is empty → `[]`.
  - The table exists but can't be read (missing column, unexpected types,
    or `sqlite3.DatabaseError`) → `None`, which means unreadable.
- `known_hashes() -> set[str]`: the hashes of `read_migrations(MIGRATIONS_DIR)`.
- `read_last_opened_by(workspace: Path) -> str | None` and
  `record_opened_by(workspace: Path, version: str) -> None` (atomic
  write).
- **`backup_database(db_path: Path, version: str, now: datetime) -> Path`**
  writes `sqlite3.Connection.backup` into a temporary name in
  `<workspace>/backups/`, fsyncs, then renames to a fresh name.
- **`prune_backups(workspace: Path, keep: Path | None) -> None`** keeps the
  three newest `nightcrate-before-*.db` and `keep`, and touches nothing
  else.
- **`restore_backup(backup: Path, db_path: Path) -> None`:**
  1. copy to a temporary file beside `db_path` and fsync; a stale temporary
     file from an earlier attempt is replaced;
  2. delete `db_path`'s `-journal`, `-wal` and `-shm` if present (they
     belong to the file being discarded);
  3. `os.replace`, then `fsync_dir(db_path.parent)`, which covers the
     journal deletions and the replace;
  4. verify that sha256(db_path) equals sha256(backup), and raise
     `RestoreError` if not.

  Only after this returns may the marker be removed.

  It is called only when no connection to that database is open in this
  process. The yoyo backend's `with` block has exited.
- **Marker (JSON):** `{"id": uuid4 hex, "backup": name, "from_version":
  str | null, "to_version": str, "state": "upgrading" | "restore_failed",
  "started_at": iso}`.
- **The workspace file:** `{"last_opened_by": str, "completed_upgrade":
  marker id | null}`.
- **Durability** (`db/durable_fs.py`):
  - `durable_write(path, data: bytes)`: a temporary file, fsync,
    `os.replace`, then fsync the directory;
  - `durable_remove(path)`: unlink, then fsync the directory;
  - `fsync_dir(path)`: opens the directory and fsyncs it on POSIX. On
    Windows it does nothing: NTFS journals the rename, and Python has no
    directory fsync; this limit is recorded in development decisions.

  Creating `backups/` fsyncs the workspace folder. The backup's rename, the
  marker, the restore's replace and the workspace file all use them.
  Every step that must survive power loss is durable before the next
  step starts: the backup and the marker before any migration, and the
  workspace file before the marker's removal. All of it is durable before
  the lifespan returns, so before any user write is admitted.
- **A marker never discards a finished upgrade.** An upgrade is finished
  exactly when the workspace file's `completed_upgrade` equals the
  marker's `id`. Step 6 writes it durably before removing the marker, and
  the lifespan returns only after that, so no user write can happen
  before it. Then:
  - a marker whose `id` matches is a leftover. It is removed durably,
    with no restore, whichever app version finds it and whatever
    migrations that version adds;
  - a marker whose `id` doesn't match proves the activation never
    finished, so no user write was admitted since its backup, and
    restoring is safe;
  - this doesn't depend on reading the migration table, so a hot journal
    can't confuse it.

  Residual risk: a version older than v0.54.0 ignores markers. If someone
  opens a half-upgraded workspace with one, then a newer version
  restores, that old version's writes are lost. Recorded in development
  decisions.
- **`initialize_workspace(workspace: Path, name: str, app_version: str, *,
  on_step: Callable[[str], None] = lambda s: None, now: datetime | None =
  None) -> ActivationResult`**, in order:
  0. **Classify the marker first, from files only** (the marker and the
     workspace file; no database access). If a marker is present:
     - its `id` matches `completed_upgrade` → remove it durably and go on
       to step 1;
     - otherwise (an interrupted upgrade or a failed restore) → restore
       now, as described next, before SQLite touches the file, then go on
       to step 1.

     **The restore, for an unfinished marker:** restore from the marker's
     backup, which drops any
     partly applied migration, yoyo's stale lock row (an `os._exit` skips
     yoyo's `finally` that deletes it, `yoyo/backends/base.py:343`), and
     any hot journal. After a successful restore, durably set the marker
     back to `upgrading` (same `id`). Keep that backup as the recovery
     point, so no new backup is taken. A failed restore sets the marker to
     `restore_failed` and raises `WorkspaceRefused(restore_failed)`.
     Restoring is idempotent: dying at any point leaves the marker, and the
     next start restores again.
  1. **Let SQLite recover.** If a `-journal` or `-wal` file exists, open the
     database read-write, run `SELECT 1 FROM sqlite_master LIMIT 1`, and
     close it. This is SQLite's own hot-journal and WAL recovery, which a
     read-only connection can't perform; it changes no schema and no
     committed rows. A `sqlite3.Error` or `OSError` here →
     `WorkspaceRefused(unreadable)` with the error, so health and Admin
     keep serving the problem screen.

  2. **Refuse:**
     - `read_applied_hashes` is `None` → `WorkspaceRefused(unreadable)`;
     - any hash not in `known_hashes()` → `WorkspaceRefused(newer)`.

     The file is untouched either way.
  3. **Back up** when there is no recovery point yet, the database file
     existed before the call, and (migrations are pending or
     `read_last_opened_by` ≠ `app_version`):
     - call `on_step("backing_up")`, back up, then prune keeping the new
       backup;
     - write the marker (`upgrading`) when migrations are pending;
     - any exception → `WorkspaceRefused(backup_failed)`; nothing is
       migrated and no marker is left.
  4. **Migrate** when migrations are pending: `on_step("upgrading")`, then
     `apply_migrations(db_path)`. On any exception:
     - with a recovery point: `restore_backup`, remove the marker, then
       `WorkspaceRefused(upgrade_failed)` with
       `error = f"{type(exc).__name__}: {exc}"` and the backup path. If the
       restore raises, set the marker to `restore_failed` and raise
       `WorkspaceRefused(restore_failed)` with both errors;
     - without one (a brand-new database), re-raise.
  5. **Seed and catalog loaders,** as `_initialize_database` does today.
     `(sqlite3.Error, OSError, ValueError)` from either is logged as a
     warning; any other exception propagates. The same rule applies at
     startup and from Admin.
  6. Durably write the workspace file (`last_opened_by` and
     `completed_upgrade`, the marker's `id` or `null`), then durably remove
     the marker.

  It replaces both the work of `admin._initialize_database` and the
  lifespan's duplicate. Creating a new workspace keeps working.
- **`db/session.py`:**
  - `set_workspace_problem(problem: WorkspaceProblem | None) -> None`;
  - `workspace_problem() -> WorkspaceProblem | None`;
  - `class WorkspaceUnavailable(RuntimeError)`;
  - `get_db_path()` raises `WorkspaceUnavailable` while a problem is set,
    before any fallback to the config path;
  - `active_db_path_or_none() -> Path | None` for callers that today read
    `config.active_db` themselves. It returns `None` while blocked.
- **The lifespan:**
  - calls `initialize_workspace` with
    `on_step=lambda s: runtime.report_step(s, name)`;
  - on `WorkspaceRefused`, sets the problem and skips the rest of the
    database startup work;
  - on success, sets `runtime.last_activation_backup`.

  `health` reports `db_configured = False` and the problem while one is
  set.
- Activating another workspace or setting one up clears the problem.
- An Admin activation that is refused returns 409 with
  `{"detail": {"problem": {...}}}`, and the previous workspace stays active.

  0. a process-wide `AtomicBool` lets only one install run; a second
     invoke returns `{stage: "busy"}` at once, and the first one goes on.

     backend;

       failure restart the backend on the same port and return `{stage:

       relaunches NightCrate. If launching fails, restart the backend and
       return `{stage: "launch"}`.

5. **Then B:** the harness switches the manifest to B and calls `POST
   /api/updates/check`. The frontend's retry installs B through the same
   flow. Within 10 minutes, B's health must report `0.0.2`, and the
   harness checks:
   - the records and their relationships unchanged;
   - the project image file present;
   - a backup `nightcrate-before-0.0.2-*.db` holding the records, with
     integrity `ok`;
   - no marker left.

Both builds come from the same source, so no migration runs here; Task
1.3's tests cover real migrations. In release builds, the self-test

requires it to be rejected, so the URL parameter can't start an install
there. If a runner can't show the GUI, that

- **Phase 1** (Codex records `12`–`21`): `serve.py`, `core/runtime.py`,
