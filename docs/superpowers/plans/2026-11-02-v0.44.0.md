# v0.44.0 — implementation plan

> **For agentic workers:** Codex implements one phase at a time under
> `docs/agent-collaboration.md` §4. Claude reviews, re-runs checks and stages.
> Steps use checkbox syntax.

**Goal:**
- make catalogs optional and removable;
- add ten deep-sky catalogs;
- link entries to the objects they cover;
- show the planner's limits truthfully;
- add Google search links.

**Architecture:**
- **Choice:** an app-wide catalog choice (`catalogs/choice.json`) decides which
  optional catalogs feed the object step. The loader removes the objects of a
  catalog that is switched off, keeping linked ones inactive.
- **New catalogs:** each is one or more VizieR files (or, for Melotte, a
  shipped list) with a pure collector in `reconcile.build_object_set`.
- **Matches:** a shared rule turns stated matches into merges. NightCrate's
  reviewed files take precedence.
- **Groups:** a catalog-derived `dso_group` relation records "part of".

**Tech stack:** Python 3.14, FastAPI, Pydantic, sqlite3/aiosqlite, yoyo; React,
TypeScript, MUI, TanStack Query (all existing).

**Spec:** [2026-11-02-v0.44.0-design.md](../specs/2026-11-02-v0.44.0-design.md).
Read §5 (decisions) and §11 (research findings) before any task.

**Base:** branch `v0.44.0/more-catalogs-and-search-links`, HEAD `d608ed7`. The
working tree holds the spec, this plan, PLAN.md and a review-record note.

**Evidence:**
- **Code maps** (2026-11-02) are cited below by file and function.
- **Full VizieR downloads** of every table are in
  `.superpowers/codex/v0.44.0/samples/` (ignored, local), with their ReadMes.
  Build every test fixture from these files; tests never touch the network.

## Global constraints

- **One forward migration, `0066`.** Never edit an existing migration. No new
  dependency, and no new settings field: the catalog choice is an app-wide
  file, not a setting.
- **Layering:**
  - services do not import `api/` or FastAPI;
  - read `app_config.APP_DIR` at call time;
  - outbound HTTP goes through the existing VizieR fetcher
    (`catalog_loader/vizier.py`).
- **Positions:** J2000 from VizieR's computed `_RAJ2000`/`_DEJ2000`, requested
  with `-out.add=_RAJ2000,_DEJ2000` as today, or the table's native J2000
  columns where they exist. No local epoch conversion.
- **Missing values stay missing.** Any value that isn't the object's own V
  magnitude or visual size goes in the notes, never into `mag_v` or
  `maj_axis_arcmin`. That covers ACO `m10`, Wolf-Rayet narrow-band `vmag`
  and LDN area.
  - The one exception is Melotte's `2·r50` size, which the spec (§11)
    allows, labelled in the list's notes.
  - Objects without a size keep today's framing defaults: a 0.25° sky
    preview and a 0.125° list thumbnail. No change.
- **Matches:** position alone never merges (spec §5.5). Reviewed NightCrate
  files take precedence over stated matches.
- **Fred's real database is protected during Phases A and B.**
  - Fred's `make dev` (8000, `--reload`) runs from this checkout. It applies
    a new migration at once, and reruns the loader on his database at every
    reload. A migration, once applied, can't be edited.
  - **Before A1,** Claude asks Fred to stop `make dev`, and copies his
    database. It restarts only at the A-phase checkpoint (A1–A5 and A10,
    after A10), once Claude has checked them on a copy of that database, or
    with Fred's say-so.
- **Codex never stages, commits or pushes.**
  - Every phase must leave `make dev` working.
  - **An upgrade must never remove or deactivate anything** (Review focus 1).
  - Name the test modules to run. Never run the whole suite.
- **Test data:** small fixtures, at most about 40 data rows each. Cut them
  from the samples, keeping the VizieR header block.
- **Keep comments and naming like the surrounding code.** No question-mark
  icons. UI copy exactly as written here.

## Review focus

1. **Upgrade safety.** An existing database with Sharpless and Barnard loaded
   and no `choice.json`:
   - after the upgrade both catalogs are still on (default), with no
     `choice.json` written;
   - no object is deleted or deactivated;
   - the second load is a no-op (A3 upgrade test; Claude repeats it on a
     copy of a real database).
2. **Remove, then add again.**
   - Unlinked objects are deleted. Linked ones stay inactive, with their
     names.
   - Adding the catalog again reactivates the same `dso.id`s, with no copies.
   - A removed catalog never defers the object step, while a catalog that
     is on with a missing file still does (A3).
3. **Wrong stated matches.** LBN 191 never lands on NGC 6960. It stands
   alone as the whole Cygnus Loop, with the Veil's six pieces as its
   parts. The match screen flags pairs whose sizes differ greatly, and
   matches onto a listed part (A6, B5, the Phase B pattern).
4. **Structured names.**
   - PN G0.0+2.0 finds PN G000.0+02.0.
   - PN G000.0+02.0 and PN G000.0-02.0 stay distinct.
   - MCG-02-05-50 finds MCG-02-05-050.
   - MCG+02-05-050 and MCG-02-05-050 stay distinct (A2).
5. **About 36,000 more objects.** Both planner modes and the catalog page
   stay usable, with no SQLite variable-limit failure (A10). This is
   measured in C2, with a stop threshold.

  - `kind: Literal["vizier", "nightcrate"]`;

  - `designation_catalogs: frozenset[str]`;

  `admin._VIZIER_FETCH_SPECS`). Each Phase B task appends its own.
- `optional_catalog(catalog_id) -> OptionalCatalog | None` and
  `catalogs_for_source(source_id) -> tuple[OptionalCatalog, ...]`.
- `CatalogChoice(chosen: frozenset[str], removed: frozenset[str])` (frozen),
  and:
  - `read_choice(catalogs_root) -> CatalogChoice | None`. It returns `None`
    when the file is missing or invalid; invalid also logs a WARNING and
    the file is left untouched.
  - `write_choice(catalogs_root, choice) -> None`, a temp file plus
    `os.replace`;
  - `with_added(choice, catalog_id)` and `with_removed(choice, catalog_id)`.
- `effective_state(choice: CatalogChoice | None, catalog, applied: str |
  None) -> Literal["on", "off", "removed"]`, a pure function, where
  `applied` is this database's `dso_catalog_applied.state` or `None`. The
  rules apply in this order:
  1. choice present and the id in `chosen` → `"on"`. An explicit add
     overrides a recorded removal;
  2. choice present and the id in `removed` → `"removed"`;
  3. `applied` is `"on"` or `"removed"` → `applied`. A lost or corrupt
     choice file, or a catalog never chosen, keeps what this database
     already applied, and nothing is removed;
  4. no applied row → `"on"` for `legacy_default`, otherwise `"off"`.

  With a choice file present, a legacy catalog that isn't in `removed`
  is `"on"` by rule 4 whenever nothing was applied.
- `ObjectStepPlan`, built by `prepare_object_step(conn, catalogs_root, *,
  force) -> ObjectStepPlan`:
  - `by_id`, `effective`, `run: bool`, `deferred_reason: str | None`;
  - the `ObjectSet`, when it runs.

  `load_catalogs` and the removal preview (A4) both use it, so deferral and
  availability decisions are identical.
- `build_object_set(sources, crossref_path, on_catalogs: frozenset[str])`.
  Collectors filter rows of a shared source by logical catalog, and record
  each entry's `catalog_id`.
- `apply_object_set(conn, new, enrichment_source_ids, *, removed_catalogs:
  frozenset[str], dry_run: bool = False) -> ReconcileReport`.
- `count_references(cur, dso_id, *, exclude: frozenset[str] = frozenset())
  -> int`.
- `ReconcileReport.deleted: int`, `.transferred: int` and
  `.applied: dict[str, str]`.

- [ ] **`choice.json`** sits at `catalogs_root / "choice.json"` and holds
  `{"version": 1, "chosen": [...], "removed": [...]}`.
  - Unknown ids are dropped when read.
  - **Only an explicit `removed` entry ever deletes anything.** A missing
    file, missing metadata or a lost choice file never does.
- [ ] **`prepare_object_step`:**
  - **Effective states:** read `dso_catalog_applied` and compute
    `effective_state` for each catalog. A source is on when any of its catalogs is
    effectively on.
  - **Off and removed sources** are left out of `by_id` and out of the
    deferral, and their crossref inputs are ignored.
  - **Deferral is unchanged** for sources that are on. A source whose
    catalogs are all removed never defers.
  - **`selection_changed`:** any catalog whose effective state differs from
    its applied row (`'on'`/`'removed'`; a missing row counts as off) makes
    the step run, whatever the file hashes. This covers a shared source
    whose file is unchanged (`png` off while `abell_pn` stays on), and a
    catalog that only contributed names or groups.
  - **`object_changed`** keeps `loader.py:520`.
- [ ] **`apply_object_set`:**
  - **An unclaimed old row with positive evidence** that only removed
    catalogs provided it. The evidence is one of:
    - it has at least one previous `dso_source_entry` row, and every row
      belongs to a catalog in `removed_catalogs`;
    - it has no entry rows (legacy rows before 0066, or retained inactive
      rows), and its own `source_catalog_id` maps to a source whose catalogs
      are all removed.

    An empty set is never evidence. Such a row gets:
    - with `count_references(cur, id, exclude=frozenset({"project_dso"}))
      == 0`: delete its `project_dso` rows, then the object, whose
      catalog-derived rows cascade. Count it in `deleted`.
    - otherwise: `active = 0`, keeping `source_key` and the retained
      designations (today's path).
  - **Any other unclaimed row** keeps today's behaviour: inactive, never
    deleted. This includes a source whose file vanished.
  - **The `dso_source_entry` rebuild** also keeps an entry for every
    retained inactive row that still has a `source_key`: its own source and
    key, and its catalog.
  - **Keyless retained rows get no entry.** These are legacy unmatched rows,
    and merged rows kept for an unknown reference, whose key was cleared
    (`reconcile.py:660`). No key is invented, and the survivor's key isn't
    restored. For removal they use the source fallback above: their own
    `source_catalog_id`, and only when every catalog of that source is
    removed.
  - **After the step,** write `dso_catalog_applied`, only for what the step
    actually did:
    - `'on'` for a catalog that was on, available and included;
    - `'removed'` for a removal that was applied;
    - delete the rows of catalogs that are off.

    An unavailable catalog's row is left as it is: one never applied stays
    absent, and one applied before keeps `'on'` and defers.
  - **`selection_changed`** counts only catalogs that are available or
    removed. An on-but-unavailable catalog that was never applied never
    triggers the step, so a fresh install without the Sharpless or Barnard
    files behaves as today (`test_load_orchestration.py:795`).
- [ ] **Identity by contribution.** It replaces the A3 transfer pass from
  round 1, as a matching pass right after exact key matching.
  - A new object's contributing keys are its own `(S, K)` plus every
    `new.merges` key that targets it.
  - **Unmatched by its own key:** it takes the unclaimed old row keyed by
    any of its contributing keys. Failing that, it takes the old row that
    the previous `dso_source_entry` lists for any of those keys.
  - It must match exactly one candidate, and an ambiguous match logs a
    WARNING and inserts as today.
  - A taken row gets the new object's source and key, its columns are
    updated, and it is reactivated. Count it in `transferred`.
  - Rebuild `dso_source_entry` after each apply, with each entry's
    `catalog_id`. An inactive retained row keeps its own `source_key` on the
    `dso` row, so adding the catalog back matches it exactly.
