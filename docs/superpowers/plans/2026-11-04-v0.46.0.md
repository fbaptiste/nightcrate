# v0.46.0 — Gallery, part 1: implementation plan

> **For agentic workers:** Codex implements one task at a time under
> `docs/agent-collaboration.md` §4. Claude reviews each handoff, re-runs
> checks, does the rendered checks and stages. Steps use checkbox syntax.

**Goal:** a Gallery page that shows every project's main image whole, filtered
and sorted on the server, with cards that turn over to show the project's
details. The Projects page thumbnails stop going stale. *(Task 8, added
2026-11-07: views show the user's 4:3 framing for their size, otherwise the
whole image.)*

**Architecture:**
- A pure service, `services/gallery.py`, filters, counts facets and sorts
  plain project records.
- `api/gallery.py` loads those records in a few batched queries, runs the
  shared DSO search for target matches, and returns one response.
- The frontend adds a persistent `/gallery` page with list and grid views.
  Its tiles show the main image's existing renditions by image id.
- The image fix has three parts:
  - browsers no longer cache project images (`no-store`);
  - URLs carry a version made of crop generation ids and a workspace key,
    so an open page notices a changed picture;
  - saving a crop changes everything or nothing, and a crop is deleted with
    the image it depends on.

**Tech stack:** Python 3.14, FastAPI/Pydantic, aiosqlite, React 19, MUI 7,
TanStack Query and Zustand. All are existing; no new dependencies.

**Spec:** [2026-11-04-v0.46.0-design.md](../specs/2026-11-04-v0.46.0-design.md).
**Visual reference:** `.superpowers/mockups/v0.46.0/gallery.html` and its
`shot-*.png` screenshots (local, ignored).

**Base:** branch `v0.46.0/gallery` at `f3fa13c`, with PLAN.md, the spec and
this plan uncommitted.

**Order:** Task 1, then Tasks 2–6 in number order. Claude does the checks
and writes the docs (Task 7).

## Global Constraints

- **No migration** and no new dependency. The one new setting,
  `gallery_view: Literal["list", "small", "medium", "large"] = "medium"`,
  goes in `core/config.py:Settings`.
- **Services** never import `api/` or FastAPI. `api/` owns HTTP, parsing and
  SQL loading; `services/gallery.py` is pure.
- **Imaging dates** come only from `project_session.session_date`, manual and
  auto rows alike. A value counts only if its first ten characters match
  `^\d{4}-\d{2}-\d{2}$` and parse with `date.fromisoformat`. The pattern
  check matters because `fromisoformat` also accepts forms such as
  "2025-W41-1". No other date ever stands in.
- **Never crop or stretch an image to fit:** `object-fit: contain` on the
  mat.
- **The mat is `#000000`** (`common.black`) in both themes.
- **Exact colours from the mockup:**

  | Use | Light | Dark |
  |---|---|---|
  | Paused label and pill | `#b85500` | `#f0a35e` |
  | Complete pill (back and list only) | `#1f63b0` | `#7fb2ea` |
  | Active, Abandoned and Retired labels and pills | `text.secondary` | `text.secondary` |

  Grid captions have no Complete label (Fred). The pills on the back and
  in the list show every status.

  Labels are outlined: 11 px, weight 600, 4 px radius. The words carry the
  meaning.
- **No tab stop inside a button.** `NameWithAlternates` keeps its default
  `tabIndex` of null.
- **Persistent page rules** (`docs/development-decisions.md`, App shell):
  - register the page in `PERSISTENT_ROUTES`, with `element: null` in
    `App.tsx`;
  - add no window-level key listeners; Esc is handled on the tile.
- **All frontend requests are same-origin,** under `/api`.
- **Tablet:** filter inputs are `readOnly` (`PillFilter` already is), and
  nothing works only on hover.
- **Never run the whole backend suite or GPU tests** in the Codex sandbox
  (MLX aborts). Run the commands listed per task.

## Review Focus

1. **Free text in a manual session date.** Values such as "spring 2024",
   "2025-02-30" and "" count as no date; "2025-10-12T23:10:00" counts as
   2025-10-12. Tested in Task 2 (`test_dates_ignore_invalid_text`).
2. **A target whose catalog was removed** (`dso.active = 0`). Its project
   still appears and still matches its designation, catalog, type and
   constellation. Tested in Task 2 (`test_inactive_target_still_matches`).
3. **From later than To.** The API answers 422 with "From is after To". The
   page shows "To is before From" under the To field and keeps the last
   results. Tested in Task 2 (`test_from_after_to_is_422`) and in Claude's
   rendered check.
4. **A session naming a soft-deleted rig.** The rig still shows by name and
   can be filtered on. Tested in Task 2
   (`test_rigs_union_declared_and_session`).
5. **Missing renditions and long names.** A 204 rendition shows "No preview",
   and the card still turns over. A 120-character name ends in an ellipsis on
   the front and is clamped to two lines on the back, with "Open project"
   still visible. The synthetic workspace includes these cases (Task 2), and
   Claude's rendered check covers them.

**Interfaces:**
- Produces:
  - `workspace_key() -> str` in `db/session.py` is a random token
    (`secrets.token_hex(6)`).
    - It is made the first time it is read, and again on every
      `set_db_path` call, which covers startup and every activation.
    - Any workspace opened or reopened, including one recreated at the same
      path, therefore gets a new key, and every image URL changes with it.
    - It only makes URLs differ within one open page; the server never
      checks it.
  - `workspace_key: str` on `ProjectListItem` (each item) and on
    `ProjectResponse`.
  - `ProjectListItem.thumbnail_version: str`: the main image id and the
    project's crop row ids by size, for example `"412.s88.m-.l91"`.
  - `projectThumbnailUrl(id, size, version, ws)` builds
    `/api/projects/{id}/thumbnail?size=…&v=…&ws=…`.
  - `renderedImageUrl(pid, imgId, variant, ws)` builds
    `…/rendered/{variant}?ws=…`.
- Behaviour:
  1. **One identity per picture.**
     - A crop's file is `thumb_crop_{size}_{row_id}.jpg`.
     - Every save replaces the size's row with a new one; AUTOINCREMENT
       never reuses an id. A new crop is therefore a new file and a new
       version, whatever the file times.
     - `get_thumbnail` serves the row's file. For crops saved before this
       version it falls back to the old name `thumb_crop_{size}.jpg`, and
       otherwise to the main image's rendition. *(Superseded by Task 8:
       there is no old-name fallback, and 0068 deleted the old rows.)*
  2. **Saving a crop changes everything or nothing.**
     - Resolve every size's source first. With no main image, answer 422
       "This project has no main image to crop." With an image from another
       project, answer 422 "Image {id} isn't in this project."
     - Generate every size into a temporary file in the project folder. Any
       failure deletes the temporary files and answers 422 "Couldn't make
       the {size} thumbnail from {file name}: {reason}". Nothing has
       changed.
     - In one transaction, first check that each follow-the-main size's
       resolved source is still the main image. If not, delete the
       temporary files and answer 409 "The main image changed while saving.
       Try again." Then replace each size's row, and rename each temporary
       file to its new row's name, which collides with nothing.
     - If a rename or the commit fails: roll back, delete the new files,
       log with `logger.exception` and answer 500 "Couldn't save the
       thumbnails: {reason}". The old rows and files are untouched.
     - After the commit, delete the replaced rows' files, and the
       old-named `thumb_crop_{size}.jpg` only for the sizes just replaced.
       Other sizes' old-named files stay.
  3. **Crops follow their image.**
     - `remove_image` deletes the crops that name the removed image, rows
       and files, before deleting it. The foreign key's `SET NULL` would
       otherwise turn them into follow-the-main crops.
     - When the main image changes, the follow-the-main crops
       (`source_image_id IS NULL`) are deleted with their files. The main
       image changes through `set_main_image` to a different image, or
       through `remove_image` of the main, which promotes another image or
       leaves none.
     - Files are deleted after the commit. Crops that name a specific image
       stay while it exists.
  4. **No browser caching of project images.**
     - `/thumbnail` and `/rendered/{variant}` send
       `Cache-Control: no-store`, so the server always decides the picture.
     - Today they are cached for an hour and a day under URLs of database
       ids, so after a workspace switch the browser can show the other
       workspace's pictures.
     - The images are small, local and loaded lazily. `FileResponse` doesn't
       answer 304, so `no-cache` would download them in full anyway.
     - Within one open page the browser reuses an image it already has for
       the same URL. URLs therefore still carry `v` (thumbnails) and `ws`
       (both), so a changed picture or workspace means a new URL.
     - The server ignores both parameters.
  5. **Image errors reset with the URL.**
     - Both Projects cards set `style.display = "none"` on an image error,
       and that survives a new `src` (`ProjectCard.tsx:55`,
       `ProjectGalleryCard.tsx:44`).
     - Replace it with a small `ProjectImage` component
       (`components/common/ProjectImage.tsx`). It owns its error state and is
       rendered with `key={src}` by its parent, so a new URL remounts it
       with a fresh attempt.
     - It takes `src`, `alt`, `sx` and an optional `fallback` node, shown on
       error.

**Interfaces:**
- Produces, in `services/gallery.py`:
  - `valid_session_date(text: str | None) -> date | None`
  - `GalleryTarget(BaseModel)`: `dso_id: int`, `name: str` (common name, else
    `dso.primary_designation`), `also_known_as: list[str]` (designations'
    display forms in display order, then other names, without the shown name,
    de-duplicated).
  - `GalleryRig(BaseModel)`: `id: int`, `name: str`.
  - `TargetFacts`: `target: GalleryTarget`, `catalogs: frozenset[str]` (its
    designations' catalogs plus its groups' catalogs, as in
    `dso_catalog_clause`), `type_group: str` (`group_for_raw_type`),
    `constellation: str | None`.
  - `ProjectRecord`: `id`, `name`, `status`, `retired: bool`,
    `main_image_id: int | None`, `targets: list[TargetFacts]` (in
    `project_target.created_at, id` order), `dates: list[date]` (distinct and
    sorted), `rigs: list[GalleryRig]`, `integration_minutes: float`.
  - `integration_minutes` is the sum of `exposure_seconds * num_subs` over
    all of the project's `project_session` rows, manual and auto, divided by
    60. That is the total `api/project_sessions.py:_compute_integration`
    gives (`:277-279`), loaded in one grouped query. It is 0.0 with no
    sessions.
  - `rigs` is the union of `project_rig` and `project_session.rig_id`, with
    rigs ordered by `rig.sort_order, rig.name`. Soft-deleted rigs are
    included.
  - `GalleryQuery(BaseModel)`:
    - `q: str | None`
    - `catalogs`, `type_groups`, `constellations`, `statuses: list[str]`
    - `rig_ids: list[int]`
    - `date_from`, `date_to: date | None`
    - `include_undated: bool = False`, `include_retired: bool = False`
    - `search_images: bool = False`
    - `sort: Literal["latest", "first", "name"] = "latest"`, `desc: bool = True`
  - `GalleryItem(BaseModel)`:
    - `project_id`, `name`, `status`, `retired`, `main_image_id: int | None`
    - `targets: list[GalleryTarget]`
    - `first_date`, `last_date: str | None` (ISO)
    - `nights: int`
    - `imaging_runs: list[ImagingRun]`, where `ImagingRun(BaseModel)` has
      `start`, `end: str` (`YYYY-MM`). These are the months with valid
      session dates, oldest first. Consecutive calendar months merge,
      across the new year too: Dec 2023 and Jan 2024 make one run.
    - `integration_minutes: float`
    - `rigs: list[GalleryRig]`
    - `found_in_image: list[str]`: the preferred names of objects in the
      project's plate-solved image that match `q`. It is filled only when
      `search_images` is on and the project's name and main targets don't
      match; otherwise `[]`. Main targets are never listed; names are in
      display order.
  - `FacetCount(BaseModel)`: `code: str`, `count: int`.
  - `RigFacetCount(BaseModel)`: `id: int`, `name: str`, `count: int`.
  - `GalleryFacets(BaseModel)`:
    - `catalogs`, `type_groups`, `constellations`, `statuses:
      list[FacetCount]`
    - `rigs: list[RigFacetCount]`
  - `GalleryResult(BaseModel)`: `items: list[GalleryItem]`, `facets:
    GalleryFacets` and `library_total: int`. `library_total` counts every
    project, with no filters and retired projects included; the page uses it
    to choose its empty state.
  - `build_gallery(records: list[ProjectRecord], query: GalleryQuery, *,
    target_search_hits: set[int] | None, image_search_hits: dict[int,
    list[str]] | None) -> GalleryResult`:
    - `target_search_hits` is the set of project ids whose targets match `q`
      (`None` when `q` is empty);
    - `image_search_hits` maps project ids to the preferred names of
      matching objects in their solved image. It is `None` unless `q` is
      set and `search_images` is on.
- Produces, in `api/gallery.py`: `GET /api/gallery`, returning
  `GalleryResponse(GalleryResult)` with an added `workspace_key: str` (Task
  1). The page builds rendition URLs with it.
  - Query parameters:
    - `q`
    - `catalog`, `type_group`, `constellation`, `status`, `rig`
      (comma-separated, as in `api/dso.py`)
    - `imaged_from`, `imaged_to` (`YYYY-MM-DD`)
    - `include_undated`, `include_retired`, `sort`, `desc`
  - It returns `GalleryResponse`.
  - It answers 422 for a malformed date, a non-integer rig id, or
    `imaged_from > imaged_to` (detail "From is after To").
- Rules `build_gallery` must follow:
  - **Matching:**
    - name search is case-insensitive substring on the project name, OR the
      project id is in `target_search_hits`, OR, with `search_images`, it is
      in `image_search_hits`;
    - filters combine with AND; the choices within a filter combine with OR;
    - a project matches a target-level filter when any of its targets
      matches;
    - the date range matches when any date is within `[from, to]`, both ends
      included; `include_undated` adds projects with no dates, and applies
      only when a bound is set.
  - **Items:** every matching project, with or without a main image
    (Fred, 2026-11-04).
  - **Facets:**
    - count matching projects, applying every filter except the facet's
      own;
    - a project counts at most once per option, however many targets or
      sessions share it;
    - omit zero counts, unless the code is selected;
    - the server's order is deterministic: catalogs by `catalog_rank` then
      code; type groups in `TYPE_GROUPS` order; constellations by code;
      statuses in the order active, paused, complete, abandoned; rigs in rig
      order. The UI's `PillFilter` sorts options alphabetically, as it does
      in the catalog and planner, and that is accepted.
    - Codes are the database's own: catalog codes such as `messier` and
      `sharpless2` (`lib/catalogNames.ts`), constellation codes such as
      `Ori`, and type-group names from `group_for_raw_type`.
  - **Sort:**
    - `latest` uses the last date, `first` the first date, `name` the
      casefolded name;
    - undated projects come last in both directions;
    - ties go by casefolded name ascending, then id ascending.
- Loading, in `api/gallery.py`:
  - one query for all projects, retired included, each with its main
    image id. Retirement is applied in `build_gallery`, so
    `library_total` sees every project;
  - batched queries for targets and DSO facts (no `d.active` filter), group
    catalogs, rigs and session dates;
  - `load_designations` and `load_other_names`;
  - for `q`: `SELECT DISTINCT pt.project_id FROM project_target pt JOIN dso d
    ON d.id = pt.dso_id WHERE <dso_search_clause(q)>`;
  - for `q` with `search_images`: `SELECT ps.project_id, d.id FROM
    project_solve ps JOIN project_dso pd ON pd.solve_id = ps.id JOIN dso d ON
    d.id = pd.dso_id WHERE <dso_search_clause(q)>`. Drop the project's own
    main targets and map the rest to preferred names;
  - API query parameter `search_images` (bool, default false).
- `tests/gallery_library.py`:
  - `async def make_library_dsos(conn) -> LibraryDsos` inserts about 40 DSOs
    with designations across M, NGC, IC, Sh2, C and LBN. It includes one Arp
    group, several constellations and types, and one inactive DSO.
  - `async def populate_gallery_projects(conn, dso_ids: list[int], *,
    n_projects: int = 500, seed: int = 46) -> LibrarySummary` inserts rigs
    (one soft-deleted), projects in every status (some retired), main images
    for 90 % of them, and targets. Its sessions are manual and auto, with
    valid dates, datetimes, None and non-date text.
  - `LibrarySummary` records the expected visible count and per-status
    counts.
- `scripts/make_gallery_workspace.py --source-db PATH --dest DIR --projects
  500 --seed 46` builds a scratch workspace from a real database, which
  already has its catalogs.
  - **Guard:** after resolving paths, `DIR` must be new or empty. It must
    not be inside or contain the app-data folder, the source database's
    folder, or any workspace registered in the app's `config.json`
    (`databases`). The script copies the source into `DIR/nightcrate.db`
    and writes only inside `DIR`.
  - It then:
    - picks real active DSOs;
    - calls `populate_gallery_projects`;
    - writes synthetic star-field JPEG renditions (`thumb_sm/md/lg/full`)
      in four aspect ratios, portrait included, to
      `DIR/project_data/{pid}/img_{id}/`;
    - leaves 5 main images without renditions;
    - gives 3 projects 120-character names, and 2 projects 8 targets and 4
      rigs each.
  - It never touches the source database or its folder.

**Behaviour:**
- **`estimate_focal_length_mm(pixel_size_um, pixel_scale_arcsec) -> float |
  None`** = 206.265 × pixel_size_um ÷ pixel_scale_arcsec. It returns None
  unless both values are finite and > 0. It is the inverse of
  `compute_image_scale`.

  | Pixel size | Pixel scale | Result |
  |---|---|---|
  | 3.76 µm | 0.775″/px | 1000.72 mm |
  | 4.63 µm | 1.91″/px | 500.00 mm |
  | 3.76 µm | 0 | None |
  | 0 | 1.0″/px | None |
  | −3.76 µm, NaN or infinity in either argument | — | None |
  | None in either argument | — | None |

- **`ProjectSolveResponse.focal_length_estimates`** is a list of
  `FocalLengthEstimate {rig_id, rig_name, camera_name, pixel_size_um,
  rig_focal_length_mm, estimated_focal_length_mm}`.
  - Which rigs: those declared on the project plus those its sessions name,
    deduplicated, retired and not-mine included. They are ordered as in the
    gallery: `sort_order`, then `name COLLATE NOCASE`, then `id`. Values come
    from `rig_summary`.
  - The list is empty when the solve has no pixel scale. A rig whose pixel
    size is missing or zero is left out.
  - Every response that `_assemble_response` builds carries the list.
- **Freshness:** changes to the project's rigs and to its sessions
  invalidate `["project-solve", projectId]`.
- **The "Estimated focal length" row** (Codex's label), after "Pixel scale":
  - one line per estimate, for example: "≈ 1,001 mm with the
    {camera_name}'s 3.76 µm pixels · {rig_name}: 1,000 mm";
  - a one-line note under it in `text.secondary`. The draft: "Assumes the
    image's pixels are the camera's own. Binning, drizzling or resizing
    changes this estimate." "A multiple of the true value" was dropped as
    ambiguous: for example, 2× binning halves the estimate and a 2× drizzle
    doubles it. The note names no factor;
  - no row when the list is empty.
