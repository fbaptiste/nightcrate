# v0.47.0 — Rig history, project setups, project software: implementation plan

> **For agentic workers:** Codex implements this plan one phase at a time
> under `docs/agent-collaboration.md` §4, in the worktree
> `.superpowers/wt-v0.47.0` on branch `v0.47.0/rigs-in-use`. Codex never
> stages, commits, pushes or opens a PR; each phase ends with a report.
> Claude reviews every phase. Steps use checkbox (`- [ ]`) syntax.
> Codex runs only the test modules a task names (never the whole suite or
> GPU tests: §10); Claude runs the full suite outside the sandbox. Reviewed
> work reaches the main checkout only on Fred's word, because his dev
> server applies 0069 as soon as it appears there.

**Goal:** a rig change either corrects every record or applies from now on;
a project shows and can adjust the setup it was shot with; projects record
the software and versions they were processed with.

**Architecture:** a rig keeps one identity. Its history is `rig_setup` rows
(earlier setups) stamped on frames and capture batches; a project's own
changes are one `project_rig_change` row per (project, rig). A view,
`sub_frame_equipment`, resolves each frame's effective telescope
configuration and camera, and every reader of equipment for records uses
it. Software gains `software_version` and `project_software`.

**Tech stack:** Python 3.14, FastAPI, Pydantic, aiosqlite, yoyo SQL
migrations; React/TypeScript, MUI, TanStack Query.

**Spec:** [v0.47.0 design](../specs/2026-11-07-v0.47.0-design.md) (approved
by Fred, 2026-11-07). Mockups: `.superpowers/mockups/v0.47.0/rigs-and-software.html`
(local; approved with the spec).

## Global constraints

- Never edit an existing migration; this version adds `0069` only.
- `ALTER TABLE ADD COLUMN` only; no parent-table reshape.
- Services take a caller-owned connection and never commit; `api/` owns
  transactions. Services never import `api/` or FastAPI.
- Router 500 handlers log with `logger.exception`; structured log prefix
  `[rigs]`, `[rig-setups]`, `[software]`.
- UI: theme tokens; colour never carries meaning alone; no question-mark
  icons; drill-downs open in a panel below the content with a close button;
  Autocompletes grouped and sorted by their group key first.
- Exact copy from the spec and mockups (prompt title, button labels, panel
  labels, "for this project", "Used by N rigs and M projects. The change
  applies to all of them.").
- Generic rig, project and equipment names in tests, docs and fixtures.
- Frontend has no test runner: frontend tasks are verified by
  `npm run build` and Claude's rendered checks.

## Definitions used by every task

- **Part groups** (`PART_GROUPS`, in this order): `telescope`
  (`telescope_configuration_id`), `camera` (`camera_id`), `filters`
  (`filter_wheel_id`, `single_filter_id`, filter slots: one group because
  slots depend on the wheel), `mount` (`mount_id`), `focuser`
  (`focuser_id`), `guider` (`oag_id`, `guide_scope_id`: the guiding mode),
  `guide_camera` (`guide_camera_id`), `computer` (`computer_id`),
  `software` (software ids). Overrides and corrections work per group, so
  swapping the OAG for a guide scope leaves the guide camera following the
  rig (mockup screen 3).
- **A frame's setup rig:** its `rig_id`, else the project's single rig
  (the derive fallback, `session_derivation.py:204-211`). Frame
  computations (pixel scale, ADU, calibration) use `rig_id` only, as today;
  batches use the setup rig.
- **Stamps:** one `sub_frame_rig_setup` row per (frame, rig), so a frame
  keeps its earlier setup for each rig it has been on; a batch has one
  `project_session.rig_setup_id`.
- **In use:** the rig appears in `project_rig`, `project_session`,
  `session`, `sub_frame` or `project_source_folder`.
- **Project count:** distinct `project_id` over those five tables.
- **Night count:** distinct (project, observing night) over frames (by
  setup rig; night = `observing_night(date_obs_utc, project tz)`),
  `session` rows, and all `project_session` rows, derived and manual (night
  = date part of `session_date`; NULL dates are not counted). *(Revised in
  review: derived batches with no frames left still count, because the
  Sessions tab shows them.)*
- **A stamp applies** to a frame on rig R when the frame has a
  `sub_frame_rig_setup` row for R, and to a batch when its
  `rig_setup_id` names a setup of the batch's rig. Otherwise the record is
  on R's current setup.
- **Transactions:** every endpoint that compares old and new equipment,
  splits, stamps or corrects starts with `BEGIN IMMEDIATE` before its
  first read (pattern: `api/projects.py:476`), commits once, and rolls
  back on any exception.
- **Effective part** for a frame or batch in project P on rig R: P's change
  for that group, else the applying stamp's part, else R's current part.

## Review focus

1. **Untagged folders in a one-rig project** (common: tagging is
   optional): ingest, derive, split, re-derive, move a night, re-derive —
   the batches keep their setup throughout (Task 4
   `test_untagged_single_rig_project_keeps_setups`).
2. **Rescan and re-tag after "from now on":** a real scan, a re-tag to
   another rig that is then changed "from now on", and a re-tag back must
   leave old frames on their first rig's earlier setup (Task 2
   `test_stamp_per_rig_survives_other_rig_split`, Task 4
   `test_rescan_through_scan_endpoint_keeps_stamps`).
3. **Two successive changes and part-level corrections:** three setups
   stay apart; a guide-camera correction reaches a setup whose guider
   differs (Task 2 `test_two_splits_then_correction`,
   `test_guide_camera_correction_ignores_guider`).
4. **Cancel and failure change nothing:** a 409, and a failure injected
   after stamping, leave the rig, slots, software and every stamp as they
   were (Task 3 `test_needs_choice_changes_nothing`,
   `test_failed_split_rolls_back`).
5. **Retired things stay visible and survive saves:** retired rigs on a
   project, retired programs and versions (Tasks 5, 7, 9, 10).
