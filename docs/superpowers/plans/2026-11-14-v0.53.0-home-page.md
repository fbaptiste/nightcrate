# v0.53.0 — Home page: implementation plan

> **For agentic workers:** Codex implements this plan phase by phase in a
> worktree; Claude reviews each phase (`docs/agent-collaboration.md`). Steps
> use checkbox (`- [ ]`) syntax.

**Goal:** a Home page that shows where your projects stand (by stage, recent
projects, the last 12 months, rigs and locations) and the next two weeks'
weather per location, plus a hand-set "Ready to process" status and the joke
wand moved to the nav.

**Architecture:**
- One summary endpoint (`GET /api/home`): the SQL lives in the router, and
  the aggregation in a pure service.
- One light per-location endpoint (`GET /api/weather/fortnight`), built on
  the existing forecast pipeline.
- A migration widens the project status CHECK.
- On the frontend, a Home page built from small components, with pure
  helpers checked by a script.

**Tech stack:** FastAPI, Pydantic, aiosqlite, yoyo; React, TypeScript, MUI,
TanStack Query.

**Spec:** `docs/superpowers/specs/2026-11-14-v0.53.0-home-page-design.md`
(the approved design; read it all first).

## Global constraints

- `CLAUDE.md` applies: raw SQL; services never import `api/` or FastAPI;
  theme tokens; no new dependencies; never edit an existing migration.
- The status value is `ready_to_process`, with the label "Ready to process".
  Order everywhere: active, ready_to_process, paused, complete, abandoned.
- Copy is exact as written in the spec (sections 3–9).
- Colours are exact as in the spec's table (section 2) and its pill
  colours (section 1).
- "Active project" means `status = 'active'` (spec section 1).
- Retired projects (`project.active = 0`) are excluded from every Home
  figure. Retired rigs and locations are excluded only from the panels and
  the forecast rows. Their projects' integration still counts.
- Session dates go through `services/gallery.valid_session_date` before any
  ranking, grouping or window filter. Minutes are floats.
- Desktop is verified; nothing is checked on tablets in this version. Keep
  the existing touch-safe patterns anyway.

## Review focus

- **The migration on a real database:** every column added to `project`
  after 0031, every index and trigger, and every child foreign key survive.
  Any loss here destroys user data.
- **Event-loop blocking:** four uncached forecast rows must not delay
  `GET /api/home`.
- **Window boundaries:** the first day of the window included, the day
  before excluded, and January's window.
- **Stage counts agree with the Projects page filter** for every stage,
  retired projects included in neither.
- **Empty databases:** no projects, sessions, pictures, rigs or locations.
  The page renders every empty state without errors.

### Task A2: The Home summary

**Files:**
- Create:
  - `backend/src/nightcrate/services/home.py` (pure, no I/O);
  - `backend/src/nightcrate/api/home.py` (SQL and the router);
  - `backend/src/nightcrate/api/home_models.py`.
- Modify: `backend/src/nightcrate/main.py` (include the router).
- Test: `backend/tests/test_home_service.py` (pure);
  `backend/tests/test_home_api.py` (a temporary database through the app,
  as `test_project_info_api.py` does).

**Interfaces** (`services/home.py`; names are suggestions, shapes are
binding):
- `window_start(today: date) -> date`: the first day of the month 11 months
  before `today`'s month (`2026-11-14` → `2025-12-01`; `2026-01-10` →
  `2025-02-01`).
- `month_keys(today: date) -> list[str]`: 12 `"YYYY-MM"` keys, oldest first.
- `stage_of(status: str, minutes: float) -> str`.
- `summarise_year(sessions, images, today) -> YearSummary`.
  - `sessions` are `(project_id, project_name, session_date: date,
    minutes: float)` rows, already normalised by `valid_session_date`.
    `images` are `(added: date,)` rows: the local date of `created_at`.
  - Rows outside `[window_start(today), today]` are ignored, so tomorrow's
    date is excluded.
  - `best_night` takes the date with the most minutes. Ties go to the
    later date, and its project to the one with the most minutes that night
    (then by name). `other_projects` counts the other projects that night.
  - `nights` counts distinct dates.
- `rank_forecast_locations(locations, active_counts) -> list[ForecastLocation]`.
  `locations` are non-retired `(id, name, is_default)`, and `active_counts`
  maps a location id to its active projects. It applies spec section 5's
  rule, at most 4. `note` is `"default"`, `"used"` (with `active_projects`),
  or `None`.
- `rank_rigs(...)` and `rank_locations(...)` apply section 8's ordering, at
  most 5.

**`GET /api/home`** returns `HomeSummary`, exactly the spec's section 10
shape.
- "Today" is `date.today()`, through a module-level `_today()` that tests
  patch.
- **`recent`:**
  - the top 3 by the latest validated session date (`valid_session_date`),
    ties by name, non-retired;
  - `lines`, `total_minutes`, `nights` and `last_date` must equal what
    `GET /api/projects/{id}/integration` reports for that project. Extract
    its computation into a function both use; don't re-implement the
    passband expansion;
  - `target_label` as the Gallery derives it (`load_project_records` and
    `build_gallery`, as `project_info.py` does). `constellation` comes from
    the plate solve's centre, as `project_info.py:71` computes it, or null;
  - `has_image` and `thumbnail_version` as `ProjectListItem` provides them.
- **`latest_picture`:** the newest `project_image.created_at` (ties by the
  higher id) among non-retired projects. `added` is the local date of
  `created_at`.
- **`rigs`:** see spec section 8. Hours, nights (distinct `session_date`)
  and `last_used` (all time) come from `project_session.rig_id`.
  `active_projects` counts the distinct `status = 'active'` projects linked
  by `project_rig` or by a session with that rig.
- **`locations`:** the same, through `project.location_id`.
- **`forecast_locations`:** see `rank_forecast_locations`.

**Tests** (concrete values):
- **`window_start`:** 2026-11-14 → 2025-12-01; 2026-01-10 → 2025-02-01;
  2026-12-31 → 2026-01-01; a 29 February today.
- **`summarise_year`:**
  - a session on `window_start` counts, and one the day before doesn't;
  - two projects on one night: minutes summed, the larger project named,
    and `other_projects` = 1;
  - `months` has 12 entries with the right sums;
  - no sessions gives `best_night` None and zeros.
- **`rank_forecast_locations`:**
  - a default plus three used locations gives 4, default first;
  - a default plus five used locations is capped at 4;
  - no default with two used locations gives 2;
  - no default and none used gives the first 4 by name;
  - no locations gives `[]`.
- **`summarise_year`, more:** today's date is included and tomorrow's
  excluded; two sessions on one date are one night; an image created at
  23:30 local time counts on that local date.
- **API:**
  - the six stage counts against a seeded database;
  - **hand-computed expected values,** not a comparison with another
    endpoint alone. A 60-minute dual-band (Ha+OIII) session gives Ha 60 and
    OIII 60 but a total of 60; an unknown filter label keeps its own line;
    an undated session counts in the totals but not in nights or recency;
  - a retired rig's sessions still count in a project's figures, while the
    rig is absent from `rigs`;
  - a retired project excluded;
  - `recent` order and its lines equal to the integration endpoint for the
    same project;
  - `latest_picture` skips a retired project;
  - rigs/locations: in-window minutes, an out-of-window session
    contributing to `last_used` only, others' rigs excluded, the cap of 5;
  - an empty database returns zeros, empty lists, `latest_picture` null and
    12 zero months.

### Task A3: The fortnight endpoint and moon-free hours

**Files:**
- Modify: `api/weather.py`, `api/weather_models.py`.
- Test: `backend/tests/test_weather_fortnight.py`.

**Interfaces:**
- `NightResponse` gains `moonless_dark_hours: float`, from the night's
  `NightSummary`.
- **Split the forecast handler:**
  - `async def _forecast_inputs(...)` does the async work: the location and
    rules lookup, and `_load_forecast_data`;
  - `def _build_forecast(inputs, request, now) -> ForecastResponse` does
    all the CPU work: `_astronomy_nights`, `moon_altitudes_at`, the
    evaluation and the response building;
  - the endpoint awaits the first, then runs the second in one
    `await asyncio.to_thread(...)`.
  - Check that `_night_summary_cached`, `moon_altitudes_at` and the
    evaluator are safe in a worker thread (no shared mutable state beyond
    `lru_cache`), and report what you checked.
- **`GET /api/weather/fortnight?location_id=`** returns
  `FortnightResponse {location_id, evaluated_at, stale_since: str | None,
  nights: list[FortnightNight]}`, where
  `FortnightNight` is `{date: str, verdict: Verdict, moonless_dark_hours:
  float}`.
  - It uses `_forecast_inputs` and `_build_forecast` with the saved rules
    and no night controls, then maps the response. Don't duplicate the
    pipeline.
  - `stale_since` is the oldest fetch time among the sources the forecast
    marks stale (`stale_sources`): the main forecast's `fetched_at`, the
    cloud models' fetch time, or both. It's null when nothing is stale.
  - A 404 for an unknown location behaves as the forecast does.

**Tests** (stub `_load_forecast_data` and `_now`, as the existing weather
tests do):
- the fortnight's nights equal the forecast endpoint's nights (same
  dates, verdicts and `moonless_dark_hours`) for the same stubbed data;
- the saved rules are used: changing a saved rule changes a verdict;
- `stale_since`, both ways: a fresh main forecast with stale cloud models
  reports the cloud models' time, and a stale main forecast with fresh
  cloud models reports the main forecast's time;
- a provider failure with no cache behaves as the forecast endpoint does;
- the endpoint runs the build through `asyncio.to_thread`. Patch it to
  record the call;
- **responsiveness is Claude's measurement** (Phase C), with real CPU work:
  clear the weather cache, start four cold fortnight requests, and time
  `GET /api/home` issued while they run. It must answer in under 300 ms;
  inline computation would take seconds. Fetches are stubbed, so the timing
  is the CPU's alone;
- an unknown location gives 404.
