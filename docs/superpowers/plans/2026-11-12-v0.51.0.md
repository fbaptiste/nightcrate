# v0.51.0 — Cleanup before Distribution: implementation plan

> **For agentic workers:** Codex implements one phase at a time under
> `docs/agent-collaboration.md` §4; Claude reviews each phase. Steps use
> checkbox (`- [ ]`) syntax. Never stage, commit or push.

**Goal:** the Gallery viewer plays a slideshow on a computer, a tablet and
a phone, with a remembered interval. Filter swatches tell the truth for
equipment filters with no lines on record, retired filters and frames whose
file names no filter. PixInsight projects with unusable image paths get a
clear message. A bad saved setting resets only itself, and a save sends
only what changed.

**Architecture:**
- **Settings:** `core/config.py` loads each stored field on its own and
  gains a partial update. `PATCH /api/settings` sends only changed fields,
  and the frontend store uses it.
- **Integration summary:** it marks "Not recorded" lines with a boolean.
  The frame-list endpoints gain a `filter_missing` scope.
- **PixInsight paths:** one path check in `pxiproject_io`, used by its three
  readers. `PxiProjectError` becomes a `ValueError`, so the image API's
  existing 422 handlers carry its message.
- **Slideshow:** pure interval helpers, a `useSlideshow` hook, a
  `SlideshowBar` component and the viewer's layout by its own size.

**Tech stack:** Python 3.14, FastAPI, Pydantic, aiosqlite; React,
TypeScript, MUI, Zustand, TanStack Query. No new dependency, no migration.

**Spec:** [v0.51.0 design](../specs/2026-11-12-v0.51.0-design.md), approved
by Fred on 2026-11-12 ("otherwise everything else looks good. go ahead an
implement"). Mockup: `.superpowers/mockups/v0.51.0/slideshow.html` (local;
the built viewer must look like it).

**Base:** `104888f` on `v0.51.0/cleanup`.
- Codex works in the worktree `.superpowers/wt-v0.51.0`, detached at the
  base. Fred's `make dev` runs from the main checkout, and a backend edit
  there would reload it on his database.
- The spec, this plan and the mockup are read from the main checkout.

**High-stakes** (`docs/agent-collaboration.md` §5):
- settings persistence: a fallback that decides which stored values
  survive, and a new write path;
- backend–frontend contracts: `PATCH /api/settings`, the new
  `not_recorded` fields, the `filter_missing` query parameter;
- path handling for PixInsight project references.

They get a fresh independent review and runs on a copy of Fred's data.

## Global constraints

- The interval steps are exactly `2, 3, 4, 5, 6, 8, 10, 15, 20, 30`
  seconds; the default is `5`.
- The words are exact: "Not recorded"; "{n} s per picture", with
  " (shortest)" or " (longest)" appended at an end; "Play slideshow" and
  "Pause slideshow"; "Shorter interval: {n} seconds per picture" and
  "Longer interval: {n} seconds per picture" ("Shortest interval" and
  "Longest interval" at the ends).
- ↑ lengthens the interval and ↓ shortens it. In the bar, − shortens and +
  lengthens.
- Keys are handled in the viewer's own `onKeyDown`: no window or document
  key listeners (development decisions, Gallery: the page is persistent).
- The viewer stays black in both themes. Use the existing viewer colours
  (`#000000`, `#e2e0dd`, `#a3a09b`, white with 0.28 border and 0.08 fill),
  the 6-digit-hex rule, and no new theme tokens.
- Touch targets in the viewer are at least 44 px.
- Services raise domain errors, never `HTTPException`; routers translate
  them (`CLAUDE.md`, Architecture).
- Settings stay one row per field in `settings`; no migration (`CLAUDE.md`,
  Shared patterns).
- Readers stay worker-safe: `pxiproject_io` runs inside spawned processes.
- No new dependency. The frontend has no test runner; frontend behaviour is
  checked by `npm run build`, ESLint and Claude's rendered checks.
- Copy and layout follow the mockup. Where this plan and the mockup
  disagree on looks, the mockup wins; on behaviour, the spec wins.

## Review focus

The five conditions most likely to bite a user that the spec implies but no
single test exercises directly. Each has its pinning check in the owning
task.

1. **A slow or failed full-size picture while playing.** The countdown must
   start only when the picture appears, and a failure must not stall the
   show (Task B3, rendered check with throttled network; failure via a
   deleted rendition).
2. **Two devices saving different settings.** Device A saves the interval
   and device B, loaded earlier, saves the Gallery view. Both values
   survive (Task A1, `test_partial_saves_from_two_clients_keep_both`).
3. **A stored value from a later version.** For example
   `gallery_view = "huge"` or an interval of 7. Only that field falls back,
   and loading writes nothing (Task A1,
   `test_invalid_field_falls_back_alone_and_nothing_is_written`).
4. **Closing the viewer or hiding the page mid-countdown.** No step after
   close, no state update on an unmounted viewer, and the wake lock is
   released (Task B3, rendered check plus the hook's cleanup).
5. **Space while a viewer button has focus.** It toggles once, not twice
   (Task B3, rendered check: focus the play button, press Space, state
   flips once).

## Phase B — frontend

### Task B1: Settings client sends only what changed; the interval field

**Files:**
- Modify: `frontend/src/api/settings.ts`
- Modify: `frontend/src/stores/settingsStore.ts`
- Modify: `frontend/src/lib/usePlannerSettingsSync.ts`

**Interfaces:**
- Consumes: `PATCH /api/settings` (A1).
- Produces:
  - `Settings.gallery_slideshow_seconds: SlideshowSeconds`;
  - `type SlideshowSeconds = 2 | 3 | 4 | 5 | 6 | 8 | 10 | 15 | 20 | 30`;
  - `saveSettingsPatch(patch: Partial<Settings>): Promise<Settings>`;
  - the store's `update(patch): Promise<boolean>` sends only changed
    fields, one request at a time. It resolves `true` when the request
    carrying this patch succeeded and `false` when it failed. It never
    rejects, so existing `void` callers are unaffected.

- [ ] **Step 1: `saveSettingsPatch`** (PATCH, JSON body). Keep `saveSettings` (PUT) only for callers that mean to save the whole object; list callers with `grep -rn "saveSettings(" frontend/src`.
- [ ] **Step 2: The store saves in order.** The generation counter only chose which response to show; it did not order the server's writes. With partial saves, a reversed completion either drops an earlier field from the UI or leaves the server holding an older value (Codex's in-memory run).
  - Keep `pending: Partial<Settings>`, the patches not yet confirmed, and
    one request in flight at most.
  - `update(patch)` applies the patch optimistically, merges it into the
    patches waiting to be sent, and starts a request if none is in flight.
  - When a request ends, the next one sends everything that accumulated
    while it ran, coalesced, with later values winning.
  - **Response:** state = response, overlaid with every patch still
    unconfirmed (in flight or waiting). So a newer local choice is never
    replaced by an older server value.
  - **Failure:** roll back only the fields of the failed request that no
    later patch has changed since, to the last confirmed server value.
    Keep the queue going.
  - Each caller's promise resolves when its own patch's request settles.
- [ ] **Step 3: Planner sync sends only what changed.** `usePlannerSettingsSync` builds the whole Planner snapshot (`buildPayload`) whenever any part changes. That lets a stale device overwrite another device's Planner choices.
  - Keep three refs per Planner field:
    - **confirmed:** hydrated from the server, then set to a call's value
      when that call resolves `true`. The store's ordered queue makes
      resolution order match send order;
    - **sent:** the last value handed to `update`, starting equal to
      confirmed;
    - **version:** a counter that increases with every send of that field.
  - Send only the fields whose current value differs from **sent**. Before
    calling `update`, record each field's value in sent and its new
    version in the call. Compare arrays and tuples by value. So A → B → A,
    with B still in flight, sends A again, and the store's ordered queue
    leaves the server on A.
  - **When a call resolves `false`:** for each of its fields whose current
    version is still the call's version (no later send of that field, even
    of the same value), reset sent to confirmed. The field then differs
    from sent, stays dirty, and goes out with the next Planner change.
    Comparing values instead would let an older failure erase a newer
    pending send of the same value (Codex, round 4). The Planner keeps
