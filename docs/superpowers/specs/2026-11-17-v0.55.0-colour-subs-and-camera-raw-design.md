# v0.55.0 — Colour-camera subs and camera raw files

A sub from a one-shot-colour camera shows in NightCrate as a grey mosaic. Its
2×2 colour-filter checker turns into a coarse grid when zoomed out, as Fred
saw on an M101 sub (2026-11-15). Raw files from DSLR and mirrorless cameras
can't be read at all.

This version makes colour subs show in colour, and lets camera raw files
work wherever FITS and XISF subs do. Fred will mostly use it for **raw files
cataloged in projects**, and secondly for viewing subs in the image analyzer
(2026-11-17).

## Evidence

- **Today** (code map, 2026-11-17):
  - nothing in the pixel path knows a colour pattern. A colour sub loads
    as a 2-D grey mosaic, and statistics, frame quality, the aberration
    inspector and every thumbnail treat it as mono;
  - the native solver merges 2×2 blocks when `BAYERPAT` is present
    (`native_solver/extract.py:272`);
  - `fits_header_map` maps `BAYERPAT`, `COLORTYP` and `ROWORDER`, but
    nothing reads them;
  - the XISF reader ignores `ColorFilterArray` (`xisf_io.py:285–326`).
- **Loading is scattered:** `pixel_loader.load_normalized` is the shared
  loader. Older hand-written loaders remain:
  - `api/images.py:142`;
  - `api/aberration.py:51` (it also drops the PixInsight-project index, a
    latent bug);
  - `project_images.py:56`;
  - `image_preview.py:282`;
  - `plate_solve.py:370`, `:414` and `:1454`.
- **The colour display path already exists:** finished RGB images (shape
  `(3,H,W)`) get per-channel statistics, an unlinked auto-stretch, an R/G/B
  histogram and a per-plane PNG render (`imaging.py:183`, `:333`, `:387`).
- **Thumbnails** shrink by taking every n-th pixel
  (`catalog_thumbnail.py:128`, `image_preview.py:200`). On a mosaic that
  samples a single colour site.
- **The pixel inspector** reads the stretched 8-bit PNG in the browser
  (`FitsImage.tsx:268–308`). The backend's raw-value `/pixel` endpoint
  (`api/images.py:401`) is never called.
- **The seeded equipment data** records `sensor.bayer_pattern` for 36 of
  77 sensors, all RGGB; the rest are mono. The column allows RGGB, GRBG,
  GBRG and BGGR.
- **Raw formats and libraries:** Codex's research
  (`.superpowers/codex/v0.55.0/04-codex-raw-research.md`, with sources).
  Claude checked the library facts on PyPI:
  - `rawpy` 0.28.0 (MIT, over LibRaw) has Python 3.14 wheels for macOS 11+
    arm64, Windows x64 and Linux x64. Its official wheels leave out the GPL
    demosaic packs;
  - `exiv2` 2.16.1 (GPLv3) has Python 3.14 wheels for macOS 14+ arm64,
    Windows x64 and Linux x64.
- **Sample files:** 18 CC0 raw files from raw.pixls.us, in
  `Imaging/sample_projects/camera_raw/` on Fred's external drive, with a
  README listing the camera, mode and checksum of each. They are daytime
  shots. No openly licensed DSLR night-sky set exists. These files aren't
  committed: they're 421 MB, and fixtures are generated (see Tests).

## Goals

1. Colour subs (FITS, XISF and raw) show in colour in the analyzer, the
   project's file thumbnails and the gallery, instead of a grey mosaic.
2. Statistics, histograms and the pixel inspector report what the sensor
   recorded, per colour, never interpolated values.
3. Star measurements (frame quality, the aberration inspector, the native
   solver) work on colour subs, without measuring invented pixels.
4. Camera raw files (CR2, CR3, NEF, ARW, RAF including X-Trans, ORF, RW2,
   PEF, DNG) open in the analyzer and catalog in project scans, archives
   included. Their capture facts become typed fields.
5. Batch correction in the Files tab covers the filter as well as the frame
   type, for every format.
6. The analyzer's metadata tab shows whatever each file type carries.

## Non-goals

- Processing: calibration, stacking, white balance, colour grading, noise
  reduction. Those belong in PixInsight and Siril (`CLAUDE.md`).
- Raw files as finished images. A raw file is capture data; the finished
  image import keeps its formats.
- Writing to raw files. Their metadata is read-only; NightCrate catalogs
  files in place.
- The calibration coverage screen (still pending). This version only keeps
  the matching views coherent for raw frames (see Scans).

## Anti-goals (a failure even if it works)

- A statistic or star measurement taken from interpolated pixels.
- A guessed value shown as fact: a time zone, a frame type or a filter
  that NightCrate inferred, without saying so.
- Colours swapped because a pattern, offset or row order was misread.
- A mosaic shown as grey when NightCrate knew its pattern.
- Any change to a user's capture files.

## Approaches (Fred picked B, 2026-11-17)

| | How | Trade-offs |
|---|---|---|
| A | Convert to colour as each file loads; everything downstream receives `(3,H,W)` | Fewest downstream changes. Triples memory (a 26 MP sub becomes about 600 MB as float64), and measures stars on interpolated pixels; the solver and quality checks would convert back to grey anyway |
| **B** | **Keep the mosaic and its pattern; each consumer asks for the form it needs** | **Statistics and measurements stay faithful to the recorded samples, and the cost of colour falls only where colour is shown. Each consumer must say which form it wants** |
| C | Merge each 2×2 block into one colour pixel at load | Cheap. Halves resolution everywhere, including 1:1 in the analyzer, and doesn't fit X-Trans's 6×6 pattern |

## Design

### 1. One loader

Consolidate every pixel read into `services/pixel_loader`, which already
raises domain errors and is worker-safe. The other loaders become callers
of it:
- the two older dispatchers (`api/images.py`, `api/aberration.py`),
  fixing the dropped PixInsight-project index;
- `project_images`, `image_preview` and the plate-solve reads.

The loader returns **one of three forms**:
- **mono** `(H,W)`;
- **colour** `(3,H,W)`, a finished or already-converted image;
- **mosaic**: `(H,W)` samples plus their colour pattern (the repeat size
  and each site's colour) and where the pattern came from (below).

Consumers ask for what they need:

| Request | Mono | Colour | Mosaic |
|---|---|---|---|
| display colour | as mono | as is | converted to colour (§2) |
| per-colour samples | one channel | three channels | each colour's real sites |
| measurement grey | as is | luminance (as today) | merged blocks (§3) |

The catalog thumbnail and frame-quality workers stay numpy-only
(`CLAUDE.md`).

### 2. Where the pattern comes from, in order

1. **Raw files:** from LibRaw (`rawpy` `raw_pattern`/`raw_colors_visible`
   over the visible area). This covers Bayer and X-Trans.
2. **FITS:**
   - `BAYERPAT` (written by N.I.N.A., ASIAIR and SharpCap), else MaxIm
     DL's `COLORTYP`;
   - shifted by `XBAYROFF`/`YBAYROFF`. An odd offset shifts the pattern by
     one column or row;
   - reconciled with `ROWORDER` and the order NightCrate reads rows in.
     Reading `TOP-DOWN` data bottom-up flips the pattern vertically
     (RGGB ↔ GBRG).
3. **XISF:** the `ColorFilterArray` element (pattern, width, height), then
   any FITS keywords kept in the file. XISF rows are top-down.
4. Otherwise the image is mono.

**No stored fallback from the equipment data** (Claude's call after the
builder check). A sensor's `bayer_pattern` has no defined row order, so
applying it can swap red and blue. Feeding it into stored results would
also force re-measuring whenever a folder's rig or a rig's camera changes.
Instead:
- the analyzer offers a **"Colour pattern" choice** for a one-plane image
  whose file names none, suggested from the rig's sensor;
- the choice is for that view only: never stored, never used for
  statistics in the catalog, measurements or thumbnails, which treat the
  image as mono.

The source is shown in the metadata tab, for example "Colour pattern: RGGB,
from the file's BAYERPAT".

**Must be verified, not assumed:** the `BAYERPAT`/`ROWORDER` combination
against real subs from N.I.N.A. and ASIAIR. Pure red, green and blue
targets, or a known star field colour, must come out in the right colour.
Fred has colour-camera subs in his own storage (read-only), and the builder records
which files were used.

### 3. The three forms in detail

- **Display colour:** NightCrate's own interpolation, the same for FITS,
  XISF and raw mosaics. It uses normalised convolution per colour: each
  colour's samples, spread by a small kernel, divided by the spread mask.
  That works for any repeating pattern, Bayer and X-Trans alike, with SciPy
  (already a dependency). No LibRaw processing, OpenCV or new library.
  - It is good enough for inspection; proper interpolation belongs in
    processing software.
  - The converted image then takes the existing colour path: the unlinked
    auto-stretch and a per-plane PNG.
- **Per-colour samples:** for each colour, only the sites under that
  filter. Bayer's two greens are combined as G; X-Trans has R, G and B.
  Statistics and the histogram use these.
- **Measurement grey:** merge each repeat block into one grey pixel, 2×2
  for Bayer and 3×3 for X-Trans (each 3×3 holds 2 R, 5 G and 2 B). This is
  what the native solver does today.
  - Star sizes (HFR, FWHM), positions and aberration results are reported
    in **sensor pixels**, multiplying by the block size, so they compare
    with mono cameras.
  - Frame quality, the aberration inspector and the native solver use
    this form.
  - **Stored quality results change meaning,** since colour frames were
    measured as grey mosaics. The migration clears the quality results of
    frames whose stored header records a colour pattern (`BAYERPAT`,
    `COLORTYP`, or an XISF colour filter array), back to "not analysed".
    Analyze measures them again on request, as `development-decisions.md`
    requires when the measurement changes. Nothing else is touched.

### 4. Image analyzer

- **Display:** colour subs show in colour, with the unlinked per-channel
  auto-stretch finished colour images already get. No white balance is
  applied: the auto-stretch neutralises the green cast of unbalanced data,
  and the numbers stay as recorded.
- **Statistics and histogram:** R, G, B from the real samples (§3), in the
  file's own units (ADU). For raw files that includes the black-level
  pedestal, as FITS includes its offset. Black and white levels show in
  the metadata tab.
- **Pixel inspector:** shows the file's recorded value at the pixel under
  the cursor, and for a mosaic, which colour filter that site sits under.
  It uses the existing `/pixel` endpoint rather than the stretched PNG.
  The displayed RGB may be shown beside it, labelled.
- **Smooth when zoomed out,** for every image: the browser's downscaling
  (`FitsImage.tsx:608`, `imageRendering: auto`) aliases fine patterns. The
  analyzer serves a smoothly reduced image below 100 %, or the equivalent;
  the builder chooses the mechanism.
- **The "Header" tab becomes "Metadata":**
  - columns **Name**, **Value** and **Description**. FITS comments go in
    Description, EXIF tags in Name;
  - for raw files, groups in this order:
    - capture: exposure, ISO, capture time and its offset, sub-seconds;
    - camera and lens, with serials;
    - colour data: pattern and its source, black and white levels, the
      visible area;
    - all EXIF tags;
    - maker notes;
  - FITS, XISF, PixInsight-project and PNG/JPEG/TIFF metadata show as
    today, under the new names;
  - editing stays FITS-only. Raw metadata is read-only, and the tab says
    so.
- **Orientation:** raw frames show as the sensor recorded them. The
  camera's orientation flag is listed in the metadata, not applied, as
  Siril and DeepSkyStacker do; rotation would break pixel positions for
  plate solving.

### 5. Thumbnails and the gallery

- **Project file thumbnails, catalog thumbnails and plate-solve previews**
  of a mosaic use **colour superpixels**: one RGB pixel per repeat block
  from its real samples, then reduced. No interpolation, and no
  single-colour sampling.
- **Project images** (gallery, Home framings) take the colour path when the
  file is a mosaic with a pattern it records, for example an OSC master
  flat or a sub added as a project image. Their existing renditions are
  regenerated: a render version goes into their cache key. Raw files
  aren't project images (non-goal).

### 6. Camera raw files

- **Reading:**
  - `rawpy` for the visible-area samples, the pattern, black levels
    (per channel), the white level and the visible area;
  - `exiv2` for EXIF and maker notes: `DateTimeOriginal` with
    `OffsetTimeOriginal` and `SubSecTimeOriginal`, `ExposureTime`, ISO,
    make, model, body serial, lens, focal length, orientation, and maker
    temperatures (Canon `CameraTemperature`, Olympus `SensorTemperature`,
    Pentax `TempInfo`, Sony `CameraTemperature`).
  - Both read file paths and in-memory archive entries.
- **Formats:**
  - the extensions for CR2, CR3, NEF, NRW, ARW, RAF, ORF, RW2, PEF and DNG
    join the extension lists (§9);
  - a DNG without a colour pattern (LinearRaw) is a colour image;
  - files LibRaw can't decode (Canon sRAW/mRAW, Nikon HE, unsupported
    bodies) are listed as files a scan couldn't catalog (v0.50.0's
    `uncataloged_file`), with the reason in plain words.
- **White level, not the integer type:** raw samples are 12- or 14-bit in
  16-bit containers. Saturation and any clipping logic use the file's
  white level, never 65535.
- **Astro traps,** shown as facts in the metadata, never hidden:
  - lossy compression (Nikon `NEFCompression`, Sony `SonyRawFileType`);
  - Sony's star-eater filtering. No reliable per-frame flag exists, so
    only the model, firmware and exposure are shown, and no warning is
    invented.

### 7. Scans

- **Frame type:**
  - FITS and XISF keep `IMAGETYP` and today's rules.
  - Raw files have no frame type. Scans guess it from names, nearest first,
    case-insensitive. The names that count are:
    - the file name;
    - the folders between it and the bound folder (and inside an archive);
    - the bound folder's own name.

    Folders above the bound folder never count, so a parent called "Dark
    Sky Site 2025" can't turn lights into darks. A folder name counts only
    when, ignoring numbers, units, dates and separators, it is nothing but
    the keyword: "Darks 300s -10C", "darks_2026-03-14" and "Bias" count;
    "Dark Sky Site" doesn't. File names count by tokens split on
    separators. The keywords:
    - light or lights;
    - dark or darks;
    - flat or flats;
    - darkflat, darkflats, flatdark or flatdarks;
    - bias or offset.

    N.I.N.A.'s `LIGHT_`/`DARK_` file-name prefixes count. No match leaves
    `unknown`.
  - A guess is `frame_type_source = 'auto'`, which corrections already
    override, and the frames table shows it as guessed from names.
- **Capture time:** `DateTimeOriginal` with `OffsetTimeOriginal` gives
  UTC. Failing that, a time zone the camera recorded in its maker notes
  (Canon `TimeInfo`, Nikon `WorldTime`) is the file's own too, and the
  metadata tab names the source. When a file has neither (many cameras, and all older ones), the
  time is read in the **project location's time zone** and marked as
  estimated. With no project location, it's the computer's time zone,
  also marked. Observing nights follow from that time.
- **Typed fields** (a forward migration):
  - **ISO** gets its own column; raw frames don't set `gain`. Capture
    batches gain an ISO column, and derivation groups by ISO wherever it
    groups by gain.
  - **Camera (body) temperature** gets its own column. `sensor_temp_c` is
    set only from a maker note that names the sensor (Olympus, some Pentax
    models).
  - **Exposure** from `ExposureTime`.
  - **Raw metadata** is kept for re-parsing, as FITS headers are, in a
    column whose name doesn't say FITS. `fits_header_json` keeps FITS and
    XISF.
- **Calibration matching:** the calibration views match raw frames by
  ISO and exposure only. Temperatures are shown but not matched: uncooled
  camera readings drift by several degrees, and today's ±1 °C rule (for
  cooled cameras' set point) would match almost no DSLR darks. No screen
  uses the views yet (Claude's call).
- **Speed:** scans read raw metadata only (`exiv2`, plus whatever `rawpy`
  needs for dimensions and pattern without decoding pixels, if possible).
  The builder measures a scan of the sample folder and reports it.

### 8. Batch correction of the filter

- The Files tab's existing selection and "Correct N frames" dialog gain
  the **filter**, for every format. Header-derived filters on FITS and XISF
  can be corrected too.
- **A filter correction survives rescans,** like frame type: a source flag
  (`auto`/`user`) beside the filter, with "reset to the file's value". The
  derived filter is never frozen behind a type guard
  (`docs/development-decisions.md`, frame classification).
- **Stored as text** in `filter_name_hint`, with the source flag (Claude's
  call). A frame keeps no link to a filter record, as since v0.41.1 removed
  per-frame equipment links. Batches keep today's name-based lookup.
- **Values:** the existing bandpass vocabulary (`line_names`) and filter
  display names. Suggestions come first from the filters in the rig's
  wheel or its single filter.
- **The rig's single filter as the default:** when a raw frame's rig has a
  single fixed filter (`single_filter_id`, the DSLR clip-in case) and the
  file names no filter, the frame takes that filter as `auto`. That comes
  from the user's own rig definition, not a guess.
- Selecting a folder's frames (an existing selection gesture, or a new
  "select all in this folder") makes a whole night's correction one
  action.

### 9. Extensions and file browsers

The raw extensions are registered once and reused:
- `path_resolver` (a `RAW_EXTENSIONS` set joining `ALL_EXTENSIONS`, and
  the `file_type` ladders);
- `ingest_classify._HEADER_EXTENSIONS`;
- `ingest_scanner.parse_image_file`;
- the frontend's file-type checks (`frontend/src/api/images.ts:110`) and
  the file browser's default filter.

`api/projects.py`'s finished-image list stays without raw (non-goal).

### 10. Dependencies, licences and packaging

- **`rawpy` 0.28 (MIT)** with LibRaw under its **LGPL-2.1** option, from
  the official wheels, which exclude the GPL demosaic packs. A test asserts
  `rawpy.flags` reports no demosaic pack, and records
  `rawpy.libraw_version`. No source builds with the packs (`CLAUDE.md`).
- **`exiv2` 2.16 (GPLv3)**, compatible with NightCrate's
  GPL-3.0-or-later. Exiv2 and its bundled libraries are inventoried.
- **README acknowledgments** for both, and for LibRaw and Exiv2.
- **The packaging notices** (`packaging/notices.py`) inventory every
  native file both wheels ship. LGPL: LibRaw stays a separate shared
  library, with its licence and a source pointer in the distribution.
- **The minimum macOS becomes 14.0:**
  - Tauri's `minimumSystemVersion`;
  - the README's system requirements;
  - the updater's handling of older systems: a macOS 14 user offered
    v0.55.0 must be told it needs macOS 14, not given an app that won't
    start. The builder checks what the current update flow does.
- **Source runs where the libraries can't install** (Fred, 2026-11-17):
  - Intel Macs, and Apple Silicon Macs before macOS 14 for `exiv2`, keep
    running NightCrate from source, with raw files off;
  - `rawpy` and `exiv2` get platform markers in `pyproject.toml`
    (`platform_machine == 'arm64'` on macOS, and for `exiv2` a Darwin
    release marker for macOS 14, if uv honours it; otherwise an optional
    group that `make install` adds where supported). The builder verifies
    `uv sync --python-platform x86_64-apple-darwin --dry-run` and an
    arm64 resolution, as `CLAUDE.md` requires for mlx;
  - **a capability probe,** like the GPU's, catches missing and unusable
    installs. Where it fails, scans list raw files as not cataloged with
    the reason "Raw files can't be read on this computer", and the
    analyzer says the same. Colour FITS and XISF subs still work. Tests
    that need the libraries skip without them;
  - `CLAUDE.md`'s dependency rule and the README's source-run notes say
    so.
- **The frozen app** (cx_Freeze plus Tauri) must load both libraries on all
  three systems. CI's install self-test opens a generated DNG and reads
  its metadata.

### 11. Tests and checks

### 12. The project Plate Solve tab (Fred, at acceptance, 2026-11-17)

After a solve, the list of objects in the image had grown too long, and
main targets weren't distinct enough from the selection. Fred chose the
layout from three rendered mockups and refined it
(`.superpowers/mockups/v0.55.0/plate-solve.html?layout=c`, local).

- **Layout.** The header and facts strip stay. Below them:
  - **A side panel** on the left, about 220 px, headed "Filters" with Clear
    and a « button. Collapsed, it is a thin full-height strip; the whole
    strip reopens it and shows a count when filters are on.
  - **No focal length check** (removed 2026-11-18, Fred: "kinda useless -
    mainly because I'm going to be using processed images in there, and I
    almost always drizzle. Other users may or may not, or they could be
    binning their camera"). The estimate was removed from the API too.
  - **The image** on the right, with zoom and pan, and the legend under it.
  - **Two tables under the image:** "Other objects in the image" (wide, on
    the left) and "Main targets" (narrow, on the right).
  - **No page scroll.** The tab fills the window below the header. The
    tables take the space under the image and never show fewer than five
    rows; on a shorter window the image shrinks instead. The side panel
    scrolls on its own if it is taller than the space.
- **Marker and row states** (the project tab only; the Image Analyzer and
  the planner keep their colours):

  | State | Marker | Row |
  |---|---|---|
  | Other object | thin grey outline, grey label | plain |
  | Main target | blue `#4fb0ff`, 2.5 px, bold label | blue left edge |
  | Selected | yellow `#ffd400`, 2.5 px, bold label | yellow tint and edge |
  | Selected main target | blue 2.5 px with a touching 2 px yellow line outside it | yellow tint |

  Line widths are on-screen pixels at every zoom. No centre dot: it could
  hide a small object or a star. The legend shows all four states. The
  "Solved and saved" pill keeps its teal.
- **Selecting.** Clicking a marker or a row selects the object. Clicking a
  marker scrolls its table just enough to show its row; selecting a row
  brings its marker into view if it is outside the zoomed area. Rows never
  move.
- **What a click hits.** An outline's interior never catches clicks, or a
  large object (a dark nebula, a cluster) would hide every object inside
  it. The click target is the outline, with about 6 px of tolerance either
  side, and the label. An outline under 12 px across on screen also takes
  clicks on its interior, so tiny objects stay easy to hit. This is a bug
  in today's shared overlay (`fill="transparent"`), so the fix applies
  wherever `DsoAnnotationOverlay` is used, the Image Analyzer included.
- **Main targets.** Ticking an object's box moves it to the Main targets
  table, and unticking moves it back; double-clicking a marker toggles it
  too. Both use the existing main-target endpoint, so the change is saved
  at once. Main targets ignore every filter, in the table and on the image.
- **Tables.** Both sort by clicking a column header (again to reverse).
  Other objects: Object (name, other names below), Type, Catalogs, Size,
  Main; sorted by size, largest first. Main targets: Object (name, common
  name below), Type, Main.
- **Filters** apply to other objects, in the table and on the image:
  - **Catalogs:** a checklist of the catalogs the image's objects belong
    to, with counts. None ticked shows everything; several ticked show
    objects in any of them. Membership is the DSO Catalog page's
    (designations plus catalog groups), so the API now returns each
    object's catalog codes.
  - **Types:** a checklist of the object types present, with counts.
  - **Minimum size:** a slider on a logarithmic scale from "Any size" to
    the largest object; objects with no recorded size hide once a minimum
    is set.
  - Each list's counts reflect the other filters. "Clear" resets all
    three. Filters, the panel's state and the zoom aren't saved.
- **Zoom and pan.** The mouse wheel zooms around the pointer; dragging
  pans (a drag never selects); +, −, Fit and 1:1 buttons; a readout gives
  the zoom as a percentage of the image's full size. Collapsing the panel
  or resizing the window keeps the zoom and the point at the centre.
  100% (1:1) is one screen pixel per pixel of the solved image; zoom
  continues to 8×. The saved image is at most 4,000 px across, so past
  that the view enlarges it.
