# v0.54.1 — Faster test runs, grid filters that survive page buttons, and picker fixes

v0.54.0's PR (#33) ran the backend test suite on GitHub's machines for the
first time, and no job finished within GitHub's 60-minute limit. Fred
merged it anyway (the checks weren't required). Then, using the installed
app, he found an Equipment page crash and two problems with the project
editor's "Processed with" picker. This version fixes the test runs, sets up
a merge gate, changes when PRs are opened, and fixes those bugs and the
others a sweep found. Fred approved the plan for it on 2026-11-15.

## Fred's decisions (2026-11-15)

- **Version v0.54.1.** LAN mode stays v0.55.0.
- **PR last:** "do not open the PR until the very last moment when
  everything is ready - this way we can avoid needlessly running CI jobs
  while we are still in the dev process." The workflow documents change
  to match.
- **Merge gate:** "no merging unless the CI checks pass (with admin
  override of course)." The checks therefore **stop running after a
  merge**, because a required run already tested the merged result.
- **A throwaway `ci/v0.54.1` branch may run the checks during this
  version** (one or two runs), to measure the fix before the PR exists.
- **Codex's second opinion** on the test speed-up.
- **Fix the Equipment crash and check every grid** where a filter set in
  the grid meets a page-level button that changes the data.
- **The "Processed with" list** must be readable and list owned software
  first, "the way things are done when building a rig".
- **Info becomes the project editor's second tab,** right after Overview
  (added during planning).
- **Remove the per-folder Target completely** (added during planning). "I
  don't see the utility for it, not even later." Fred chose full removal,
  including the stored columns, over hiding it.
- **Fix the gallery card's expand button showing through a flipped card**
  (added during planning).
- **Show the files being added** (added during planning): "adding files to
  a project can take quite a bit of time - just the Scanning spinner is not
  sufficient … a scrolling display that shows the current and previous 9
  files that were processed".

## Evidence

**Locally** (Fred's Mac, the v0.54.0 tree):
- 62 min serially; 13 min on 16 workers (4,280 passed, 4 skipped);
- 4,218 of the 4,284 tests take over 1 s;
- imitating GitHub's machines (empty HOME, no terminal input, 3 workers)
  ran normally.

**PR #33's job logs** (each job cancelled at 60 min):

| | Collection | Tests |
|---|---|---|
| Ubuntu, 2 workers | 20 s | about 72 tests per 50 s; would need about 70 min |
| Windows, 2 workers | 51 s | 72 tests per about 21 min, twice running; about 17 s per test per worker |
| macOS, 3 workers | 43 min | no batch of 72 in the remaining 15 min |

**Causes found:**
- **The autouse `_test_db` fixture** (`backend/tests/conftest.py:103-205`)
  rebuilds a full database before every test:
  - 5 hand-made tables;
  - about 628 SQL statements from migrations 0005 onward, mostly
    autocommitted, each with its own journal file and syncs;
  - yoyo parses all 73 migration files and writes 74 log rows;
  - the seed data loads from 30 CSVs.

  The finished database is about 1.8 MB, one file with no journal left
  beside it. About 200 other tests build their own full databases on top
  of that.
- **yoyo calls `socket.getfqdn()` for every log row** (yoyo
  `backends/base.py:584`). On a Mac whose hostname doesn't resolve, that
  can stall for seconds per call. GitHub has an open report of broken
  hostname lookup on its macOS runners (actions/runner-images#8649). This
  is the leading suspect for macOS but is **not yet confirmed on a
  runner**.
- **A second macOS suspect:** mlx running on the GPU in a VM without Metal
  Performance Shaders. `core/compute.py:29-44` falls back when importing mlx
  raises any exception. A failure or hang during later GPU work, or a
  process-level abort, isn't caught (corrected after Codex's review).
- **Tests that can't pass in CI as written:**
  - `test_planner_api.py:894-924` runs Vite, but CI runs the backend tests
    before `npm ci`.
  - On Windows, `_sleeping_astap` (`test_plate_solve.py:886`) is an
    extensionless script.
  - On Windows, `test_serve.py:370` cleans up busy workers on POSIX only.
- **The grids.** Of the app's four `DataGrid`s, checked against the MUI X
  8.28.1 source:
  - When columns change, MUI X drops filter and sort items whose column has
    gone. It never re-checks an item's operator against a column whose
    *type* changed, and an unknown operator throws
    (`gridFilterUtils.js:108`).
  - No route has an error boundary, so that throw replaces the whole app
    with React Router's "Unexpected Application Error!".

## Requirements

### 1. PR last

- Publish becomes:
  1. commit;
  2. review the committed branch diff locally;
  3. Fred chooses which findings to fix, and the fixes are a follow-up
     commit;
  4. push;
  5. open the PR as the very last step.
- No PR exists while a version is in development. Once one is open,
  pushes are avoided, because each one reruns every check.
- A version that changes CI or the test setup is measured first on a
  throwaway `ci/<version>` branch, with Fred's authorization.
- Updated:
  - `.claude/skills/finalize-session/SKILL.md`;
  - `docs/agent-collaboration.md` §2 row 10, which still says "commit,
    tag, push, PR" although tags moved to `release.yml` in v0.54.0. Fred
    approved the change; the document's own rule asks Claude to consult
    Codex, which happens in this version's plan review;
  - Claude's memory.

### 2. CI triggers and the merge gate

`checks.yml`:
- runs on `pull_request`, on `workflow_dispatch`, and on pushes to `ci/**`
  (throwaway measurement branches); no longer on pushes to `main`;
- one run per ref at a time, and a newer push cancels the older run;
- installs the frontend before the backend tests, so tests that need
  `frontend/node_modules` can run;
- gives pytest `-o faulthandler_timeout=600` (a hung test prints every
  thread's stack) and `--durations=20`;
- sets the worker count and `timeout-minutes` from measured runs.

**Merge gate** (branch protection on `main`, applied once the `ci/` run
passes):
- required checks: `checks (macos-15)`, `checks (ubuntu-22.04)`,
  `checks (windows-2022)`;
- branches must be up to date before merging, so what merges is what was
  tested;
- administrators are exempt, which is Fred's override;
- the existing protection stays: no force-push, no deletion.

Windows becomes required, and loses `continue-on-error`, once a full run
passes. In v0.54.0 it was "informational in this version" because the suite
had never run there. Windows test failures found on the way are fixed in
this version.

### 3. Faster tests

- **A template database per test worker.** It is built once, with today's
  recipe, under pytest's temporary folders and with `APP_DIR` redirected,
  so nothing touches the real app-data folder. Each test gets a byte
  copy at `tmp_path/"test.db"`: a copy, never a hard link, because
  `initialize_workspace` refuses hard-linked files.
- **The per-test fixture** keeps today's four monkeypatches (`_db_path`,
  `_workspace_problem`, `APP_DIR`, `CONFIG_PATH`) and becomes synchronous.
- **The template keeps yoyo's tables** (`test_migration_0064.py` reads
  them). Building it asserts that no `-journal` or `-wal` file is left
  beside it.
- **yoyo's hostname lookup is replaced in tests only,** on yoyo's own
  module reference, so the `socket` module is untouched.
- **The suite passes on Windows.**
- **The same tests pass and skip as before:** 4,280 passed and 4 skipped
  on Fred's Mac, unless a Windows fix adds tests.
- **The first `ci/` run carries a temporary diagnostic step,** removed
  before the PR:
  - the time of one `getfqdn` call;
  - import times during collection;
  - an mlx one-liner under a time limit.

  If mlx misbehaves on the runner, CI runs the numpy path instead (the
  mechanism is chosen in the implementation plan); local runs on Fred's
  Mac keep covering mlx.
- **Production keeps yoyo's lookups,** 74 on a first-run workspace. If the
  runner confirms multi-second lookups, that becomes a separate question
  for Fred, not a change here.

### 4. Grids

- **Equipment lists** (`EquipmentList.tsx`, behind 12 lists). A dropdown
  filter column (manufacturer, plus each list's `dropdownFilterFields`) is
  always a dropdown, whatever rows are loaded:
  - its options come from the rows, an empty list when there are none;
  - each value keeps its type, so numbers stay numbers.

  This removes every crash path the sweep found:
  - Owned or Show Retired switching to a list not loaded yet;
  - a list that is really empty, such as nothing owned, the last row
    unstarred, or the last row retired;
  - a field with no values in the new list;
  - a filter set while the list is empty, before rows arrive.

  It also fixes the filter-wheel **Positions** filter, which never matched
  because its values are numbers and its options were strings.
- **FITS header edits belong to one file.** Switching to another file or
  HDU starts the header table afresh, so unsaved edits can't show on, or be
  saved into, a different file. Pending edits are discarded on a switch,
  as Discard does (Claude's call).
- **DSO catalog:** no column-menu filters. The page's own search, catalog,
  type, constellation and distance filters work on the server; the column
  filters only ever saw one page (Claude's call).
- **A page crash stays inside the app.** An error element on the routes
  shows what went wrong and a Reload button, inside the app shell
  (Claude's proposal, approved with the plan). The installed app has no
  address bar or obvious way to reload.
- **Equipment lists reach every row** (Fred, 2026-11-15: "I can scroll all
  the way down and it stops on QHY cameras - I cannot get to the ZWO
  cameras"). MUI X Community shows at most 100 rows per page, and
  `EquipmentList` hides the grid's footer (`hideFooter`). So rows after the
  first 100 in manufacturer order can't be reached. The seed has 247
  cameras, 117 telescopes and 108 filters. Fix:
  - the footer shows its page controls: 25, 50 or 100 rows per page,
    100 by default; the selected-row count stays hidden;
  - opening a list at an item (`?select=ID`) goes to that item's page
    before scrolling to it.
- **Lookup tables:** no change; their column types are fixed.

### 5. "Processed with"

- **The list is readable.** The "+ Add software" field is 142 px wide, and
  MUI sizes the list to the field. The list gets its own width
  (`max-content`, between 280 and 420 px), opening from the field's left
  edge. Names and manufacturers don't wrap.
- **Owned items come first, in every equipment and software picker.** The
  rig builder's hardware pickers already show a "My Equipment" group of
  owned items above the manufacturer groups (`withMineGroup`,
  `components/rigs/mineGroup.ts`); owned items also stay in their own
  group. Missing today:
  - "Processed with": gets a **"My Software"** group above the
    categories, which keep their order (Processing first);
  - the rig builder's software picker gets the same "My Software" group;
  - every picker in `RigPartsForm.tsx` (the project's rig change and
    Correct setup dialogs) gets "My Equipment", or "My Software" for
    software. Telescope configurations inherit their telescope's
    ownership, which `RigPartsForm` drops today;
  - the session form's filter picker keeps "My Rig" first (the filters in
    the project's rigs), then "My Equipment" (owned filters not in those
    rigs), then the bandpasses, then manufacturers.
- **Retired items kept for an existing selection** form one "Retired"
  group at the end of the list, as hardware does today. Software's
  category order must not split them into several "Retired" groups.

### 7. Remove the per-folder Target

Since v0.41.3, a source folder could declare its target, and ingest
stamped it onto the folder's light frames (migration 0056). It is shown
only in the frames table's Target column (projects with several targets)
and edited only in the frame corrections dialog.
`session_summary.distinct_targets` counts it, but nothing reads that.
No totals, batches, verdict, plate solve, sky chart or gallery use it.

- **Removed from the app:**
  - the add-folder and folder-row Target fields;
  - the frames table's Target column;
  - the target part of frame corrections;
  - ingest's target stamping;
  - the API fields.
- **Removed from the database** by forward migration 0074:
  - `project_source_folder.project_target_id` and its index;
  - `sub_frame.project_target_id`, `sub_frame.project_target_source` and
    their index;
  - `session_summary.distinct_targets`.

  Both tables are rebuilt with the established pattern (foreign keys off,
  `legacy_alter_table = ON`, as in 0073). Everything else stays identical:
  every other column and constraint, indexes, triggers, the other views,
  the autoincrement counters, and the rows of child tables that reference
  these two.
- **Project targets themselves are unchanged:** the project's list of
  targets, used by the planner, sky chart, gallery and plate solving.
- **Verified** on a copy of Fred's database at migration 0073 and on a
  fresh database:
  - row counts unchanged;
  - `PRAGMA integrity_check` returns `ok`;
  - `PRAGMA foreign_key_check` is empty.
- Existing target labels are discarded; nothing else uses them.

### 8. Gallery cards: nothing shows through when flipped

The gallery's expand button sits on the card's front face with its own
`z-index`. WebKit, the engine of the installed app on macOS, doesn't
reliably hide such children of a `backface-visibility: hidden` face. So
the button appears mirrored over the back's text.

The fix is in the shared flip component (`components/common/FlipTile.tsx`),
which the Messier tiles also use, with the same button and arrows. A face
that ends up turned away is hidden (`visibility: hidden`) when the rotation
actually ends; the face turning toward you is visible from the start of
the turn. Keyboard focus therefore moves to the newly shown face's button
exactly as today. A flip reversed mid-turn shows the face coming back at
once, and with reduced motion everything happens at once. During the
400 ms turn itself, backface handling still applies as today.

Descendants mustn't override the hiding: the Messier image, which sets
`visibility: visible` once loaded (`MessierSkyImage.tsx:213`), inherits
instead.

### 9. Showing the files being added

Today a scan is one request that returns only when every folder is done
(`api/ingest.py:start_ingest`), and the Files tab shows a spinner on the
folder's button. Instead:

- **While a scan runs**, whether adding a folder, re-scanning one or
  scanning all of them, the project's Files tab shows a progress panel in
  place of the frames table. It shows:
  - the folder being scanned;
  - the stage: listing files, reading file headers, saving, or grouping
    into sessions;
  - while headers are read, "N of M files";
  - the **10 most recent files, newest at the bottom**, each by its path
    inside the folder (for example `Lights/2024-10-01/M31_L_001.fits`).

  A file whose header couldn't be read says so in words, not only by
  colour. When the scan finishes, the table returns, with today's summary
  message.
- **The panel follows the scan, not the page.**
  - If the Files tab is opened, or reopened, while a scan of this project
    is running, or a scan is started from another window, it shows the
    panel. The scan buttons are disabled until the scan ends.
  - The finished scan's result is kept for a few minutes, so the table
    refreshes and the summary shows once, even for a scan that started and
    ended between two checks.
- **Two scans can't overlap.** Starting a scan while one runs is refused,
  as intended today; a race that let a second request queue behind the
  first is closed.
- **The backend keeps a small in-memory record of the running scan,** like
  `services/catalog_progress.py`: the folder, the stage, the counts and the
  last 10 files. A read-only endpoint returns it; the page polls about
  twice a second while a scan runs.
- **Listing the folder no longer blocks the backend,** so the panel shows
  "Listing files" on a slow volume instead of hanging.
- **Each file reports as soon as its header has been read.** When headers
  are read without worker processes ("maximum worker cores" set to 1, or a
  single file), they are read on a background thread, one file at a time,
  so the backend keeps answering the page.
- **What is parsed, saved and grouped doesn't change,** nor the scan's
  result and summary.

Claude's calls:
- the count line;
- newest at the bottom, like a log;
- the panel replacing the table during the scan, since the table is stale
  until the scan ends.

### 10. Home pictures use the project's framing

Fred (2026-11-15): "in the home view, I think the project images need to be
cropped from the large thumbnail definition - not the entire original
image - that's because in some cases the large image auto crop in this view
fails to catch the actual target(s) - for example the Leo Triplet".

Today:
- **"Latest picture"** loads the whole picture into a box about 660×340 px
  (`components/home/LatestAndYear.tsx:53`, `objectFit: cover`). The
  browser keeps the centre band, which can miss an off-centre target.
- **The recent-project cards** ask for the *medium* framing. Without one,
  the server returns the whole main image.

Every saved framing is 4:3 (`docs/development-decisions.md`, "Crops").
Home uses one whenever it can:
- **Recent projects:** the project's large framing, else its medium,
  else its small, else the whole main image, as today.
- **Latest picture:** a framing **of that picture**, in the same order
  (large, medium, small). A framing frames the picture it names, or the
  main image when it follows the main. Otherwise the whole picture, as
  today.
- The box sizes stay as approved for v0.53.0. A 4:3 framing still fills
  them, cropped top and bottom, around the framed target instead of the
  whole image's centre.
- The framing order after "large" is Claude's call: any saved framing
  beats the whole image.
