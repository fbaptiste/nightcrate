# v0.54.0 — Installers and updates

**Approved by Fred on 2026-11-14.**

Today NightCrate runs only from a development checkout (`make dev`: uv,
Node and Vite). A Windows user asked for an installer (issue #16), and
people who run the development servers inherit their security advisories.
This version makes NightCrate installable on macOS, Windows and Linux. The
installed app tells you when a new version or a catalog update exists,
and asks before installing anything.

Fred shaped the work on 2026-11-14. A throwaway packaging test the same day
(PLAN.md, "Packaging test results") showed that the approach works on all
three systems and found the defects listed in section 10. The approved
mockup is `.superpowers/mockups/v0.54.0/updates.html` (ignored). Where the
mockup and this text differ, the text wins.

## Fred's decisions (2026-11-14)

- **Two versions.** v0.54.0: installers, updates, and app and catalog
  notices; the installed app is local-only. v0.55.0: LAN mode. `make
  dev-lan` stays for development meanwhile.
- **No code signing at first.** The README carries walkthroughs for the
  one-time step: "Open Anyway" in macOS System Settings, and "More info →

- **Targets:** macOS on Apple Silicon, Windows x64 and Linux x64.

- **Catalog notices: real versions plus age reminders.** OpenNGC reports a

  numbers. Once they are six months old, they get a "last downloaded …
  ago" reminder, never worded as an update. The VizieR catalogs get no
  notice; NightCrate's own catalog data arrives with app updates. Catalog
  work never starts by itself: the notice links to the Catalogs section.
- **Releases:** merging stays as it is. When Fred says "release", GitHub
  Actions builds the three installers into a draft release; Fred tries

- **Notices appear in the sidebar,** as a pill under the workspace name. A
  bell and a banner were rejected.
- **Test builds before acceptance:** Claude may push temporary commits to a

  deletes it (section 10).
- **LGPL bundling is approved,** and each release carries the exact sources
  of the bundled LGPL libraries (section 11).
- **macOS will ask again for folder and drive access after each unsigned
  update.** Accepted and documented; signing stays out (section 2).

  downgrades, and a plan for losing the signing key;

- installers carry their licence obligations;
- ASTAP stays user-installed.

## Goals

- A new user downloads one file, opens it, and has NightCrate running,
  with no Python, Node or terminal.
- An existing user keeps their workspaces: the installed app uses the same
  app-data folder as a development checkout.
- The app says when a newer version exists and installs it only when asked.
  An upgrade can never cost anyone their records.
- Catalog news shows in the same place, and only links to where the user
  acts.
- Each release is built by GitHub from merged code, tested by machine, and
  then tried by Fred before anyone can receive it.

## Non-goals

- LAN mode, other devices, certificates, pairing (v0.55.0).
- Code signing and notarization; Intel Macs; Linux packages other than
  AppImage; CUDA in the installers.
- Automatic installs, background downloads or a backend scheduler.
- Catalog downloads started by a notice.
- Telemetry of any kind.

## 1. What a user sees

**Installing:**
- **macOS:** a `.dmg`; drag NightCrate to Applications. The first launch
  needs "Open Anyway".
- **Windows:** a per-user `.exe` installer with no administrator prompt. The
  first launch needs "More info → Run anyway".
- **Linux:** an AppImage; mark it executable and run it.

**Opening:**
- A small window says "Starting NightCrate…" while the backend starts, then
  the app window opens.
- A new user sees the existing Welcome card, which gains the
  automatic-check box (section 7).
- A user from a development checkout sees their workspace, plus the one-time
  check question.

**When something is new:** an amber pill appears in the sidebar, and
clicking it lists the notices (section 5).

**Installing an update:** Install and restart → progress → NightCrate opens
again, backs up and upgrades the workspace, and says "Updated to 0.55.0"
(section 6).

## 2. The installed app

The shell is Tauri 2 (the packaging test used tauri 2.12.5 and its updater
plugin 2.14.1). It uses the operating system's web view: WebKit on macOS,
WebView2 on Windows and WebKitGTK on Linux. The shell does only what a
browser can't do: start and stop the backend, show the window, and install
updates.

- **Identifier:** `io.github.fbaptiste.nightcrate`. It is permanent: the web
  view's storage and the updater depend on it.
- **Icon:** NightCrate has none. The only icon in the repository is
  `frontend/public/favicon.svg`, Vite's default lightning bolt. Claude
  designs two or three options as a mockup, and Fred picks one before the
  release. The chosen icon also replaces the favicon.
- **Window:** titled "NightCrate", opening at 1400×900 (minimum 1024×700),
  and remembering its size and position. Closing the window quits
  NightCrate on every system, which stops the backend.
- **Loading window:** a small local page with "NightCrate" and one status
  line. It follows the system's light or dark mode, using the app's page
  colours (`#f5f4f2` with `#2c2c2c` text in light mode, `#1a1c20` with
  `#e2e0dd` in dark). It shows the backend's startup steps as they arrive
  ("Starting NightCrate…", "Backing up My NightCrate…", "Upgrading My
  NightCrate…"). If the backend exits before it is ready, the window
  instead says "NightCrate couldn't start", shows the last 20 log lines,
  and offers "Open the log folder".
- **One NightCrate at a time.** Opening NightCrate again focuses the
  running window. If a development backend holds the app-data folder
  (section 3), the loading window says: "NightCrate is already running from
  source code on this computer. Stop it, then open NightCrate again."
- **Links that leave NightCrate open in the default browser.** That covers
  every `target="_blank"` link and `window.open` call to another site (14
  files today). One exception: a project image's "open in its own window"
  (`pages/ProjectDetailPage.tsx`) opens a separate NightCrate window that
  fits the image, as it does in a browser today. It loads a small viewer
  page from the backend; the old way, writing a document into a blank
  window, can't work in the app (plan review, 2026-11-15).
- **Downloads work.** The PHD2 Analyzer's export (a `createObjectURL`
  download, the app's only one) opens the system Save dialog in the
  Downloads folder with the file's name filled in; cancelling saves
  nothing, and a message says where the file went. Fred, 2026-11-15: "I
  should be given the choice to change the download location". The shell
  remembers the chosen path, because macOS never reports it.
- **In-page drag and drop keeps working:** nav reordering and gallery
  reordering. (Horizon files are imported through a button; there has never
  been a drop target for them. Corrected 2026-11-15 by the independent
  review.) The shell must not intercept
  drops; on Windows, Tauri does by default.
- **Keyboard:** copy, paste and select-all work in text fields on macOS,
  which needs the standard Edit menu. Zoom shortcuts work (Cmd/Ctrl
  +/−/0).
- **Permissions:** the web page may call only the shell's update commands
  (section 6) and set its own zoom level, and nothing else of Tauri's. On
  macOS and Linux, Tauri's zoom shortcuts are a script in the page that
  asks the shell to zoom. The page loads from the
  backend's local address, so the shell's permission list allows that
  address and no other.
- **macOS privacy permissions after updates.** Without an Apple developer
  certificate, the app's signature identity is its code hash. The
  packaging test's app reports `designated => cdhash H"…"` with no team
  ID, so every update is a different app to macOS. macOS will very likely
  ask again for access to Documents, Desktop, and external and network
  drives after each update. **Fred (2026-11-14): accept it and document
  it;** signing stays out. The README's macOS section explains the repeated
  prompts. The Mac check confirms the behaviour, and its result is kept
  as evidence for revisiting signing.
- **Updater:** configured with the public key (committed) and the manifest
  `https://github.com/fbaptiste/nightcrate/releases/latest/download/latest.json`.
  On Windows it installs in passive mode, which shows progress without
  asking questions.
- **What's inside:**
  - mlx on macOS, but no CuPy anywhere: CuPy isn't a declared dependency, so
    Windows and Linux use numpy, as a default install from source does today;
  - the GPL text;
  - the third-party notices (section 11);
  - the sky chart's data notices.

## 3. The production backend

A production entrypoint runs the same FastAPI app without Vite. The shell
uses it, and so does `make start` from source (section 9). `make dev` is
unchanged.

- **Startup:** calls `multiprocessing.freeze_support()` first. Runs uvicorn
  without reload, bound to `127.0.0.1` only; `NIGHTCRATE_LAN` is ignored
  here.
- **Port:** 8765 by default, so the web page's origin stays the same between
  launches. The frontend keeps some preferences in `localStorage`, which
  belongs to the origin. If 8765 is taken, the backend tries 8766–8775 and
  reports the port it got.
- **Serving the frontend:** the built frontend (`frontend/dist`) is served
  under `/`, with `/assets` as static files. Any unknown path that isn't
  under `/api`, `/docs` or `/openapi.json` returns `index.html`, so deep
  links work.
- **Host check:** requests whose `Host` isn't exactly `127.0.0.1:<port>` or
  `localhost:<port>`, port included, are rejected. Starlette's
  `TrustedHostMiddleware` ignores the port, so the check is NightCrate's
  own. This blocks DNS-rebinding pages from
  reading the API. No CORS origins are allowed in production; the page is
  same-origin.
- **Readiness:** once startup (workspace activation included) has finished,
  the backend prints one machine-readable line with its port. It also
  prints a line for each startup step the loading window shows. The shell
  waits for the ready line.
- **Exits when the shell goes away.** The shell holds the backend's stdin
  open. When stdin closes (normal quit, crash or force-quit of the shell),
  the backend shuts down gracefully, cancelling requests still running
  after 10 s. It exits by itself after 15 s at the latest, terminating
  its worker processes explicitly (a spawned worker outlives a parent
  that just exits), because after a force-quit no shell is left to kill
  it. On Windows the shell also holds the backend in a job object that
  kills it, and its workers, when the shell dies. This applies during startup too. The shell also kills it if it
  hasn't exited after 15 s. The test found that a killed shell left the
  backend running with the database open.
- **A heartbeat while starting.** Until it is ready, the backend prints a
  heartbeat line every 5 s, so a long backup of a large workspace isn't
  mistaken for a hang. The shell gives up after 60 s without any line
  (plan review, 2026-11-15).
- **One backend per app-data folder.** On startup, every backend (`make dev`
  included) takes an operating-system lock on a file in `APP_DIR`. The lock
  is released automatically if the process dies. A readable file next to it
  records the process ID, the kind ("installed" or "source"), the version
  and the port. A second backend that can't take the lock logs who holds
  it, and exits with a distinct code so the shell can show the message from
  section 2. Tests redirect `APP_DIR` (`tests/conftest.py`), so each test
  gets its own lock.
- **Version:** from package metadata (`importlib.metadata`), in source runs
  and frozen builds alike, not from the repository's `VERSION` file.
  `/api/health` reports it, along with `install_kind` ("installed" when the
  shell launched it, otherwise "source").
- **Logs:** the production entrypoint also writes rotating log files (5 ×
  5 MB) to the platform's log folder (`platformdirs` `user_log_dir`). Admin
  shows the folder. `NIGHTCRATE_LOG_LEVEL` still applies.
- **Startup work stays in the lifespan,** as today. Section 4 adds the
  checks before migrations.

## 4. Upgrading a workspace safely

Every workspace activation goes through one guarded path: at startup, from
the setup wizard, and from Admin's workspace list.

1. **Refuse a newer database.** The database is newer if yoyo's
   migration table lists migrations this app doesn't have. That table is
   read through a read-only SQLite connection: yoyo's own API creates or
   upgrades its tables when it opens a database (plan review, 2026-11-15).
   The workspace is then left untouched, and the user sees the "newer"
   screen. A migration table NightCrate can't read is refused the same way,
   as "unreadable". A small file
   in the workspace, `nightcrate-workspace.json`, records the version that
   last opened it, so the message can name that version. If the file is
   missing (workspaces from before v0.54.0, or a copied database), the
   message just says "a newer version".
2. **Back up** when migrations are pending, or when this app version hasn't
   opened the workspace before:
   - SQLite's backup API copies the database consistently into
     `<workspace>/backups/nightcrate-before-<version>-<YYYY-MM-DD-HHMMSS>.db`,
     written to a temporary name and then renamed. A backup never replaces
     an existing file: a clash gets a `-2`, `-3`… suffix;
   - the three most recent backups are kept, and nothing else in the folder
     is touched. The backup an unfinished upgrade depends on is never
     pruned;
   - before migrating, a marker file in `backups/` records which backup the
     upgrade depends on; it is removed once the upgrade succeeds. If
     NightCrate stops in the middle (a crash, power loss, or the shell
     killing it), the next start finds the marker and first restores that
     backup, which drops any half-applied migration and the migration
     tool's leftover lock. It then upgrades again from a clean copy, with
     no new backup. A restore that is itself interrupted is simply done
     again;
   - a normal crash of an older version can leave SQLite's own recovery
     files (a hot journal). SQLite recovers them first, as any open would,
     before the read-only check;
   - if the backup fails (disk full, permissions), nothing is migrated and
     the user is told why.
3. **Migrate, seed and reconcile catalogs,** as today.
4. **On a failed migration, put the backup back.** With every connection
   to the database closed, restore the file from the backup by an atomic
   replace, leaving no stale `-wal` or `-shm` files: some databases are in
   WAL mode (the seed loader's command line sets it). Then check that the
   restored file matches the backup. Only then does the user see the
   "upgrade failed" screen, which says the workspace is unchanged. If the
   restore itself fails, the workspace stays blocked with a "restore
   failed" screen giving the backup's path and how to put it back by hand,
   and the next start tries the restore again. Expected seed and
   catalog-loader failures (database, file and value errors) stay warnings,
   at startup and from Admin alike; anything else is a bug and stops the
   activation.
5. **Record success:** update `nightcrate-workspace.json` with this version.

While a workspace is refused, or its upgrade has failed, no request opens
its database: every path that opens the active database goes through the
guarded accessor, the star catalog's rig coverage included
(`api/star_catalog.py`, which opens it directly today). The workspace list, activating another workspace and creating
a new one still work. `/api/health` reports the problem: its kind, the
workspace name, the version that last opened it, the error and the backup
path. `App.tsx` shows the problem screen in place of the setup wizard. An
activation from Admin that fails leaves the previous workspace active and
shows the same content in a dialog.

**The screens (mockup section 3):** a 600 px card, centred as the Welcome
card is.
- **Upgrade failed:** titled "NightCrate 0.55.0 couldn't upgrade My
  NightCrate". A slate-bordered box says "Your workspace is unchanged.
  NightCrate put back the copy it made just before the upgrade." Below it,
  "What you can do":
  - download the previous version (named when known; the link goes to that
    release on GitHub, otherwise to the releases list);
  - report it on GitHub;
  - open another workspace.

  "Details" opens the error, the workspace and the backup path.
- **Newer database:** "My NightCrate was last opened by NightCrate 0.56.0",
  with "Install 0.56.0 or newer to open it" (a link to the latest release)
  and "open another workspace".
- **Backup failed, restore failed and unreadable** use the same card. Their
  wording is in the plan; the restore-failed card names the backup file and
  says to quit NightCrate and copy it over `nightcrate.db`.
- **"Open another workspace"** lists the other known workspaces with an Open
  button each, and offers "Create a new workspace" (the setup form).

## 5. Update check and notices

**Where the answers live:** `APP_DIR/updates.json`, separate from
`config.json`. Older versions rewrite `config.json` and would drop fields
they don't know. The file holds:
- whether to check (unanswered, on or off);
- the last check time and result;
- the skipped app version, and "Later" until when;
- the skipped OpenNGC release;
- the per-catalog reminder dates;
- the last version that ran.

The answer belongs to the app, not to a workspace, so switching workspaces
doesn't ask again. Unreadable JSON counts as an empty file. Reading the
file never writes it.

**The check** happens in the backend, and only when the frontend asks: at
app start, and when the window becomes visible again if 24 hours have
passed. There is no timer in the backend.
- **App:** fetch `latest.json` from the URL in section 2, and the latest
  published release from GitHub's releases API.
  - `latest.json` decides availability: for an installed app, the notice
    appears only when it has an entry for this platform and its version
    is newer than the running one. A source run needs no platform entry.
  - The releases API gives the notes, the publish date and the release
    page. `latest.json` is written when the draft is built, so it misses
    Fred's later edits to the notes and the real publish date.
  - If the two disagree on the version, the notice offers "Download the
    installer" (the release page) instead of Install.
- **OpenNGC:** the existing release-tag check, behind
  `/api/admin/catalogs/remote-version`, and only when OpenNGC is installed.
- **Both** use `services/http_client.get`, are deduplicated if two arrive
  at once, and never block a page. Automatic checks run only when checking
  is on. Failures are silent outside Admin, which shows "Last check failed
  at 21:04: couldn't reach GitHub."
- **Checks the user starts** still run when automatic checks are off:
  "Check now" in Admin, and opening Admin's Catalogs section, which asks
  GitHub for the OpenNGC version today and keeps doing so.

**Notices** (computed by the backend, filtered by skips and reminders):

| Notice | When | Buttons |
|---|---|---|
| "NightCrate 0.55.0 is ready to install" | newer app version | Install and restart · Later · Skip this version |
| "OpenNGC has a new release" | OpenNGC tag differs from the installed one | Open Catalogs · Skip this release |
| "The 50 MGC catalog was last downloaded 7 months ago" | downloaded and older than 183 days | Open Catalogs · Remind me in 6 months |
| "Wikipedia links were last downloaded 7 months ago" | Wikidata downloaded and older than 183 days | Open Catalogs · Remind me in 6 months |
| "NightCrate now downloads more from Wikidata" | the installed Wikidata query version is older than the current one | Open Catalogs · Remind me in 6 months |

- The app notice also shows "You have 0.54.0. Released on 20 November 2026",
  up to four bullet lines from the notes, and "All release notes on
  GitHub", which links to the release page
  (`…/releases/tag/v<version>`). Its fine print reads: "NightCrate backs up
  your workspace before it upgrades it. Installing takes about a minute,
  and NightCrate opens again by itself."
- **Source runs** get the same notice, without Install. In its place:
  "You're running NightCrate from source code. To update, pull the latest
  version from GitHub."
- **Later** hides the app notice for 24 hours. **Skip this version** hides
  that version until a newer one appears; Admin can bring it back.
- **Skip this release** hides that OpenNGC tag until a newer one appears.
- **Remind me in 6 months** snoozes that reminder. A fresh download resets
  its age anyway.
- **Open Catalogs** goes to `/admin#catalogs`. The Catalogs section gains
  the anchor `id="catalogs"`, as the star-catalog section already has one.

## 6. Installing an update

1. **Install and restart** first asks the backend what is running:
   - scans, behind `_INGEST_LOCK`;
   - frame analysis. The frontend drives it as a series of batches
     (`lib/useAnalyzeRun.ts`), and `_ANALYZE_LOCK` is free between
     batches, so the frontend checks its own running analysis as well;
   - plate solves (`solve_operations`);
   - catalog actions (`catalog_progress`);
   - star-catalog downloads, imports and index builds.

   If any is running, a dialog names it ("Install after the scan finishes.
   NightCrate is scanning a folder for NGC 7000. Click Install and restart
   again once it has finished.", with OK) and nothing is installed. Nothing
   is stopped halfway. Otherwise the backend reserves the install: until
   the install ends or fails, it refuses to start new scans, analyses,
   solves and catalog work, so nothing can start between the check and the
   stop. The reservation also counts requests already admitted but not
   yet started. It lasts two minutes and the open install dialog renews
   it, so a long download keeps it, and a crashed page lets it lapse (plan
   review, 2026-11-15).
2. **Otherwise the shell installs, in this order:**
   1. check the update;
   2. download it, reporting progress while the backend keeps running;
   3. stop the backend (closing its stdin, as in section 3);
   4. install;
   5. relaunch.

   Stopping before installing matters on Windows, where the installer
   replaces the backend's files and the updater exits the app itself.
3. **The progress dialog** (mockup section 2, middle) lists four steps:
   "Download the update" (with its size), "Install it" (with a bar), "Open
   NightCrate again", and "Back up and upgrade your workspace". After the
   relaunch, the loading window shows the last two.
4. **Failures:**
   - a failed download or signature check leaves everything as it was, and
     the dialog says why;
   - on macOS and Linux, a failed install restarts the backend on the old
     version and says "NightCrate couldn't install 0.55.0 and is still on
     0.54.0". The same applies on Windows if the installer can't be
     started;
   - **on Windows, once the installer has started,** the updater exits
     NightCrate (Tauri's updater 2.14.1 calls `std::process::exit` after
     launching it), and the installer reopens NightCrate when it finishes.
     If the installer itself fails after that point, NightCrate can't
     recover by itself; the installer shows its own error. The README says
     to download the installer from the release page in that case (plan
     review, 2026-11-15; Claude, under Fred's delegation).

   The failures NightCrate reports offer "Download the installer" (the
   release page), so a broken updater is never a dead end.
5. **The update must be the one the user agreed to.** The shell installs
   only the version shown in the notice. The updater requires the version
   recorded inside the signature to match the announced one
   (`requireSignedVersion`), so a forged manifest can't pair a newer
   version number with an older signed build.
6. **After the update:** on the first start of a new version, the frontend
   shows a toast: "Updated to 0.55.0. Your workspace was backed up first.
   What's new". The middle sentence appears only if a backup was taken.
   - The toast uses `#2f3238` with `#ece9e4` text in light mode, and
     `#e8e5e0` with `#23262c` text in dark mode, with a close button.
   - It sits at the bottom left of the content area and stays until closed
     or for 15 s, like the joke toast.
   - The backend tells the frontend that the version changed, from
     `updates.json`.

## 10. Build and release

Everything for packaging lives in a new top-level `packaging/` folder: the
freeze script, the Tauri shell, the notices generator and the smoke test.
Nothing in it is imported by the app.

**Freezing (cx_Freeze 8.7.4 in the test):**
- packages are kept as files, not zipped;
- the built frontend, the migrations folder and the package data are
  included.

The build checks what the test found:
- **Migrations:** the frozen migrations folder must match the source folder
  file for file. cx_Freeze dropped `0064` and `0067`, whose names aren't
  module names.
- **mlx kernels (macOS):** `mlx.metallib` must sit beside `libmlx.dylib`.
  Without it, the first GPU render killed the backend.
- **Version:** the frozen backend must report the package version; the test
  build reported "unknown".

**The smoke test**, run against the frozen backend on each system:
- health, version and a new workspace with every migration (integrity and
  foreign-key checks clean);
- the 20-file scan from the test (16 FITS, 4 zstd XISF), FITS and XISF
  renders (with the GPU on, on macOS) and a deep link;
- the Host check, and the stdin exit: the backend must exit after its stdin
  closes.

**Workflows** (`.github/workflows/`, actions pinned by commit; uv, Python
3.14, Node and Rust pinned to releases at least 7 days old):
- **`checks.yml`** runs on pull requests and pushes to `main`: the
  CLAUDE.md backend checks and `npm run build`.
  - It runs on macOS and Linux.
  - Windows runs too, but its failures don't fail the run in this version:
    the suite has never run on Windows. Its failures become PLAN.md items.
- **`release.yml`** runs only when started by hand, with the version as
  input. It builds `main`, and first checks that `VERSION`, both package
  versions and the shell's version all match the input.
  - **Each system:** freeze, run the build checks and the smoke test,
    generate the notices, and build the shell with the updater signing
    key.
  - **Each installer is then installed and launched** with a `--selftest`
    option: the shell checks that the page actually rendered in the app
    window and that it can reach the shell, then exits with the result. The
    backend must also answer `/api/health` with the right version. Then it is
    uninstalled. Linux runs under a virtual display.
  - **Finally:** create a **draft** release tagged `v<version>`, with the
    three installers, their update archives, signatures, `latest.json`
    and the LGPL source archive (section 11).
    Release notes are drafted from PLAN.md and edited by Fred in the draft.
  - **Source:** GitHub's source archives for the tag carry the
    Corresponding Source, build scripts included.
- **`update-rehearsal.yml`**, started by hand: builds a test pair (A, then
  B with a higher test version). Both use a private data folder and a
  local manifest set at build time, because macOS relaunches drop the
  environment. It runs A, lets it update itself to B unattended, and checks
  that B reports its version and that the workspace survived. It runs on
  all three systems. If a runner can't show the GUI, that system's
  rehearsal moves to the real-machine check.

**Test builds before acceptance.** GitHub starts a hand-started workflow
only once its file is on `main`. So v0.54.0's first signed draft release
can only come after the merge. GitHub's Windows and Linux machines can
still build and test unsigned installers before then, from code pushed to
GitHub. **Fred (2026-11-14):** Claude pushes temporary commits to a
throwaway test branch whenever installers need testing, and deletes the
branch at the end. Those commits stay out of the v0.54.0 branch's history.
The release workflow's build jobs also run on pushes to that branch:
unsigned, with installers kept as workflow artifacts and no release. A
test key signs the update rehearsal's builds.

**Tags move to release time.** From v0.54.0, `release.yml` creates the
version tag on the commit it builds, and `finalize-session` stops tagging
at PR time. Today a tag can end up behind the merged code: v0.53.0's tag
is on `97139ea`, before the PR's last commit. Versions Fred doesn't release
get no tag.

**The updater signing key:**
- Fred adds the private key and its password as repository secrets, and
  keeps an offline copy.
- The public key is committed in the shell's configuration.
- **If the key is lost:** installed copies can't verify new updates, and
  everyone must download the next installer by hand, once. The README says
  so, and the key's offline copy is the protection.
