# v0.53.0 — Home page: where your work stands

The Home page today shows a welcome line and a joke wand. Fred asked on
2026-11-13 for a real Home page ("at this point I have no idea whatsoever
what should be on the home screen"). He shaped it from local mockups that
day, and confirmed a revised mockup on 2026-11-14:
`.superpowers/mockups/home/home-v2.html` (ignored). Where the mockup and this
text differ, the text wins.

## Fred's decisions

- **Purpose:** show where your projects stand, and when you can image next.
  NightCrate isn't "first and foremost a planner", so a night time line of
  which projects are up tonight was rejected for the top of the page, as
  were a season ribbon and a picture-first page (2026-11-13).
- **Content, in order:**
  - projects by stage;
  - the three most recently imaged projects;
  - the next two weeks, per location;
  - the latest picture;
  - the last 12 months;
  - Rigs and Locations panels (2026-11-13).
- **The heading is just "Projects".** A sentence repeating the bar was
  rejected ("that's already shown in the bar graph underneath").
- **The last 12 months is a rolling window,** not the calendar year ("what
  does this year mean when it's January 10th").
- **The next two weeks has one row per location,** each with its own
  forecast and moon-free dark hours. Each row loads on its own, so the rest
  of the page never waits ("it has to not delay loading the rest of the
  page").
- **Rigs and Locations panels** link to each item's page and to the main
  pages.
- **The joke wand moves to the nav's bottom row,** right-aligned beside the
  theme and log icons. The joke shows as a toast that stays about 15 s or
  until closed ("the joke popup is too fast to disappear").
- **"Ready to process" becomes a project status you set by hand,** like
  Complete (2026-11-14, option 3). Per-filter goals were removed in v0.41.1,
  so the stages can't be derived from goals.
- **Location rows when no default is set** (2026-11-14, "that's fine"):
  - the locations active projects use;
  - if there are none, your locations, up to four;
  - with no locations, a line about the weather, not about imaging ("this
    is not about what you can image next, this is about the weather
    conditions").
- **The revised mockup is approved** ("ok, this is good. please proceed"),
  with unattended building and Claude's calls confirmed at the end.

## Goals

- The page answers "where do my projects stand?" at a glance, and links
  straight to the projects, rigs and locations behind each number.
- The forecast rows never delay the rest of the page.
- Every figure comes from the same data as the project pages (sessions,
  pictures), so the numbers agree.

## Non-goals

- Per-filter goals, or any progress-against-goal display.
- Tablet and phone checks. These wait for Fred's later tablet review; the
  layout still stacks sensibly when narrow.
- Changing the Weather page or its verdict rules.

## 1. The new status: Ready to process

- **Value:** `ready_to_process`. The full set, in this order everywhere it's
  listed, is:
  - `active`;
  - `ready_to_process`;
  - `paused`;
  - `complete`;
  - `abandoned`.
- **Label:** "Ready to process". The status menu describes it as "Captured,
  waiting to be processed". The others keep their descriptions: "Still
  capturing", "On hold", "Finished" and "Stopped for good".
- **Database:** a new migration rebuilds `project` with the wider CHECK
  constraint.
  - `project` is a parent table, so the rebuild uses
    `PRAGMA legacy_alter_table = ON`, as migration 0040 does. This keeps
    child foreign keys pointing at `project`.
  - Keep every column, including ones added after 0031 (`location_id` and
    any others), with their defaults, indexes and triggers.
- **Everywhere statuses are listed:** the backend `ProjectStatus` and
  `_VALID_STATUSES`, the Gallery's status order and filter, the status menu
  (`ProjectStatusChip`), the Gallery pills (`StatusPills`) and
  `PROJECT_STATUS_COLORS`. Search for `abandoned` to find them all.
- **Gallery pill colour,** outlined like the others: `#17786d` in the light
  theme, `#5cc6b9` in the dark.
- **"Active project"** keeps meaning `status = 'active'` wherever the app
  counts active projects (the Home page's rigs, locations and forecast
  rows). A project that's ready to process no longer needs the sky.

## 3. Projects by stage

- **Stages,** for projects that aren't retired (`project.active = 1`):

| Stage | Rule |
|---|---|
| Not started | status `active`, with no integration time (no `project_session` minutes) |
| Capturing | status `active`, with integration time |
| Ready to process | status `ready_to_process` |
| Complete | status `complete` |
| Paused | status `paused` |
| Abandoned | status `abandoned` |

  Integration time is `SUM(exposure_seconds × num_subs)` over the project's
  `project_session` rows, the same figure as the Overview tab.
- **The bar** is 40 px high with 8 px corners and 2 px gaps.
  - Each non-zero stage is a segment whose flex weight is its count.
  - The segment shows its count (13.5 px semibold), with a 34 px minimum
    width.
  - Each segment is a link to `/projects?stage={key}`. It has an accessible
    name ("Capturing: 4") and a tooltip ("Capturing: 4. Active, with data
    captured.").
- **The key** sits below the bar and lists all six stages, zeros included.
  Each entry is a 12 px swatch, the bold count, then the lower-case label.
- **With no projects at all,** the bar and key are replaced by "No projects
  yet." and a "Create a project" link to `/projects`.
- **The Projects page** reads `stage` from the URL. With a valid value it
  shows only those projects, and shows a removable chip ("Showing: Capturing
  ✕") that clears the parameter.
  - `GET /api/projects` gains an optional `stage` parameter, filtered on the
    server, because Not started and Capturing depend on integration time.
  - It applies alongside the search and the retired toggle.
  - An unknown value in the page's URL is ignored and not sent; the API
    rejects one with 422.

## 4. Recent projects

- **Which:** the three non-retired projects with the latest night imaged,
  any status. Ties go by name.
  - Session dates are read through `services/gallery.valid_session_date`,
    as the Overview and Gallery do, so text that isn't a date never wins.
  - Projects with no valid session date don't qualify.
- **Each card** (a link to the project):
  - **Picture:** the project's main-image thumbnail, 150 px high and
    cropped to fill, or "No picture yet" on a dark ground.
  - **Name** (15 px semibold), with a stage pill in the stage colour.
  - **Target line:** the same target text the Gallery card shows, followed
    by "in {constellation}". The constellation comes from the plate solve's
    centre, as the Info tab works it out
    (`api/project_info.py`, `constellation_for_coords`).
  - **"{total} collected",** with the total in semibold.
  - **One row per filter line,** in the order and with the labels of the
    project's integration summary (`GET /api/projects/{id}/integration`):
    the label, a 5 px bar in the filter's colour scaled to the project's
    largest line, and the duration. A "Not recorded" line keeps its existing
    look.
  - **"Last imaged {date}, {n} nights so far".**
- **No qualifying projects:** "Nothing imaged yet. Projects you capture
  data for show up here."

## 5. The next two weeks

**Which locations** (at most four rows), using non-retired locations only:
1. **A default location exists:** the default, then the locations of active
   projects (`project.location_id`) by number of active projects, then by
   name.
2. **No default:** the locations of active projects, ordered the same way;
   if there are none, your locations by name.
3. **No locations at all:** "Add a location to see its weather for the next
   two weeks.", with an "Add a location" button to `/locations`.

**Row label:** the location name (13 px), with a note under it (12 px,
quiet): "Default location", "Used by {n} active project(s)", or nothing.

**The grid:**
- 170 px for labels, then 14 equal columns.
- **The columns are 14 nights,** starting from tonight by the browser's
  clock, using the Weather page's rule: before local noon, "tonight" is the
  night that began yesterday.
- The header shows the weekday and day number; tonight's is in amber.
- **Rows match cells to columns by ISO date.** A location in another time
  zone, or a night the forecast doesn't return, leaves an empty cell
  ("–", "No forecast for this night").
- Each cell shows:
  - the night's verdict mark (20 px round);
  - a bar of moon-free dark hours, up to 30 px for 11 h;
  - the hours, to one decimal ("4.5 h").

**Verdict marks,** using the Weather page's labels and colours:
- Go: "✓" on the clear ground;
- Uncertain: "?" with an outline in the uncertain colour;
- No: "✕" on the no-go ground;
- Not enough data, and Night over: "–" with a dashed outline in the neutral
  colour.

**Cells:**
- A cell's accessible name and tooltip read, for example, "Backyard,
  Monday 16 November: Go; 6.8 h of dark sky with the Moon down".
- Clicking a cell opens `/weather?location={id}&date={date}`.

**Under the grid:** a legend with Go, Uncertain and No, and "Dark hours with
the Moon down, for each location".

**Loading:**
- The page asks for the row list with its summary. The rows then request
  their nights one after another, each starting when the previous has
  succeeded or failed. Loading them together made Open-Meteo answer 429
  Too Many Requests (rendered checks): each load is about seven provider
  calls. Each row still loads independently of the rest of the page.
- While a row loads, its marks are 20 px skeleton circles.
- The moon-free hours could be computed without the forecast, but they come
  in the same response, so a loading row shows skeletons for both.
- If a row fails, it shows "Couldn't load the forecast for {name}." with a
  "Try again" text button. The other rows are unaffected.
- **Freshness:**
  - The legend line ends with "Updated {time}" (the oldest evaluation among
    the loaded rows) and a "Refresh" text button that refetches every row.
  - A row whose forecast data is stale (the provider couldn't be reached,
    so the cache was used) adds a quiet note under its label: "Forecast
    from {time}". The time is the oldest stale source's (`stale_since`).

**Backend:**
- `GET /api/weather/fortnight?location_id=` returns `{location_id,
  evaluated_at, stale_since, nights: [{date, verdict,
  moonless_dark_hours}]}` for the forecast nights.
  - It's built from the same cached forecast pipeline as
    `POST /api/weather/forecast`, with the location's saved rules.
  - `stale_since` is the oldest fetch time among the stale sources (the main
    forecast, the cloud models), or null.
- `moonless_dark_hours` is `NightSummary.moonless_dark_hours`, which the
  forecast already computes. `POST /api/weather/forecast`'s night response
  gains the same field.
- **All of the forecast's CPU work runs off the event loop:**
  - the night summaries, the Moon altitudes, the evaluation and the
    response building, in one `asyncio.to_thread` call after the async data
    loading;
  - this covers `POST /api/weather/forecast` too, so four uncached
    locations don't hold up other requests, such as the page summary.
- **Frontend:**
  - one query per location, with `staleTime` 5 minutes, refetch on window
    focus, and no interval refetch;
  - saving a location or its imaging rules invalidates its row.

## 6. Latest picture

- **Which:** the most recently added project picture (`project_image`, the
  newest `created_at`, ties by the higher id) of a non-retired project.
- **Shown:** 340 px high and cropped to fill. The image is that picture's
  own rendition (`renderedImageUrl` with its `image_id`), sized with
  `pickRendition` for the drawn width. The caption, on a bottom gradient, reads:
  - the project name (16 px semibold);
  - "{target} in {constellation}. {Status}, {date added}." Missing parts
    are left out.
- **Click:** opens the project.
- **No pictures:** "No pictures yet. Add a picture to a project to see it
  here."

## 7. The last 12 months

- **Window:** from the first day of the month 11 months before the current
  month, through today. For any day in November 2026 it starts on
  1 December 2025. The subtitle reads "since 1 December 2025".
  - This keeps the 12 monthly bars whole and always ends on today, so 10
    January shows February to January, not ten days.
- **Figures,** from `project_session` rows whose valid session date
  (`valid_session_date`) falls in the window, for non-retired projects:
  - hours of light frames (exposure × subs);
  - nights (distinct `session_date`);
  - new pictures (`project_image.created_at` in the window).

  They read, for example: "**46 hours** of light frames across **19
  nights**, and **3 new pictures**."
- **Best night:** the date with the most integration across all projects.
  It reads "Your best night was 30 September: 7 h 40 m of light frames on
  Pacman Nebula." There's no "the", because project names are free text
  ("on the Test" read badly in the rendered checks).
  - It's "best", not "longest", because two rigs on one night add up, so
    the figure is integration, not the length of the night.
  - When more than one project shared that night, "on Pacman Nebula and
    1 other".
  - It's left out when there are no nights.
  - Images count by the local date of `created_at`.
- **Monthly bars:** 12 bars, oldest first, labelled with the month's
  initial. Each bar's height is proportional to its hours (52 px for the
  largest), and an empty month shows a 2 px track. Each bar's tooltip and
  accessible name give the month and hours.
- **Nothing in the window:** "No light frames in the last 12 months." The
  bars still show.

## 8. Rigs and Locations panels

Each panel has its heading, an "All rigs" or "All locations" link to the
main page, then up to five rows. Each row links to the item.

- **Rigs:** rigs that are yours and not retired (`is_mine = 1`,
  `active = 1`). They're ordered by hours in the window (most first), then
  by the existing rig order.
- **Locations:** non-retired locations. The default comes first, then by
  hours, then by name; the default carries a "Default" tag.
- **Each row:**
  - the name (14 px semibold);
  - on the right, hours ("31 h") over nights ("13 nights", or "No nights");
  - under the name, quiet:
    - "Last used {date}, by {n} active project(s)";
    - "Last used {date}" when it's in use by no active project;
    - "Not used yet" when there's no session at all.
- **Rig figures** come from `project_session.rig_id`.
  - Its active projects are those with status `active` that link the rig
    (`project_rig`) or have sessions with it.
- **Location figures** come from the sessions of projects whose
  `location_id` is that location. Sessions don't record a location, so this
  is the location set on each project.
- **Retired rigs and locations** are left out of the panels and the
  forecast rows. Their projects' integration still counts in the stages,
  recent projects and the 12 months.
  - Its active projects are those with status `active` at that location.
- **Links:** `/rigs?select={id}` and `/locations?select={id}`. Both pages
  read `select` on load, select that item and scroll it into view. An
  unknown id is ignored.
- **Empty panels:** "No rigs yet." or "No locations yet.", with the heading
  link kept.

- **The wand moves to the nav's bottom row,** after the theme and Activity

  - With the nav open, it's pushed right (`margin-left: auto`).

  - a Snackbar at the bottom left of the content area, at most 460 px wide;
  - a small wand icon, the text and a close button;
  - it stays 15 s, or until closed;
  - clicking a wand again replaces the line with the next one;
  - the toast's inverted colours follow MUI's Snackbar default.

  `EasterEggWand` keeps its props, and its sparkles stay.
- **There is one toast slot for the whole app,** so the nav wand and a
  page's wand never stack toasts. A new line replaces the shown one and
  restarts the 15 s timer. Moving the mouse away no longer dismisses it.

## 10. The Home API

`GET /api/home` returns one summary, computed on request with the server's
local date as "today". The page refetches it on every visit (`staleTime` 0),
because it's cheap, and edits elsewhere would otherwise leave stale counts.
Minutes are floats, as in the integration summary.

```json
{
  "today": "2026-11-14",
  "stages": {"not_started": 1, "capturing": 4, "ready_to_process": 1,
             "complete": 3, "paused": 1, "abandoned": 1},
  "total_projects": 11,
  "recent": [{"project_id": 3, "name": "…", "status": "active", "stage": "capturing",
              "target_label": "…", "constellation": "Cas" | null,
              "thumbnail_version": "…", "has_image": true,
              "total_minutes": 140,
              "lines": [{"label": "Ha", "minutes": 80, "not_recorded": false}],
              "last_date": "2026-11-09", "nights": 2}],
  "latest_picture": {"project_id": 7, "project_name": "…", "image_id": 12,
                     "added": "2026-05-18", "status": "complete",
                     "target_label": "…", "constellation": "UMa" | null} | null,
  "year": {"since": "2025-12-01", "minutes": 2760, "nights": 19, "new_pictures": 3,
           "best_night": {"date": "2026-09-30", "minutes": 460,
                             "project_id": 5, "project_name": "…", "other_projects": 0} | null,
           "months": [{"month": "2025-12", "minutes": 210}]},
  "rigs": [{"rig_id": 1, "name": "…", "minutes": 1860, "nights": 13,
            "last_used": "2026-11-09" | null, "active_projects": 3}],
  "locations": [{"location_id": 1, "name": "…", "is_default": true, "minutes": 2040,
                 "nights": 15, "last_used": "2026-11-09" | null, "active_projects": 3}],
  "forecast_locations": [{"location_id": 1, "name": "…", "note": "default" | "used" | null,
                          "active_projects": 2}],
  "workspace_key": "…"
}
```

- `months` always has 12 entries, oldest first.
- `recent` has at most 3 entries; `rigs` and `locations` at most 5;
  `forecast_locations` at most 4.
- Pure aggregation lives in a service module that takes rows and "today".
  The router does the SQL, as the project's API boundary rules require.
