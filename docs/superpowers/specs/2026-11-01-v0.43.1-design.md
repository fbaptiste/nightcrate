## 1. Sky images built from tiles

### 1.1 Why

Catalog thumbnails and the planner's sky cells come from CDS's hips2fits
service.
- Every image is one request to `alasky.cds.unistra.fr`, which renders a JPEG
  from the CDS DSS2 colour HiPS.
- hips2fits has no mirror outside Strasbourg, and CDS has been unreachable
  since about 2026-10-21.
- New thumbnails and planner areas fail. Each failure waits about 81 s of
  timeouts (colour, then red, each 2 × 20 s), then backs off for an hour.

**Fred (2026-11-01):** NightCrate assembles the images itself from the
survey's HiPS tiles. It fetches the tiles from CDS first and from ESA's copy
when CDS is down.

### 1.2 Facts

- **The survey.** CDS's DSS2 colour HiPS (`CDS/P/DSS2/color`): 512 px JPEG tiles
  in HEALPix NESTED order, deepest order 9 (0.805″ pixels), equatorial frame,
  release 2019-05-07.
- **Sources:**
  - CDS serves it at `https://alasky.cds.unistra.fr/DSS/DSSColor` (Aladin
    Lite's default list; unreachable to verify during the outage).
  - ESA serves an official mirror at `https://cdn.skies.esac.esa.int/DSSColor`
    (verified 2026-11-01; `hips_status = public mirror unclonable`, release
    date 2019-05-07).
  - A copy of CDS's own `properties` file made in September 2024 (Aladin
    Lite repository) shows the same release date, so ESA's copy matches the
    CDS master as of then.
- **Tile URL:** `{root}/Norder{k}/Dir{(n // 10000) * 10000}/Npix{n}.jpg`
  (HiPS 1.0 §6.1).
- **Prototype, 12 cached planner cells:** the north pole region, RA 0/360 and
  the ±41.8° HEALPix base boundary, four per tier, compared with the cached
  hips2fits renders.
  - **Orientation.** Split a pixel's NESTED index into tile index
    `n >> 18` and in-tile Morton coordinates: `ix` from the even bits, `iy`
    from the odd bits. The pixel then sits at JPEG `column = iy`,
    `row = ix`, with row 0 at the top. This rule won on all 12 cells against
    the other seven orientations, by correlation 0.77–0.96 against at most
    0.57. It matches HiPS 1.0 figure 4 (FITS tile corners: bottom-left E,
    top-left S, top-right W, bottom-right N) and the standard's note that
    JPEG rows run top-down.
  - **Output orientation.** Output images are computed in FITS pixel order
    (row 0 = south edge for north-up) and flipped vertically when encoded as
    JPEG.
  - **Position:** within 0.02 px of hips2fits.
  - **Tile order:** the coarsest order whose pixels are no larger than the
    output pixels, the same order hips2fits evidently used. Neighbouring
    orders correlated worse.
  - **Bilinear sampling:** correlation 0.88–0.99. Mean brightness within
    0.6/255 in 8 cells and 1–1.3 in 3. Near the north pole the dark
    background is about 5 levels brighter than hips2fits's; the cause is
    unknown (§1.9).
  - **Cost per planner cell:** 10–13 tiles (0.6–1.9 MB). About 0.5–0.9 s
    cold, 0.2 s once the tiles are cached, against about 2.3 s from
    hips2fits. A 3×3 block of cells needs about 40% fewer tile downloads with
    a cache.
  - **Seams:** none visible where a new cell meets cached hips2fits cells,
    except the faint near-pole square.
- **Terms:**
  - The DSS terms (STScI) are unchanged from today; only the transport
    changes.
  - HiPS 1.0 §5.4: "unclonable" forbids another server copying the survey; it
    says nothing against client access.
  - ESA's science-archive terms (CC BY-NC 3.0 IGO) cover data from ESA
    missions, not third-party data such as DSS. No ESASky-specific terms were
    found.
  - NightCrate fetches tiles at runtime for the user and redistributes
    nothing.

### 1.3 Design

**New service: `services/hips_tiles.py`.** It holds pure functions plus one
async fetch layer, does not import `api/`, and replaces `hips_client.py`.

- **Sources, in order (Claude's call: CDS first, Fred's stated preference;
  one constant to reorder after the speed check in §1.9):**
  ```
  HIPS_TILE_SOURCES = (
      HipsTileSource("cds", "https://alasky.cds.unistra.fr/DSS/DSSColor"),
      HipsTileSource("esa", "https://cdn.skies.esac.esa.int/DSSColor"),
  )
  ```
  The survey identity stays `CDS/P/DSS2/color` (`HIPS_DSS2_COLOR`). It moves
  here from `hips_client.py`.
- **Tile order (pure):** `tile_order_for(scale_deg_per_px)` returns the
  coarsest order `k` in 0–9 whose pixel size,
  `58.6323° / 2^(k+9)`, is at most the output pixel size.
- **Render plan (pure):** `plan_render(wcs, width, height)`:
  - computes the sky position of every output pixel centre, then its NESTED
    index at pixel order `k+9` (`astropy_healpix.lonlat_to_healpix` with
    `return_offsets=True`);
  - computes the tile set;
  - **Cap: `MAX_TILES_PER_IMAGE = 32` (Claude's call).** If the set is
    larger, it moves one order coarser and recomputes, down to order 0. Today's
    largest cells need 13 tiles. The cap guards against a bug or an
    unexpected request fetching thousands of tiles, which the prototype once
    did (12,700).
- **Sampling (pure):** bilinear inside each tile, using the sub-pixel offsets
  `dx, dy` (which line up with `ix, iy`, checked to 1e-4″), clamped at tile
  edges.
  - Output: `uint8` RGB, H×W×3, flipped vertically.
  - Pixels whose sky position is not finite stay black.
- **JPEG:** Pillow, quality 90. Cached hips2fits cells averaged 56–93 KB at
  800².
- **Tile fetch (async):** `fetch_tile(order, npix) -> TileBytes(jpeg,
  source)`. Revised after the plan review (round 1).
  - **One attempt per source.** `http_client.get` gains `attempts: int = 2`;
    existing callers keep today's single retry, and tiles pass
    `attempts=1`. Each attempt uses `timeout=20, connect_timeout=5`.
  - **Acceptance.** A 200 is accepted only if the body decodes completely as
    an RGB 512×512 JPEG. The check runs in a worker thread, before anything
    is cached. A truncated or HTML body is rejected the same way as a 404 or
    5xx: try the next source for this tile, without marking the source down.
  - **Source health (Claude's call; Codex agreed; state machine revised in
    round 2).** Each source is in one of four states:
    - `unknown`, at start and after a down window expires;
    - `up`, after a success;
    - `probing`;
    - `down until t`.

    Transitions:
    - **From `unknown`:** exactly one request becomes the probe, and the
      state goes to `probing`. While a probe runs, other requests skip that
      source. If no other source is usable, they await the probe's outcome,
      then choose again.
    - **Down:** a connect error, connect timeout or read timeout (from an
      `up` or `probing` source) gives `down until now + 10 min`.
    - **Up:** a success gives `up`.
    - **Other failures:** a 404, a 5xx or an invalid body tries the next
      source for this tile. From `up` the state is unchanged; a probe that
      ends this way gives `up`, because the server is reachable.
    - **Every probe settles (round 3).** A probe is one attempt at one
      source, not the whole tile fetch. Whatever ends it moves the source
      out of `probing`:
      - success or an HTTP or body failure → `up`;
      - a connect or read timeout → `down`;
      - an unexpected exception or cancellation → `unknown`.
    - **Each tile fetch tries each source at most once,** so it cannot loop.
      When every source has been tried or is unusable, it raises
      `TileUnavailable`.
    - **Total outage:** if every source is `down` and unexpired, `fetch_tile`
      fails at once with no request. Recovery is guaranteed because windows
      expire to `unknown`.
    - **Cost:** a total outage costs one probe per source per 10 minutes: a
      5 s connect timeout, or up to 20 s for a read timeout. Requests already
      in flight when a healthy source fails can each fail once, up to 8.
  - **Shared fetches.** Concurrent requests for the same `(order, npix)`
    share one task. A render awaits it through `asyncio.shield`, so
    cancelling one render never cancels a tile another render needs. Cache
    and health state change only on the event loop.
  - **Concurrency:** one module-level semaphore of 8 tile requests in total,
    so no single server sees more than 8 connections from NightCrate at once.
  - **Memory:** an in-memory LRU of validated compressed tiles, with their
    source, capped at 64 MB (Claude's call), keyed by `(order, npix)`. Both
    sources serve the same release. Nothing is written to disk, so no new
    folder, sweep or eviction rule is needed. Rendered images keep their
    existing disk caches.
  - **Logging:** each successful tile at DEBUG with its source; each
    source-down transition at WARNING.
- **Render (async):**
  `render(wcs, width, height) -> RenderedImage(jpeg: bytes, sources:
  frozenset[str])`.
  - It plans, fetches every tile concurrently (failing on the first tile no
    source can supply), then samples and encodes.
  - **Sequence (revised in round 2):**
    1. Acquire the module render permit.
    2. Plan in a worker thread.
    3. Fetch the tiles asynchronously.
    4. Decode, sample and encode in a worker thread.
    5. Release the permit.
  - **Cancellation:** the permit is held until any started worker thread has
    actually finished, even after cancellation. That uses the shield-and-wait
    pattern of `star_catalog.fetch._in_thread`, so repeated cancellations
    cannot exceed the bound.
  - **Limit:** `MAX_CONCURRENT_RENDERS = 4` (Claude's call; the round-1
    draft said 2). The two caches together can request 16 renders at once.
  - **Memory:**
    - plans store compact arrays (`int32` tile index, `float32` offsets),
      about 13 MiB for a 1024² cell;
    - sampling gathers only the four neighbouring `uint8` values per output
      pixel and works in float32 on those, never converting the whole tile
      stack;
    - Codex's estimate (round 3): 4 plans about 52 MiB, 4 decoded tile sets
      about 96 MiB, and the LRU 64 MiB, before sampling buffers.
    - Claude measures the total incremental peak and keeps 4 permits only if
      it stays near that.
  - It is numpy and Pillow only, with no GPU and no process pool, about
    0.1–0.25 s per 800² cell.
- **WCS builders (pure):**
  - Sky cells keep `sky_tiles.cell_wcs(...)`.
  - Thumbnails get a new `thumbnail_wcs(ra, dec, fov_deg, width, height)`:
    TAN, north up, east left, `CDELT = fov / max(width, height)`,
    `CRPIX = ((w+1)/2, (h+1)/2)`. This matches hips2fits's `fov`, the size
    of the larger image dimension (astroquery's hips2fits documentation).
    Every thumbnail is square.

### 1.4 Changes to the two caches

- **`thumbnails._fetch_and_store` and `sky_tile_cache._fetch_and_store`:**
  - call `hips_tiles.render(...)` inside their existing semaphores;
  - store `source='dss2_color'`;
  - on failure, store the existing `placeholder` row with `fetch_error`
    naming each source's last error.
- **Red fallback dropped (Claude's call).** The colour survey covers the whole
  sky (`moc_sky_fraction = 1`). Its 11 plates with no blue keep their red
  data. The red fallback only ever fetched another hips2fits rendering.
- **Failure backoff: 1 hour → 10 minutes (Claude's call).** A failure now
  means every source failed. Ten minutes still prevents request storms. This
  answers the open question recorded on 2026-10-30.
  - The frontend is unchanged. Sky cells stop at a 204, and thumbnails stop
    after 30 retries.
  - Recovery therefore happens on the next request after the window: a
    remount, reopening the view or panning. It is not automatic in an open
    view.
- **Atomic file writes.** Write a temporary file, then `os.replace`. Today's
  `write_bytes` can leave a truncated JPEG after a crash.
- **Unchanged:**
  - filenames, keys, rehydrate and the sweep, so the 2,941 cached cells stay
    valid (same survey, same geometry);
  - the API, its responses (200/202/204) and the frontend;
  - the `source` CHECK values, so no migration;
  - `_ALLOWED_HIPS_SURVEYS`.
- **Removed:**
  - `hips_client.py` and `tests/services/test_hips_client.py`;
  - the hips2fits serialisation tests in `test_sky_tiles.py`, but only if
    `cell_wcs_dict` goes unused. If nothing else uses it, remove it and its
    two tests; `cell_wcs` stays.

### 1.6 Tests (normal, edge, failure)

**Pure functions:**
- `tile_order_for` at each tier: narrow → 8, medium → 6, wide → 4; and at the
  clamps 0 and 9.
- **Orientation, against an independent oracle.** The test paints each
  synthetic tile from a smooth function of sky position.
  - The sky position of JPEG pixel (column, row) comes from HiPS 1.0
    figure 4's corners: JPEG top-left is the S corner, top-right W,
    bottom-left E. Through `astropy_healpix.healpix_to_lonlat` at the tile's
    own order, that means `dx = (row + 0.5)/512`, `dy = (column + 0.5)/512`.
    This is a code path independent of the Morton split under test.
  - The render must reproduce the function at each output pixel's WCS
    position. The test computes those positions itself with astropy, JPEG
    row flip included, not with the renderer's helpers.
  - **Tolerances:** within JPEG quantisation, set by encoding the synthetic
    tiles at quality 100 and comparing in a smooth region. Bilinear
    interpolation error on the smooth function is bounded and stated in the
    test.
  - Orientation mutations are applied to the renderer only, never to the
    oracle.
  - Cases: views at the equator; straddling a tile edge and a base-face
    corner; crossing +41.8° and −41.8°; containing the north pole;
    containing the south pole; crossing RA 0/360; a thumbnail view.
  - A parametrised check proves the test fails for the 7 wrong orientations
    and for a missing output flip.
- **No DSS fixtures in the repository.** DSS imagery is not redistributed.
- The tile cap coarsens the order. A forced over-cap request (very large
  view, cap 4) ends at an order whose tile count is at most the cap. A cap
  that cannot be met even at order 0 raises.
- Pixels with non-finite positions stay black.

**Tile fetch** goes through the real `http_client.get` with
`httpx.MockTransport` failures, not a stub, so attempt counts are real.
- CDS succeeds. Then CDS fails to connect: exactly one attempt, and ESA
  serves the tile.
- A 404 from CDS tries ESA.
- A truncated JPEG and an HTML 200 are rejected, and ESA is tried; the bad
  body is never cached.
- Every source fails: the error names each source.
- **Down window** (patchable monotonic clock):
  - the window skips CDS;
  - after it expires exactly one probe goes out while 8 concurrent requests
    wait or skip;
  - with every source down, the call fails with no request.
- **Probe outcomes:** a cold probe and a recovery probe each return 404, 5xx
  or an invalid JPEG, with concurrent callers waiting. Each probe settles to
  `up`. Neither the callers nor the probe hang or spin. When both sources
  fail this way, `TileUnavailable` is raised once per fetch. Cancelling a
  probe returns the source to `unknown`.
- **Shared fetches:** concurrent requests for one tile make one request.
  Cancelling one waiting render leaves the shared fetch running for the
  other.
- The LRU respects its byte cap and keeps the source.
- The global semaphore caps concurrent tile requests at 8, and the render
  limit caps CPU renders at 2.

**Caches:**
- Existing tests that patch `hips_client` move to patching
  `hips_tiles.render` or `fetch_tile`.
- Tests that compare bytes now compare against the rendered JPEG.
- The 10-minute backoff expires. Red-fallback tests become no-fallback tests.
- The cache file is replaced atomically: a fail-mid-write leaves no partial
  file.

**`test_app_dir_isolation.py`:** no new `APP_DIR` use; the scanned paths still
include `services/thumbnails.py`.

## 2. Faster star download and the already-built range fix

### 2.1 Download in four parallel pieces (Fred, 2026-10-30)

**Facts:**
- One stream from Zenodo ran at 0.66–0.77 MB/s, about 25–30 minutes. Four
  ranges ran at 2.36 MB/s in total, about 8 minutes.
- The file is 1,142,276,749 bytes, with a published SHA-256.
- Today `stream_to_file` resumes one `.part` file and needs an exact
  `Content-Range`.

**Design:**
- **Pieces:** `PIECES = 4`, with fixed boundaries `[i·S//4, (i+1)·S//4)`
  (S = compressed size). Each piece streams into its own staging file,
  `<compressed_name>.part{i+1}of4`.
  - A piece's file size is its progress, so resume needs no extra record.
  - Each request is `Range: bytes={start+have}-{end-1}`. It needs a 206 with
    exactly `Content-Range: bytes {start+have}-{end-1}/{S}`. Writes never pass
    the piece's end.
- **Shared code:** `http_client.stream_to_file` generalises to a byte range
  (`offset`, `length`, `total_size`). The single-stream form is the case
  offset 0, length S.
  - **In piece mode,** a 200 or a 206 whose Content-Range is not the
    requested range raises `RangeNotHonoured` before any body byte is
    written.
  - **The single stream keeps today's rules:** a 200 restarts from 0, and a
    wrong Content-Range is `MalformedRange`.
  - One transient retry per piece, as today.
- **Running the pieces:** four piece tasks under the operation.
  - **Progress:** each piece reports through its own counter, starting from
    its validated file size. The operation's `_progress(done)` gets their
    sum, so the speed and remaining-time display keep working. No file
    sizes are re-read during writes.
  - **Stopping (revised after round 1):**
    - Pieces are stopped by explicitly cancelling their tasks and awaiting
      every one, not through the user's cancel event.
    - A watcher cancels them as soon as the user cancels, even if no data is
      arriving.
    - The user's cancel always wins: no fallback or assembly starts after
      it.
    - Shutdown's 10 s wait therefore holds even with stalled connections.
  - If one piece fails after its retry, the others are cancelled and
    awaited, the piece files are kept, and the operation fails with the
    piece's error. The user resumes with Download.
- **Falling back to one connection (Fred: when the server doesn't return the
  requested range):**
  - The pieces are stopped.
  - **Order matters for crash safety:** delete pieces 2–4 first, then rename
    piece 1, which is a prefix of the file, to the single-stream `.part`.
    If piece 1 is missing, the `.part` starts empty. A crash between steps
    leaves either piece 1 alone, which resumes as pieces, or the `.part`
    alone, which resumes as a single stream. It never leaves both.
  - Speed samples reset. Progress drops to the retained prefix, honestly.
  - The single stream continues in the same operation, unless the user has
    cancelled.
- **Which partial is used.** Every file's length is validated first:
  - a piece file must be 0 to its range length;
  - a `.part`, 0 to S;
  - a `.bz2`, exactly S;
  - anything else is deleted.

  Only one form counts, chosen in this order:
  1. a `.bz2`, only when no partial exists beside it (see the cleanup
     rule);
  2. pieces or a `.part`. If both exist, which only a manual copy could
     cause, keep the form holding more bytes and delete the other;
  3. a v0.43.0 `.part` resumes as a single stream with its bytes kept
     (Claude's call; Codex agreed);
  4. a fresh start in pieces.
- **Cancellation in every network mode.** The same watcher owns the four
  pieces, the fallback single stream and the legacy single stream. Each runs
  as a task, cancelled and awaited when the user cancels. The watcher itself
  is cancelled and awaited on every exit path.
- **Stale cleanup before the space check.** `start_download` and
  `start_import` run the stale-staging cleanup, while no operation is
  active, before their free-space preflight. A leftover assembly file
  therefore cannot block a retry that fits once it is removed.
  - **An archive beside partials (rounds 3–4).** When a `.bz2` sits beside
    piece files or a `.part`, the cleanup keeps the partials and deletes the
    `.bz2`, before the preflight.
    - **Why:** size alone cannot prove the archive was verified. An
      interrupted import writes the `.bz2` before checking it (`fetch.py:279`).
    - **Assembly crash after the rename:** if the pieces are complete, the
      next Download joins them again (one copy and hash, no download). If
      some were already deleted, only those pieces are downloaded again.
- **Assembly (revised after round 1; the round-1 blocker):**
  - **Join:** pieces 1–4 are copied in order into a hidden temporary file,
    `.<compressed>.assembling.tmp`.
    - The copy and the hash run in the operation's owned thread
      (`_in_thread`).
    - Both check the thread cancel flag between 8 MiB chunks, so a cancel or
      shutdown stops them promptly.
  - **Check:** the temporary file is checked by SHA-256.
  - **On a match:** it is renamed to the `.bz2`, then the pieces are deleted,
    then unpacking proceeds as today.
  - **On a mismatch:** the temporary file and all pieces are deleted, since
    the bad bytes cannot be located, and the next Download starts fresh.
  - **If interrupted:** a crash, cancel or disk-full during the copy leaves
    the pieces intact. The stale-staging cleanup deletes the hidden
    temporary file at the next claim, as it does for `.*.tmp` today.
  - **Free space:** the pieces (S) and the temporary file (S) coexist; the
    `.bz2` and the unpacked file coexist later. The peak is
    max(2S, S + U) = S + U, because U = 1.52 GB is larger than S = 1.14 GB.
    That is what `required_free_bytes` already reserves, so it is unchanged.
- **Staging cleanup** at claim keeps the piece files, as it keeps `.part`
  today.
- **Out of scope:** more than four pieces, and other hosts.

**Tests**, using fakes via `httpx.MockTransport` that serve byte ranges from
an in-memory body:
- **Basic:**
  - 4 pieces, each requested with its exact range;
  - the four transfers overlap (the fake holds each response until all four
    requests have arrived);
  - assembly gives the exact bytes.
- **Resume:**
  - uneven piece files request only the missing tails;
  - files that are missing, complete or oversized (deleted) are handled.
- **Fallback:**
  - a 200 or a wrong-range 206 for a piece falls back to a single stream,
    with piece 1 kept as the prefix and no wrong byte written;
  - fallback when piece 1 is absent;
  - fallback racing a user cancel: the cancel wins.
- **Stopping:**
  - a user cancel during stalled headers or a stalled body stops all four
    promptly and keeps their files;
  - the same holds for the fallback single stream, the legacy single stream
    and assembly;
  - shutdown completes within its 10 s wait in each of those modes;
  - one piece fails twice: the operation fails, the siblings are cancelled
    and awaited, and the files are kept.
- **Fallback crash points:** an interruption after each step (each unlink
  of pieces 2–4, then the rename) resumes correctly, with the prefix kept.
- **Assembly crash points:** an interruption right after the `.bz2` rename,
  and after each piece deletion, succeeds at the next Download with only the
  minimum free space. It rejoins or downloads the missing pieces again.
- **An interrupted import beside partials:** a cancelled piece download,
  then an import of a corrupted archive of the right size interrupted during
  verification. The next Download keeps the partials, deletes the archive and
  resumes. Also cover a checksum failure at minimum space.
- **Assembly:**
  - an interruption during the copy, and a disk-full error during it, keep
    every piece; the temporary file is removed at the next claim;
  - a restart where space suffices only after removing that file succeeds;
  - a checksum mismatch deletes the temporary file and the pieces.
- **Legacy and progress:**
  - a legacy `.part` resumes as a single stream;
  - progress is monotonic across pieces, except for the documented drop at
    fallback.

### 2.2 Already-built range in a build request (tracked v0.43.0 record `77`; Fred, 2026-10-30)

- **`fetch.start_build`** drops ranges in `built_ranges()` from the request.
  If none remain, it raises `AlreadyBuilt`, and the API answers 422 "Those
  ranges are already built." `StarOperation.ranges` lists only the ranges
  that will run.
- **Ranges whose layers are all ready but which are missing from the
  manifest** still take the publish-only path and get their manifest entry.
- **`/status` checks `built` before the current range,** so a built range can
  never show "Building".
- **API test, through the real `POST /ranges/build` and `GET /status`
  routes while a solve holds the slot:**
  - a request of `[built Standard, Narrow]` reports Standard `built` while
    Narrow builds, and does not wait on an active solve before Narrow starts;
  - a request of only built ranges returns 422;
  - a ready-but-unlisted range is published.

## 3. Stellarity filter for processed finals (Fred, 2026-11-01)

### 3.1 Facts

- The built-in solver fails 10 corpus finals and the Veil mosaic. In the
  phase B1 benchmark run, all 11 failures were `no_match` in 6.5–15.9 s.
- **Detection today** (`native_solver/extract.py`):
  - sep extraction;
  - cuts on area, `b > 0.45`, elongation `a/b ≤ 2.5`, minimum width and the
    edge;
  - a small-PSF check;
  - then the brightest 250 by isophotal flux, spread over a 5×5 grid.
- **No upper width limit.** On the NA final, 41 detections were wider than
  8 px (up to 209 px). Nebula patches rank among the brightest because
  isophotal flux sums their area.
- **IC 1805 final:** real stars make up 37%, 41% and 54% of the brightest
  30, 80 and 250 detections.
- **Settled constraints (not to change):**
  - the solver thresholds (`ln 1e18`, three quadrants, minimum matches),
    budgets and minimum detection counts;
  - zero wrong solutions on the corpus and trials;
  - the real-sky trials build detections directly, so they do not exercise
    extraction.

### 3.2 Experiment (2026-11-01, Claude)

Results are filled in from `width_filter_exp.py`, run on the 11 failing images
and then on every final, mosaic, sub and master. The filter keeps candidates
whose width is at most `factor ×` the median candidate width. It runs before
the brightest-250 selection, so the freed places go to real stars.

**Decisive runs** (2026-11-01). The filter was injected into the benchmark's
own worker processes, so these are true `native` and `native-blind` modes.
The run covered 149 corpus images, compared per image and per mode with the
unfiltered run. Every limit had zero wrong solves and zero negatives solved.

| Width limit | native | native-blind | Gains | Losses |
|---|---:|---:|---|---|
| none | 132 | 128 | — | — |
| 4.0 (run twice, identical) | 135 | 133 | NGC 6888 crop and M81 jpg and xisf (both modes); IC 1396 and IC 443 crops (blind) | none |
| 5.0 | 134 | 132 | IC 1805 final and NGC 6888 crop (both modes); IC 1396 and IC 443 (blind) | none |
| 6.0 | 134 | 132 | the same as 5.0 | none |

- **Validation of every gain:**
  - against ASTAP: IC 1396 0.21 px, IC 443 0.51 px, IC 1805 0.51–0.54 px;
  - by a Gaia overlay: NGC 6888 median 0.13 px, M81 0.50 px, against a
    randomly shifted control of 2.8–4.1 px. M81's jpg and xisf solutions
    are identical.
- **Contamination:** in IC 1805, real stars among the brightest 30
  detections go from 37% without a filter to 90–100% at every limit from
  1.5 to 4.0. Outcomes still vary with the limit, because whether an image
  solves also depends on quad membership and verification scoring (Codex,
  round 1).
- **Earlier exploratory runs** with Claude's own harness are superseded:
  they omitted the request hint by mistake, so header hints still applied.

### 3.3 Design

- **`ExtractionConfig.max_width_ratio: float | None`.**
  - **Gate (revised after round 1, agreed with Codex):** the default stays
    `None` unless a factor clears the full bar. Of the factors that clear
    it, choose the least restrictive one that shows repeatable improvement,
    meaning the same gains on a second run.
  - **The bar:**
    - per image and per mode (`native` and `native-blind`), no image that
      solved without the filter fails with it;
    - zero wrong, and zero negatives solved;
    - every newly solved image is independently validated: against ASTAP or
      a header WCS where one exists; otherwise by a catalogue overlay of
      Gaia stars through the new solution, viewed by Claude, with a median
      offset under 2 px;
    - unverified gains are reported separately, never counted as "not
      wrong".
  - **If no factor qualifies,** the filter ships disabled. The item is
    recorded as unresolved for Fred, not as done.
  - **Result (2026-11-01):** 4.0, 5.0 and 6.0 all cleared the bar. Under
    the gate, **6.0** is the least restrictive repeatable one (two runs
    identical per image), so it is the default.
    - 4.0 had more image-mode gains, 8 against 6. Grouped by object, both
      rescue four: 4.0 rescues M81 where 6.0 rescues IC 1805.
    - Claude proposed 4.0. Codex held to the gate (record 41), and Claude
      agreed.
- **The typical width** is the median `fwhm_working` of the candidates that
  pass the existing cuts and the PSF check, before selection. It is computed
  per extraction, so it follows each image's own binning and seeing.
- **The filter** drops candidates wider than `max_width_ratio × typical`.
  It runs in every profile (index and catalog-only).
- **No other change:** thresholds, budgets and the selection rule are
  unchanged.
- **Tests:**
  - a synthetic field of stars plus wide Gaussian blobs brighter than the
    stars: without the filter the blobs fill the brightest slots; with it
    they are gone, and the field solves through `solve_image` (a real solve
    assertion, not only extraction);
  - a field of stars only keeps every star;
  - the rendered `nebula-only` negative still reaches full verification
    (all blobs share one width, so the ratio keeps them) and stays unsolved;
  - every rendered trial still passes;
  - the configuration pin test is updated for the new field only.
- **Acceptance (high-stakes, scientific):**
  - the corpus benchmark in all three modes: zero wrong, zero negatives
    solved, no image that solved before fails, and every bar line passes;
  - the 2,000/1,000 real-sky trials unchanged (they do not use extraction);
  - the rendered trials pass.

## 7. Fetch progress on the Catalogs page (Fred, 2026-11-01, acceptance test)

**Why.** Fred re-fetched Sharpless during his acceptance test. Strasbourg
and Harvard failed and the South Africa mirror served it, but the button
showed only a spinner for minutes. He asked for text saying what the fetch
is doing: connecting, downloading, trying a mirror. **Scope (Fred):** every
fetch and reload button on the Catalogs page, not only VizieR.

**Facts (Claude, from the code):**
- Each button awaits one POST that returns only when the download and the
  catalog load have both finished (`api/admin.py`: OpenNGC, VizieR, 50 MGC,
  Wikidata, the NightCrate reload and "Reload all from local cache").
- `_run_loader` runs the synchronous loader **on the event loop**. While it
  runs, no other request is served, so a status endpoint polled during the
  load would not answer.
- The four downloads read whole bodies through `http_client.get`, so no
  byte count is available while they arrive.
- The database uses the default rollback journal, and connections use the
  default 5 s busy timeout. Today the blocked event loop accidentally keeps
  every other request away from the database during a load.

**Measured (Claude, 2026-11-01, a copy of Fred's 134 MB database; journal
mode `delete`):** a load with nothing else changed takes 0.1–0.6 s; "Reload
all" (`force=True`) takes 3.1 s. The long waits are network.

**Design (converged with Codex's plan review, records `64`–`67`):**
- **One catalog action at a time.** Sharpless and Barnard share
  `vizier/.download`, which each fetch deletes first, so concurrent fetches
  can break each other today. Admission is atomic, before the first
  `await`; a second action gets 409 "Another catalog update is running.",
  and the page disables the other buttons and says why. Every explicit
  fetch and reload endpoint goes through the guard, including the
  NightCrate reload endpoint, which keeps no UI button.
- **The loader stays on the event loop** (`_run_loader` unchanged). Moving
  it to a thread would need a database-contention policy, for a few
  seconds' gain. Consequence: the status endpoint does not answer during
  the load, so the page keeps the last step until the result arrives; for
  "Reload all" the page shows "Reloading cached catalogs…" itself.
- **Progress registry** (`services/catalog_progress.py`, no FastAPI): the
  active operation's ID, action, phase, message, bytes and total when
  known, and seconds in the phase. A finished entry is kept until the next
  action or five minutes. Updates carry the operation ID and are ignored
  if it is no longer current. The entry is finished in a `finally`.
- **Status endpoint** `GET /api/admin/catalogs/fetch-status`, with no
  database access.
- **Streaming events in `http_client.get`** (opt-in): attempt started,
  response received (status, length), wire bytes (`num_bytes_downloaded`),
  retry delay. The response interface, timeouts, retry classification and
  `attempts` are unchanged. `retry_with_backoff` reports its retries.
  Counters reset per attempt and per mirror; OpenNGC sums its two files.
- **OpenNGC's two downloads are owned together** (`TaskGroup` or an
  equivalent cancel-and-drain): today, if one fails, the other keeps
  running and writes into the staging folder after it is deleted. Cleanup,
  the final outcome and releasing the guard wait for both.
- **Outcome from the targeted sources' results:** OpenNGC targets `openngc`
  and `openngc_addendum`; each VizieR fetch, 50 MGC and Wikidata target
  their own source. `loaded` or `unchanged` → success naming the source;
  `failed` → "Download saved; database update failed."; `skipped` with an
  error or `missing` → finished with warnings, with the reason. Reloads say
  "Catalog reload failed." or "Reload finished with warnings." instead.
  For a reload, a `missing` source is not a warning: it is a catalog the
  user never downloaded (Claude, Phase D review cycle 1).
- **Page:** reads the status on mount and polls about once a second while
  an action is active, so leaving and reopening the page keeps the line.
  Results from an older operation are ignored. A failed poll does not mean
  the action finished. One line under the row's caption; the live region
  announces phase changes only, not the seconds or bytes.

**Status lines** (Codex drafted; Claude checked each against the code):

| Step | Line |
|---|---|
| Accepted | Starting catalog update… |
| OpenNGC release lookup | Checking the latest OpenNGC release on GitHub… |
| OpenNGC transfer | Downloading OpenNGC files from GitHub… 2.4 of 4.1 MB |
| VizieR first host | Trying CDS Strasbourg… 8 s |
| Moving on | Strasbourg timed out. Trying the Harvard mirror… |
| Other reasons | couldn't connect / returned an error (HTTP 503) / returned no data / returned something that isn't the catalog |
| VizieR transfer | Downloading Sharpless from the South Africa mirror… |
| 50 MGC | Contacting GitHub for 50 MGC… then Downloading 50 MGC… |
| Wikidata | Waiting for Wikidata results… then Downloading Wikidata references… |
| Retry | GitHub request failed. Retrying… |
| Checking | Checking downloaded files… |
| Saving | Saving files to the local cache… |
| Loading | Updating catalogs in the database… |
| Reload all | Reloading cached catalogs… |
| Success | Sharpless loaded. / Cached catalogs reloaded. |
| Warnings | Update finished with warnings. See details below. |
| Download failed | Download failed. See details below. |
| Load failed | Download saved; database update failed. |
| All mirrors failed | No VizieR source returned usable data. |
| Conflict | Another catalog update is running. |

Seconds are shown while waiting for a reply; bytes as "2.4 MB received" or
"2.4 of 8.1 MB", with no percentage without a valid total.

**Tests** (normal, edge, failure): every action completes and reports its
steps; a VizieR run through all three hosts reports each reason in order
(real `http_client.get` over a fake transport, not a mocked `get`); gated
multi-chunk bodies report bytes as they arrive; the status endpoint answers
during a gated transfer; 409 for a second action of any kind; an invalid
source or unconfigured database leaves no reservation; retained and expired
outcomes; failed, missing, unchanged and deferred results; an OpenNGC
failure while the second download is active leaves no writes or callbacks
after the guard is released.
**Rendered check:** every button on the private test server, a real
Sharpless re-fetch while Strasbourg is down, leaving and reopening the page
mid-fetch, two tabs, a narrow layout and keyboard use.

## 8. Bugs found during v0.43.1, fixed in v0.43.1 (Fred, 2026-11-01)

**Why.** Fred: bugs found during a version are fixed in that version when
they can be, not recorded for later. These were found while building and
checking v0.43.1; all predate it.

**Fixes:**
1. **"Fetched" dates show the UTC date.** `CatalogsAdminSection.tsx` shows
   the first ten characters of a UTC timestamp (a fetch on the evening of
   2026-11-01 in Arizona shows 2026-11-02). Show the user's local date.
   Check every fetch-date label on that page.
2. **Moving the app-data folder deletes the cached sky images.** Cache rows
   store absolute `file_path`s; the startup sweep (`sync_orphan_files` in
   `services/thumbnails.py` and `services/sky_tile_cache.py`) deletes files
   whose path isn't in the table. A copied app-data folder (another account,
   a restored backup, future packaging) loses every cached image at the next
   startup (seen on a private copy, 2026-11-01: 2,941 cells). The files'
   names are already stable sky identities (CLAUDE.md "Disk caches"), so
   the sweep and the cache lookups must not depend on the folder's absolute
   location. The fix and whether it needs a migration are for the plan
   review.
3. **The image-cache budget is not shared.** The Admin page and
   `core/config.py` describe `thumbnail_cache_max_mb` as one budget shared
   by the thumbnail and sky-cell caches, but each cache's `_evict_lru`
   enforces it separately (up to twice the setting in total). "Clear All"
   clears only the thumbnail cache, and the statistics count thumbnails
   only. Make the budget, "Clear All" and the statistics cover both caches.
4. **Star-data status logs a traceback with no database set up.**
   `api/star_catalog.py` `_rig_coverage` logs a warning with traceback on
   every status poll when no database exists. With no database, return no
   rig coverage quietly; keep logging real failures.
5. **The solver's cancellation waits can log a false error.**
   `services/plate_solve.py` (`_finish_awaitable` and the ASTAP and native
   cancel loops) and `api/project_solve.py` (`_finish_awaitable`) repeat
   `asyncio.shield` on the worker itself, so in Python 3.14 each abandoned
   shield logs "exception in shielded future" if the worker later raises,
   and `_finish_awaitable` lets that exception replace the cancellation.
   Use `core/tasks.py:settle`, keeping each caller's cancel behaviour (stop
   flag, process kill, slot release only after the task ends).
6. **Switching databases during a catalog action.** A catalog fetch that
   finishes after the active database changed loads into the new one.
   Refuse database create, add, activate and setup with 409 while a catalog
   action runs (the Phase D guard), with a plain message.

**Not changed, with reasons:**
- **The catalog load blocks the server for its duration** (0.1–3.1 s
  measured): kept by design in §7, because moving it needs a database
  contention policy.
- **Harvard's degraded mirror:** external; the mirror order handles it.

**Converged design (Codex plan review, records `75`–`78`):**
- **Fix 2:** no migration. New rows store the validated filename; legacy
  absolute paths resolve by filename (POSIX and Windows spellings) inside
  the cache directory read from `app_config.APP_DIR` at call time, never
  the old location; traversal and escaping symlinks are rejected. Lookups,
  rehydration, eviction and clearing all use that identity; rehydration
  repairs a conflicting row's path and keeps its access time; the sweep
  runs only after a reconciliation with no unresolved database or file
  errors. The orphan policy is otherwise unchanged (Claude's counter;
  Codex accepted).
- **Fix 3:** one budget across both tables (combined LRU), combined
  statistics with one maximum, one "Clear All" that empties both and resets
  both failure backoffs; one lock serializes publication, eviction,
  clearing and the sweep; rendering stays outside it; a generation check
  discards a render started before a clear.
- **Fix 5:** ASTAP and native waits use `settle(task,
  on_cancel=operation.cancel)` from the first wait; the commit,
  `committed = True` and the generation cleanup run as one settled
  coroutine, so a cancelled save never deletes committed images; the
  process-exit helper keeps its delayed cancellation; shutdown keeps its
  10 s limit on a shielded non-raising waiter.
- **Fix 6:** create, add, activate and setup return 409 "A catalog update
  is running. Wait for it to finish before changing databases." before any
  side effect, only while an operation is active.
- **Fixes 4 and 1:** status returns no coverage before opening a database
  when none is configured; one browser-local date formatter for the VizieR,
  50 MGC and Wikidata rows (OpenNGC keeps its release label).

**Tests:** each fix gets normal, edge and failure tests, including a copied
app-data folder whose cached files all survive a startup sweep, a shared
budget evicting across both caches, "Clear All" emptying both, and the
solver callers' repeated cancellation with a worker that raises afterwards.

## 9. DSO catalog table sorting (Fred, 2026-11-01, acceptance test)

**Reported by Fred:**
- Clicking a column header switches ascending to descending, but not back.
- Designations sort as text: M 1, M 10, …, M 2.

**Facts (Claude, from the code and a copy of Fred's database):**
- `pages/DsoCatalogPage.tsx` uses MUI DataGrid with `sortingMode="server"`
  and the default sorting order (ascending, descending, none). On the third
  click the grid sends an empty sort model; `setSortModel` ignores it, so
  the store stays on descending.
- `api/dso.py` `list_dsos` orders by `d.<column> <dir> NULLS LAST, d.id`
  with `SORT_COLUMNS`:
  - `primary_designation`: text, so numbers sort as text;
  - `obj_type`: the type code, while the table shows a readable label;
  - `constellation`: the IAU abbreviation with case-sensitive ordering
    ("CMa" before "Cam"), while the table shows the full name;
  - `common_name`: case-sensitive (not a column in `SORT_COLUMNS` today;
    check whether the grid can sort it);
  - `ra_deg`, `dec_deg`, `mag_v`, `distance_pc` and `size`
    (`maj_axis_arcmin`): stored as REAL, so already numeric. Size sorts by
    the major axis; kept (the largest dimension drives the footprint).
- Primary designations look like "NGC 7000", "IC 1805", "M 31", "B 33",
  "Sh2-155", "ESO 107-004", "PGC 143", "Mel 101", "C 14", "UGC 4305".
- Nine addendum objects show a literal "OTHER" prefix: "OTHER HCG092"
  (Stephan's Quintet), "OTHER HCG079" (Seyfert's Sextet), "OTHER H05",
  "OTHER MWSC3561" and others. Their OpenNGC names are not parsed into a
  catalog and number.
- In a Caldwell view only 4 of 109 objects use a Caldwell primary name, so
  sorting by primary name gives C 14, C 41, C 9, C 99, then IC and NGC.

**Design:**
1. Header clicks alternate ascending and descending (no unsorted state).
2. **Designation, several catalogs or none:** order by the catalog prefix
   (case-insensitive), then the number numerically, then any remainder
   (suffix letters, ESO's second number) — "NGC 1", "NGC 2", "NGC 10".
3. **Designation, one catalog selected (Fred, 2026-11-01):** the
   Designation column shows that catalog's own name (C 1, C 2 …) and sorts
   by its number; the main name (NGC 188) moves to Alt designations. Same
   for any single catalog. Objects with several numbers in that catalog
   use their lowest.
4. Type sorts by the label shown; Constellation by the full name shown;
   Common name case-insensitively; missing values stay last in both
   directions.
5. The nine "OTHER" names are parsed properly: HCG names into the existing
   `hickson` catalog (Stephan's Quintet becomes "HCG 92"); names whose
   catalog NightCrate has no code for display their own prefix and number
   ("MWSC 3561", "H 5"?), never "OTHER". The plan review decides what H05
   is and whether any vocabulary change is needed (a migration would be a
   stop-and-ask).

**Converged design (Codex plan review, records `93`–`94`; Claude accepted
every finding):**
- **One natural designation key** (`services/dso_sorting.py`), registered
  in SQLite with `create_function` and reused in Python and the frontend
  (`lib/designationSort.ts`): display prefix first (case-insensitive, so
  M before Mel, `Sh2` recognized), then every numeric part numerically
  ("ESO 107-2" before "ESO 107-010"), then the remainder. No migration.
- **Objects without a primary designation row** (the loader skips
  unrecognized names) are kept: a left join falls back to
  `dso.primary_designation`.
- **Single-catalog view:** after de-duplicating the catalog filter, exactly
  one catalog selects each object's lowest designation in it (lowest in
  either direction) before pagination; the list response gains
  `display_designation` (keeping `primary_designation` and `is_primary`)
  and includes that catalog's aliases; Alt designations shows every other
  name, the primary name included.
- **Type, Constellation, Common name:** server-side label expressions
  mirroring the frontend maps (a parity test keeps them aligned; unknown
  codes fall back as the frontend does), case-insensitive, missing values
  last. Common name joins `SORT_COLUMNS` (sorting it returns HTTP 400
  today).
- **Header clicks:** `sortingOrder={["asc","desc"]}`; a sort change resets
  to the first page in the same update.
- **The "OTHER" names:** "OTHER" comes from `_build_display_form`
  uppercasing a synthetic code. HCG names parse to `hickson` (Stephan's
  Quintet becomes "HCG 92"); Harvard and MWSC names display as "H 5" and
  "MWSC 3561" with no new catalog code (a filter for them would need a
  vocabulary migration and Fred's decision). An idempotent repair renames
  existing rows without a re-download, preserving `source_key`, row IDs
  and user links.
- **The same text sort elsewhere:** the planner's designation sort
  (`api/planner.py`) and the plate-solve object grid
  (`PlateSolveDsoGrid.tsx`) use the natural key; search pickers inherit
  the list order.
- **Alt designations stays unsortable** (a list of names has no single
  order).
- **Duplicates found while reviewing (Claude, read-only audit of Fred's
  database; design checked in records `108`–`109`):** the Horsehead was two
  objects (OpenNGC addendum B033 and Barnard 33) and the Cave Nebula two (C 9
  and Sh2-155). A Barnard row now merges into an OpenNGC object whose parsed
  own name is that Barnard number (alternate names never merge, so B 33 and
  IC 434 stay separate); Sh2-155 gains a cross-reference to C 9. An object's
  own name now outranks another object's alternate name, which returns
  `ngc 764` and `ngc 6839` to their own objects (held by NGC 755 and M 71).
  Each has an idempotent repair trigger for existing databases. None of the
  objects had user links.

**Tests:** natural order for each prefix format above, mixed catalogs,
single-catalog views (Messier, Caldwell, Sharpless, Barnard), both
directions, pagination stability, missing values last, the label orders,
and the nine renamed objects. **Rendered check:** clicking each header

**Design (Fred chose, 2026-11-01):**
1. **Several catalogs selected:** each object shows and sorts by its name
   from the selected catalogs. When it has names in more than one selected
   catalog, the catalog order is Messier, NGC, IC, Caldwell (the
   primary-name order), then the other selected catalogs in a fixed,
   documented order; within the chosen catalog its lowest designation, as
   for one catalog. Messier + IC lists IC 1 … IC 5386, then M 1 … M 110.
   No catalog selected: unchanged (primary designation).
2. **Alternate names as pills (Fred):** the Alt designations column shows
   every other name of the object as small pills, in the same catalog
   order, natural order within a catalog, the displayed name excluded. It
   moves next to Designation so it is visible without scrolling. Pills
   that do not fit collapse into a "+N" pill; the detail panel still lists
   every name. The list response carries all designations for the rows of
   the page.
3. **Mirror messages:** a move names the failed mirror's own time —
   "Strasbourg timed out after 21 s. Trying the Harvard mirror…" — and
   the counter keeps counting the new attempt.

**Converged design (Codex plan review, records `140`–`143`; Claude accepted
every finding, Codex accepted Claude's counter on the `+N` pill):**
- **Catalog rank** lives in `services/dso_sorting.py`: Messier, NGC, IC,
  Caldwell, then every other catalog code alphabetically. With one or more
  catalogs selected, each object's displayed name is chosen among its names
  in the selected catalogs, always ascending by catalog rank, catalog code,
  natural key and `dd.id`, before pagination. The rows are then ordered by
  that name's natural key in the requested direction, then `d.id`; rank
  chooses a name and never orders rows (Messier + IC ascending is IC 1 …
  then M 1 …). One selected catalog is the same rule. Search and the other
  filters stay independent, so an unselected alias still finds the object.
  Measured by Codex in memory: about 95 ms against 34 ms today.
- **Every designation** of the page's rows ships in the list response (about
  37 KB → 53 KB per 100 rows), ordered by the same rank and natural key.
  The search pickers and the planner do not read this array.
- **Pills:** the column moves next to Designation, fixed 360 px,
  `resizable: false`, single line; at most two name pills (natural width,
  140 px maximum, ellipsis), then a `+N` pill that never shrinks; neutral
  outlined small chips in theme tokens; the displayed name is excluded. The
  hidden names are read out from visually hidden text ("3 more: …"), the
  visual `+N` hidden from assistive technology. Enter on a focused cell
  (only when the cell itself has the event) opens the detail panel, which
  lists every name; closing it returns focus to the cell. OpenNGC component
  suffixes such as "IC 80 NED01" and "UGC 02688 NOTES01" are genuine names
  and simply ellipsize.
- **Mirror durations** are measured with a monotonic clock around each
  host's complete download (both attempts and the backoff), never from the
  progress phase clock.
- **Fused names (found by Codex, verified by Claude on a copy of Fred's
  database):** two OpenNGC rows lack a comma, so IC 1166 NED01 and IC 1191
  NED01 carry "PGC 056771SDSS J160208.91+261945.5" and "PGC
  057152SDSS J160628.98+181603.9". The parser splits a PGC number followed
  directly by another catalog's name into the two names, and an idempotent
  repair fixes existing databases without a re-download.
