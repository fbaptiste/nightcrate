# v0.49.0 — Object search

Fred started this version on 2026-11-10 and shaped it in conversation the
same day. The scope is the roadmap's object search (`PLAN.md`, v0.49.0 ›
Scope, decided 2026-10-24 and 2026-10-30). Fred approved the mockup
`.superpowers/mockups/v0.49.0/search.html` (local; both themes) on
2026-11-10. Claude made the remaining choices; they are listed at the end
for his review.

## Why

Fred's words (2026-11-10):
- "Often times, a photo may have more than one object beyond just the
  primary one. Think of the Leo Triplet for example. Or maybe it's an image
  with dozens of galaxies (like Markarian chain), or even sometimes a
  prominent object, but a lot of background tiny galaxies in the image. I'd
  like the ability to know, and search, what those secondary objects are
  that I captured."
- Asked whether he'd start from a name or from a picture: "both, really —
  search by name and see it in each picture. But seeing it in the picture
  is already kind of solved by plate solving."
- What a search for NGC 3628 should show: "a list of the projects, with the
  object marked on each image."
- Where: "part of the gallery".

Today the Gallery's "Also search plate-solved projects" reads the object
list saved when a project was plate solved. That list keeps only the 500
largest objects in the field, from the catalogs present then. In a dense
field (Markarian's Chain, with the optional catalogs on) the smallest
galaxies are the first to go, and a catalog turned on later never appears.
Designations also match from the start, so "M1" finds M 10–M 19 too.

## Goals

- Type an object's name in the Gallery's search and get every project
  whose main targets include it or, when the user asks, whose plate-solved
  image contains it, however small or faint the object.
- Each result shows where the object is: its plate-solved image with the
  object ringed and named; a tiny object also gets an enlarged view.
- Each result says why it matched: main target, in the plate-solved image,
  or both.
- Designations match exactly: "M1" finds M 1, not M 10–M 19. Suggestions
  appear while typing.
- The Messier page shows which objects the user has caught in a solved
  picture without making them a project's target.

## Non-goals

- **Searching by sky position** (coordinates, or "everything within 1° of
  M 87").
- **Catalogs NightCrate doesn't load.** A tiny galaxy is found only if one
  of the loaded catalogs lists it, under any of its designations (the
  Hamburger Galaxy is also PGC 34697 and UGC 6350).
- **Pictures that aren't plate solved.** Nothing can say what's in them.
- **The DSO Catalog's and the Planner's searches.** They keep matching
  designations from the start; they are for browsing.
- **Re-solving, or changing the Plate Solve tab's object list** (see "The
  Plate Solve tab", and "Decisions for review" 7). The tab does get the
  ring-angle fix below.
- **A per-object page.** The Gallery's results are that page.

## Anti-goals (failures even if everything works)

- A mark in the wrong place: off the object, mirrored, or misaligned on a
  picture whose proportions differ from the tile's.
- "In the plate-solved image" for an object outside it, or a missing result
  for an object inside it because it is small, faint, or from a catalog
  turned on after the solve.
- A mark drawn on a picture that isn't the plate-solved one (the main image
  or a framed thumbnail).
- "M1" finding M 10–M 19 in the Gallery.
- The Gallery's search becoming noticeably slower on a large library.
- An object only in a solved picture counted as imaged on the Messier page.
- Colour alone telling "Main target" from "In the plate-solved image".
- Retired projects in results when "Show retired" is off (as today).

## Decisions

### Matching

- **One search box, as today.** The text matches:
  - project names, anywhere in the name (as today);
  - objects, through **designations exactly**: the normalised text equals
    one of the object's designations (`catalog_loader/designations.py`
    `normalize_designation`), so "M1", "M 1" and "m1" are M 1, and
    "NGC 36" is NGC 36 only;
  - objects, through **names anywhere**: the common name and the other
    names (`dso_other_name`) contain the text, case-insensitively, as
    today ("Hamburger" finds the Hamburger Galaxy);
  - groups ("part of", `dso_group`): the members of a group whose
    designation equals the text or whose name contains it, as today's
    shared clause does, with designations exact.
- **A text that is exactly a designation doesn't search project names.**
  "M1" names M 1, so a project called "M13 Hercules" doesn't appear
  because its name contains "M1". A project named after M 1 is still
  found through its main target. Any other text searches project names
  anywhere, as today.
- **Results are deduplicated by object** and then by project: a project
  appears once, whichever of its objects matched and however.
- **A project matches through an object** when the object is one of its
  main targets (`project_target`, inactive objects included, as today) or,
  with "Also search plate-solved projects" ticked, when the object lies in
  its plate-solved image (next section). Retired projects follow "Show
  retired", as today.
- **The checkbox** keeps its name, "Also search plate-solved projects".
  It stays off by default and lasts for the app session, as today
  (Claude's call; see "Decisions for review" 6).
- The Gallery's other filters and its sort apply to the results as today.
- **Only the Gallery changes.** The shared `dso_search_clause` keeps its
  prefix matching for the DSO Catalog, the Planner and the target picker;
  the Gallery gets an exact-designation variant built on the same
  normaliser.

### Which objects are in a plate-solved image

- **Worked out when searching, not read from the saved list.** For each
  project with a solve (one per project, `project_solve`), the object is in
  the image when its catalog position, projected through the stored
  solution, lands inside the image. This is the rule the Plate Solve tab
  already uses (`services/image_annotations.py` `project_dsos`): the
  object's centre within the frame enlarged by its semi-major axis, so a
  large object overlapping an edge counts.
- **One shared function** decides membership and the pixel geometry
  (centre, semi-axes, angle) for the search, the Messier page and the Plate
  Solve tab, so the three can never disagree about whether an object is
  in a picture or where.
- **No size cap and no catalog snapshot.** Every active object of the
  catalogs loaded now is considered, so a 0.4′ background galaxy and a
  catalog turned on after the solve are both found. Inactive objects
  (kept only for a user link after their catalog was removed) are not
  found in images; main targets still match whatever their state.
- **Mirror-imaged and bottom-up pictures** are handled by the stored
  solution, as in the Plate Solve tab (migration 0064 put standard images'
  solutions in top-down row order).
- **Speed:** a search must stay quick on a large library (see "Checks").
  How objects and solves are narrowed before projecting is the builder's
  call; an angular pre-filter around each solve's centre is the obvious
  one.

### What a result shows

Matching mockup: "Gallery search", examples "NGC 3628" and "IC 2729
(tiny)".
- **Marks appear only with "Also search plate-solved projects" ticked.**
  With it off, results look as they do today: the usual picture or
  framing, with the "Main target" chip. The in-image work is done only
  when the box is ticked.
- **With the box ticked, a project whose plate-solved image contains a
  matched object** shows that image, whole, instead of its usual picture or framed thumbnail. It
  is the only picture whose sky position is known. The image keeps its own
  proportions inside the 4:3 tile, on black, as the Gallery shows any
  picture.
- **Every matched object in the image is ringed and named:**
  - an ellipse at the object's catalog size and angle, a little larger than
    the object so it doesn't hide its edge, never smaller than about 9 px
    on screen;
  - the colour of the Plate Solve tab's selected object (`RIG_ORANGE`,
    `#ed6c02`), with a dark halo so it shows on bright and dark sky;
  - the object's primary designation beside the ring (12 px on screen,
    dark halo), kept inside the picture;
  - an object larger than the picture is ringed as far as the picture
    goes; its label stays inside.
- **A tiny object** (ring radius from its own size under 8 px on screen)
  also gets an enlarged view:
  - a circle about 46% of the picture's height (at most 220 px), in the
    top-left or bottom-right corner farthest from the object (the other
    corners hold the expand button and the chips);
  - it shows about five times the object's size (at least 2.5′) around
    it, ringed the same way, joined to the small ring by a dashed line;
  - the label "IC 2729 enlarged ×12" sits beside the circle;
  - it is cut from the solve's full-size rendering (4,000 px long side) so
    it stays sharp, loaded only for tiles that need it, near the viewport.
- **Chips** at the picture's bottom left, replacing today's "In image: …"
  pill:
  - "Main target" (teal, with a target icon) when a matched object is one
    of the project's main targets;
  - "In the plate-solved image" (dark, with the existing in-image icon)
    when a matched object is in the image;
  - both when both are true;
  - on small tiles and in the list, the icons alone, with the words as the
    accessible name and tooltip.
- **With the box ticked, a project matched only as a main target**:
  - not plate solved: its usual picture, the "Main target" chip, and under
    the caption "Not plate solved, so nothing is marked.";
  - plate solved, but the object lies outside the solved image: its usual
    picture, the "Main target" chip, and "Not in the plate-solved image."
- **A project matched only by its name** looks as it does today.
- **The results line** names the object when the text resolves to one:
  "3 projects with NGC 3628 Hamburger Galaxy" (an alias in place of the
  common name when there is none: "also PGC 1430330"). Otherwise the
  count alone, as today.
- **The tile's back** is unchanged.

### Suggestions while typing

Matching mockup: "While typing".
- A list under the search box, from two characters, after a short pause.
- Objects whose designation **starts with** the text, or whose name
  contains it. Each row: the matched designation with the typed part
  highlighted, the common name or another designation, and how many of the
  user's projects contain it ("3 projects"), counted the way the search
  would count with the checkbox as it is.
- **"In your pictures" first**, most projects first; then **"Not in your
  pictures"**, greyed, with "none". At most about eight rows in all.
- Picking a row (click, or arrows then Enter) puts its designation in the
  box ("NGC 3628") and searches. Escape closes the list. Enter without a
  pick searches the text as typed.
- While the list is open the results behind it are dimmed; they still
  follow the text as today.
- The list belongs to the search box for screen readers (combobox and
  listbox roles) and is usable by keyboard alone.

### Full-size viewer

Matching mockup: "Full size".
- A result showing a plate-solved image opens it full size, with the same
  rings, labels, enlarged view (when the object is still tiny at that
  scale) and chips. The title is the project's name; the subtitle
  "Plate-solved image".
- The arrows step through the results in order, each showing what its tile
  shows (marked solve image, or the usual picture).

### Ring angle (a bug found while specifying)

- **Every ring drawn today is tilted wrongly** unless the object's
  position angle is 45° or 135°. `project_dsos` returns `PA − image
  rotation`, which `DsoAnnotationOverlay` applies as an SVG rotation of an
  ellipse whose long axis starts horizontal. For a north-up picture that
  turns a north–south object east–west, and it ignores mirror-imaged
  pictures. Found by the builder check on 2026-11-10 and confirmed by
  Claude on a rendered Leo Triplet field: NGC 3628 (PA 104°) came out
  76° off, M 65 and M 66 about 90° off. It affects the Plate Solve tab
  and the Image Analyzer's Identify tab today.
- **The fix is in the shared function:** the angle comes from the stored
  solution itself, for example by projecting a point a short way along the
  position angle and measuring its direction in pixels, so rotation and
  mirroring are both right. The Plate Solve tab, the Image Analyzer, the
  Gallery and the viewer all draw with it.
- No stored data changes; nothing needs re-solving.

### The Plate Solve tab

- **Its object list is unchanged:** it still shows the objects saved at
  solve time, so a search can find an object the tab doesn't list (a very
  small one, or one from a catalog turned on later). Re-solving refreshes
  the list. See "Decisions for review" 7.
- It still uses the shared function for pixel geometry, so a ring in the
  Gallery and a ring in the tab sit at the same place.

### Messier page

Matching mockup: "Messier page".
- **A new slot marker, "In a solved picture":** the Messier object is in
  the plate-solved image of a project that isn't retired, and the slot has
  no project of its own (state `none`). Order of precedence: imaged, then
  project with no image yet, then in a solved picture, then not imaged.
- **With "Never rises":** the map box shows "In a solved picture" (the
  user has the object in a picture, which outweighs a planning hint); the
  tile shows the pill and keeps its "Never rises at …" line; each count
  stays its own.
- **The tile** keeps its not-imaged look (survey picture with the X, or
  blank) and gains a pill at its bottom left: "In {project name}", or "In
  {n} solved pictures". Clicking it opens the Gallery searching for that
  object, with "Also search plate-solved projects" ticked.
- **The map** gives the box a teal outline with a teal dot; the legend
  adds "In a solved picture" when any box has it. The box's tooltip lists
  the pictures, as boxes with projects do.
- **The progress line** adds "1 more is in one of your plate-solved
  pictures." (or "{n} more are …") when any are.
- An object in a solved picture is never counted as imaged.

### Rig view and the not-imaged ribbon (Fred, 2026-11-10, after his first look)

Fred, at his first look: small objects in a rig's field looked like "a
total blank with a dot in the middle"; he asked for the Planner's way of
showing it ("show what the image including its surroundings would look
like in the selected rig, and also add a percentage representing how much
of the field of view the object takes up"), and for a replacement for the
cross, which "interferes too much with small central objects". He approved
the rig-view mockup (`.superpowers/mockups/v0.49.0/rig-view.html`) and
chose option C, the corner ribbon, from five mocked alternatives
(`not-imaged.html`).
- **With a rig selected, every tile shows that rig's view,** centred on
  the object: the survey sky rendered across the whole field, the rig's
  orange frame fitted within 92% of the tile (in width and height), the
  object at its true size. An object larger than the field shows the part
  that fits. Without a rig, tiles are unchanged (the object's close-up).
- **Own pictures are never put in the rig view** (Fred, 2026-11-10,
  reversing the approved mockup's overlay: "if I have Own image selected,
  even with a rig selected, the rig overlay should not be used. However,
  if I have Sky image selected and a rig is selected, then yes"). With
  "Own image", the user's picture shows as it does without a rig: no sky
  around it and no rig frame. The rig view applies to survey pictures
  only: slots not imaged, and imaged slots shown as "Sky survey".
- **Coverage:** under the picture, on the type line's right, "{n}% of the
  field": the Planner's formula (`compute_coverage_pct`: the object's
  major and minor axes against the field's, the larger of the two
  percentages), rounded to a whole number as the Planner shows it. Shown
  only with a rig whose field is known and an object with a size.
- **The survey picture for a rig view** is the checklist variant at the
  view's field (`max(major, minor × 4/3) / 0.92` degrees across the
  4:3 picture's width), with its own render key; switching rigs draws new
  pictures once, through the same request queue, and the cache keeps
  them.
- **Pictures on screen come first; a switch back is quick** (Fred,
  2026-11-10: "when I change the rig, it looks like the tiles are
  generating from scratch. are they not being cached?" and "the system
  would favor images in view to render ahead of unrendered images I have
  already scrolled past - but that's not what is happening"). The server
  kept every rendered picture, but it rendered in arrival order and kept
  working through pictures for tiles already scrolled past or for a rig
  no longer selected. Now the server renders the most recently requested
  picture first, and a tile that asks again moves its picture up; the
  pictures nobody is asking for any more wait behind (they still finish
  and fill the cache). Every tile near the view tells the server about
  its picture straight away instead of three at a time. A switch back to
  a rig shows its stored pictures without rendering, and a tile never
  stays blank after a switch (a bug found here: switching away and back
  before the new pictures arrived left tiles on their numbers for good).
- **Not imaged:** a dark ribbon across the picture's top-left corner
  reading "Not imaged" replaces the cross on survey pictures of slots not
  imaged (blank tiles are unchanged). It never covers the middle; the
  top-left corner is free on those tiles (the imaged check sits there
  only on imaged ones).
- **"Sky survey", one name** (Fred, same day: the option said "Sky
  image" while the pictures said "Sky survey"): the "Imaged as" and "Not
  imaged as" options read "Sky survey"; the stored setting values don't
  change.
- **Own pictures get a border** (Fred, 2026-11-10: "when an image is a
  project's image, let's have a distinctive border around that image"):
  a teal border (the imaged colour) around the user's own picture's
  area on the tile, with or without a rig: 4 px, 3 px on small tiles,
  following the tile's rounded corners (Fred, same day, asked for it
  thicker after seeing 2 px). Survey pictures never have it.
- **The progress map jumps to a tile** (Fred, same day: "if I click on the
  capture map in the top right, it should auto scroll to the image
  corresponding to the cell I clicked"). This reverses v0.48.0's "nothing
  in the map is clickable". Clicking a box scrolls its tile into view
  below the pinned header and highlights it briefly (an amber ring that
  fades after about 1.5 s); focus moves to the tile so the keyboard can
  continue from there. The click never changes "Show" (Fred, same day:
  "when I have Imaged selected and click on a cell in the capture map, it
  switches the display to show All. It should not do that"): a box whose
  tile the current filter hides does nothing, and only boxes whose tiles
  are shown get the pointer cursor.
  The boxes stay a pointer shortcut (keyboard users reach every tile by
  Tab); the tooltip is unchanged.

## Constraints

- No migration: membership is computed, and nothing new is stored.
- No new dependency.
- One designation normaliser (`normalize_designation`); one membership and
  geometry function shared by the Gallery, the Messier page and the Plate
  Solve tab.
- Solve images come from the stored renderings
  (`GET /api/projects/{id}/solve/image/{variant}`: `thumb_sm`, `thumb_md`,
  `thumb_lg`, `full`). In the Gallery their URLs carry the workspace key,
  as the Gallery's other image URLs do, besides the solve id.
- Marks are drawn in the solve image's own pixel space (the stored
  `image_width` × `image_height`), scaled with the picture, as
  `DsoAnnotationOverlay` does; never in the rendered JPEG's pixels.
- Colour-blind safe: orange rings, teal and dark chips, each with words
  and an icon.
- The Gallery's behaviour for searches that match no object, and for
  every filter and sort, doesn't change.

## Checks the plan must include

Beyond counts and screenshots:
- **matching:** "M1", "M 1", "m1" and "M10"; "NGC 36" against NGC 36 and
  NGC 3628; an alias ("PGC 1430330"); a common name in part
  ("Hamburger"); a name shared by two objects ("Eyes": NGC 4435 and
  NGC 4438, both ringed); a group's name; a project name and an object
  matching the same text; an inactive main target; retired projects with
  "Show retired" off and on;
- **ring angles against hand-computed answers:** a north-up picture, one
  rotated 30°, a mirror image and a bottom-up FITS solution, each with
  objects at position angles 0°, 45°, 104° and 170°; then a visual check
  on real solves in the Plate Solve tab and the Image Analyzer;
- **membership against hand-computed positions:** an object at the
  centre, one just inside and one just outside an edge, a large object
  overlapping an edge, a field crossing RA 0°/360°, a field near a celestial
  pole, a mirror-imaged solution, a bottom-up FITS solution, and an object
  beyond today's 500-object cap in a dense field;
- **a catalog turned on after a solve** finds its objects without
  re-solving; one turned off stops finding them;
- **marks:** a picture whose proportions differ from 4:3 (both ways), each
  tile size and the list, the viewer, a tiny object's enlarged view in
  each corner choice, an object larger than the picture, a label near
  every edge;
- **missing renderings:** a solve whose JPEG is gone (the route's 204)
  falls back to the usual picture, with the chips and no mark;
- **suggestions:** keyboard only, Escape, Enter without a pick, counts
  with the checkbox off and on, a text matching nothing, slow and failed
  requests;
- **speed:** the search and the suggestions on the 500-project synthetic
  library with solves, for a designation, a common word ("galaxy") and a
  one-object text; the Messier page's load time against v0.48.0;
- **Messier:** precedence against imaged, project and never-rises slots;
  the pill's single and plural forms and its link; the map box, legend
  and tooltip; the progress line;
- **workspaces:** two workspaces whose projects and solves share ids show
  their own solve images;
- **the Gallery unchanged** for name-only searches, empty searches and
  every filter.

## Left to the builder

- Endpoint shapes: whether the marks ride on `GET /api/gallery` or a
  separate call, and the suggestion endpoint's name and limits.
- How solves and objects are narrowed before projecting, and any caching,
  within the speed check.
- How the Messier pill opens the Gallery with the search filled in (the
  Gallery is a persistent page, like the Planner's `object` parameter).
- Exact spacing and sizes, matched to the approved mockup.
- The test library: the synthetic workspace needs solves whose fields hold
  known objects (the mockup's three fields are a ready source).

## Decisions for review (Claude's calls)

7. **The Plate Solve tab's list stays as saved at solve time.** Fred

8. **"In a solved picture" applies only to slots with no project.**
9. **Inactive objects aren't found in images;** main targets still match.
10. **The enlarged view** appears below 8 px of ring radius and is cut from
    the full-size rendering.
11. **A text that is exactly a designation doesn't search project names**
    (from the builder check).
12. **Marks only with the box ticked;** with it off, results keep their
    usual pictures (from the builder check).
13. **"In a solved picture" outranks "Never rises" in the map box;** the
