# v0.46.0 — Gallery, part 1

Fred started this version on 2026-11-04 and skipped the spec questions ("skip
questions and proceed"). The scope is the roadmap's gallery, decided on
2026-10-24 (`PLAN.md`, v0.46.0 › Scope). Claude made the remaining choices.
Fred reviewed them with the mockup on 2026-11-04 and changed five; his
decisions are listed at the end.

**Amended 2026-11-07** after Fred's first look: the gallery uses each
project's framed thumbnails, and four smaller additions. See
[Amendment (Fred, 2026-11-07)](#amendment-fred-2026-11-07); it supersedes
the "Images" section and Claude's decision 3.

## Why

Fred wants to see his finished work across projects. Today each finished image
lives inside its own project. The Projects page has a picture view, but it is
built for managing projects:
- its cards show saved crops;
- clicking a card opens the project;
- it sorts by edit dates;
- it can't filter by object, catalog, rig or imaging date.

## Goals

- One page that shows every project with its main image whole, as it was
  finished. *(Amended 2026-11-07: each view shows the user's framing for
  its size, otherwise the whole image.)*
- Find projects by what was imaged (name, catalog, object type,
  constellation), how (rig), when (imaging dates) and status.
- Look at an image full size, or see its project's basic details, without
  leaving the page.
- Let projects record a status (Active, Paused, Complete, Abandoned). The
  field exists today but nothing can set it.
- Fix the Projects page thumbnails, which go stale when the main image or a
  crop changes (the roadmap puts this first).

## Non-goals

- **The slideshow's automatic playing.** It is part 2, the next version,
  under the rules already in the scope: play and pause, timing, and pausing
  on hover. It builds on this version's full-size viewer, which already
  steps through the results (Fred). The throwaway packaging test moves
  with it.
- **The rest of the roadmap's object search.** This version's search box can
  include objects in plate-solved images (Fred). The later object search
  keeps:
  - exact designation matching;
  - membership computed from the solve at query time rather than the stored
    list;
  - showing the solve image with the object marked.
- **Integration filters and sorts.** They wait until manual and derived
  sessions can no longer count the same subs twice (roadmap, "Later").
  - The back of each card does show the project's total integration
    (Fred). It is the same number as the project page's, with the same known
    limitation.
- **Re-rendering.** No new renditions, and no refresh when a file changes on
  disk. Renditions are made when an image is added, as today.
- **Editing projects from the gallery.**
- **The Messier checklist.** It is a later roadmap item.

## Anti-goals (failures even if everything works)

- An imaging date that isn't a capture session date, or a guessed date for a
  project that has none.
- A finished image cropped or stretched to fit a tile. (Amended 2026-11-07:
  a crop the user framed is intended; a stretch or a crop they didn't choose
  is still a failure.)
- A project hidden because a catalog it was imaged from was removed.
- A turned card that leaves focus on the hidden side or reads both sides to
  a screen reader.
- The Projects page still showing the old picture after the main image
  changes.

## Decisions

### The page

- **A new Gallery page** at `/gallery`, with a nav item after Projects.
  - The Projects page stays as it is, apart from the thumbnail fix.
  - **Why:** the two pages answer different needs. Projects is for working
    on a project: clicking opens it, and its cards use crops. The gallery is
    for looking at images: clicking turns the card over.
- **The page stays mounted** after its first visit, like the Planner and the
  DSO Catalog, so scroll position, filters and turned-over cards survive
  opening a project and coming back.
  - It refetches its data each time it becomes visible, keeping turned
    cards that still exist.
  - It keeps its own scroll position.
  - Filters last for the app session; they aren't saved.
  - The chosen view is saved in a setting, `gallery_view` (`list`, `small`,
    `medium` or `large`; default `medium`).

### Which projects appear

- **Every project** (Fred).
  - A project without a main image gets a card whose mat says "No main
    image". It can be turned over but has no expand button.
- **Projects without targets** appear, without target names (scope).
- **Retired projects** are hidden unless "Show retired" is on (scope). When
  shown, a retired card says "Retired" in text, not just by fading.

### Views

- **List:** a 180 px wide image beside the details (see "What a card says"),
  with the status pill beside the name.
  - The project name opens the project.
  - The image's only control is its expand button.
  - Rows are at most 980 px wide.
- **Grids:** small, medium and large tiles, at least 180, 300 and 480 px
  wide. Each tile grows evenly so that every row fills the width, with 16 px
  gaps. The content is at most 1,600 px wide, because Fred caps widths on
  wide monitors.
- **The tile's image area is 4:3 with the whole image inside it,** centred on
  a black mat. A tall or square image has mat at its sides.
  - **Why:** most finished astrophotos are landscape, and a mat never crops.
    A justified layout, with each image at its own width, was rejected as
    more complex than a gallery of a few hundred images needs.
- **Below each tile's image:** the project name and the target names, each
  on one line, ending in an ellipsis if too long.
  - A small outlined label follows the name for Active, Paused and Abandoned
    projects, and "Retired" for retired ones.
  - Complete projects get no label (Fred: "remove that Complete label").
  - Paused is orange; Active, Abandoned and Retired are grey. The words carry
    the meaning.

### Images

*Superseded on 2026-11-07 for projects with a framed thumbnail; see the
amendment. Projects without one still show the whole image as below.*

- **The whole main image, from its existing renditions:** `thumb_sm` (180 px),
  `thumb_md` (400 px) and `thumb_lg` (800 px), aspect preserved. Custom crops
  are not used.
  - **Why:** crops are square or 4:3 previews made for project cards, and the
    gallery shows images as finished.
- **The page picks the rendition:** the smallest one that covers the tile's
  actual width at the screen's pixel density. For example, a 2× screen
  showing a 346 px tile gets the 800 px rendition. `srcset` width
  descriptors would be wrong for portrait images, whose 800 px rendition is
  400 px wide.
- **Browsers don't cache project images,** so the server always decides the
  picture. The images are small, local and loaded lazily.
  - URLs carry a workspace key, renewed whenever a workspace is opened, and
    Projects thumbnails also carry a version made of crop generation ids.
    An open page therefore notices a changed picture or workspace.
- **Images load as they near the screen,** with an IntersectionObserver as in
  the Planner's thumbnails. Native lazy loading is unreliable inside nested
  scroll areas.
- **A missing rendition** (the endpoint answers 204) shows the mat with the
  words "No preview". The card can still be turned over.

### Turning a card over (scope; the back click is Fred's)

- **In the grids, the image is a button** labelled "Show details for
  {project}".
  - Activating it turns the card over: a 400 ms turn about the vertical
    axis.
  - With reduced motion requested, the sides swap without turning.
  - Enter and Space work, as on any button.
- **Only the image turns** (Fred). The caption stays below it.
  - The back covers the image area and shows the card's details (see "What
    a card says").
  - It has no project name, because the caption already shows it (Fred).
  - The status is a pill at its top right (Fred), followed by a "Retired"
    pill when the project is retired.
  - "Open project" sits in a footer that is always visible.
  - **Targets on the back take at most two lines** (Fred): as many names as
    fit, then a "+N" pill for the rest. Hovering the pill lists them. In
    the large grid more names fit, so the pill appears less often.
  - With targets at two lines, rigs at one, and the shorter date range, the
    back fits at a 300 px tile.
  - If it still can't (a narrower tile or larger text), the details scroll
    inside the back without a visible scrollbar. Their bottom edge fades
    while there is more below.
  - **Clicking anywhere on the back turns it back** (Fred), except on "Open
    project", which opens the project.
  - For keyboard and screen-reader users, a button covering the back, behind
    its text, does the same; it is labelled "Show image for {project}".
  - Esc also turns the card back while focus is on it.
  - In the small grid the back shows the imaging dates, the rigs (Fred) and
    "Open project".
- **The hidden side is `inert`,** so it is out of the focus order and hidden
  from screen readers. After a turn, focus moves to the button of the side
  now showing.
- **Cards turn independently.** Several can be turned over at once. A change
  of view or filters turns them all back to the image.

### Full-size viewer (Fred)

- **Every image has an expand button,** in the grids and the list. It is a
  round button in the image's top-right corner, labelled "View {project}
  full size".
  - It is always visible, because tablets have no hover.
  - It doesn't turn the card.
  - Projects without a main image have none.
- **It opens a full-window viewer:**
  - a black background;
  - the image's `full` rendition (up to 4,000 px on its long side), fitted
    to the window;
  - the project name and target names underneath;
  - a Close button.
- **Moving through the results** (Fred):
  - a left and a right arrow sit at the middle of the window's left and
    right edges, outside the image;
  - **the arrows never move** (Fred). They are placed against the window,
    not the image, so the image's size or shape, the caption's length, and
    reaching the first or last image never shift them. You can keep
    clicking without moving the pointer, and the Close button and counter
    stay put too;
  - the ← and → keys do the same;
  - they step through the current results in their current order,
    skipping projects without a main image;
  - at the first and last image the matching arrow is dimmed and does
    nothing, without wrapping;
  - a counter at the bottom right says where you are, for example "3 of
    12";
  - the full-size images either side of the current one load in advance.
- **Closing:**
  - Esc and Close close it.
  - Focus returns to the expand button of the image last shown, scrolled
    into view, which may not be the one opened.
  - It also closes if the page is left, because the gallery stays mounted
    while hidden, or if the image shown drops out of the results.
- **While loading,** the viewer shows a progress indicator. A missing file
  shows "Couldn't load the full-size image."

- **Description gets a heading,** styled like "Main targets", with the edit

  - The text lines up with the heading.
  - When there is no description, a slim dashed box reads "Add a

  - The Notes tab gets the same heading ("Notes") and empty box ("Add

**Imaging dates** come only from `project_session.session_date`, manual and
derived rows alike (the roadmap rule). A value counts only when its first ten
characters are a valid `YYYY-MM-DD` date, so a manual note typed into the date
field is never taken as a date. Edit, creation and file dates never stand in.

### Filters

All filtering and sorting happen on the server. Different filters combine with
AND, and the choices within one filter combine with OR.

- **Search** (explained to Fred and confirmed, 2026-11-04). It updates about
  a third of a second after typing stops, and combines with every other
  filter. A project matches when either is true:
  - **its name contains the text,** ignoring capitals: "rosette" finds
    "Rosette, two seasons";
  - **one of its main targets matches,** exactly as in the DSO catalog's
    search (`dso_search_clause`):
    - **designations** match from the start, ignoring spaces and capitals.
      "M31", "m 31" and "NGC224" all find a project targeting M 31. "M1"
      finds M 1 and also M 10–M 19 and M 100–M 110, narrowing as more is
      typed (Fred kept this over exact matching);
    - **names** match anywhere in the name: "andromeda" finds the Andromeda
      Galaxy, and "veil" finds NGC 6992, the Eastern Veil Nebula;
    - **group names** match too: "stephan" finds a member of Stephan's
      Quintet.
  - **with "Also search plate-solved projects" ticked** (Fred's wording; off
    by default), also when an object in a plate-solved project's image
    matches, by the same designation and name rules.
    - The objects are the ones stored when the project was solved: at most
      the 500 largest in the field, from the catalogs present then. An
      object from a catalog added later, or a small one in a very crowded
      field, is missing until the project is solved again.
    - A project that matches only through its image shows why: a marker in
      the image's bottom-left corner, "In image: M 32" (and "+N" when more
      objects matched).
  - **Not searched:** project descriptions and notes, rig names (they have
    their own filter) and file names.
  - **Layout:** the search box has its own line, 420 px wide with a
    magnifier, and the checkbox beside it. The five pill filters are on the
    next line. Like the filters, the checkbox lasts the app session.
- **Catalog, Object type, Constellation, Status and Rig:** pill filters
  (`PillFilter`), each option with a project count.
  - Each filter's counts reflect every other active filter, but not its own,
    as in the DSO catalog.
  - An option with no projects is hidden unless it is selected.
  - **Catalog** matches through any designation of a main target, using
    `dso_catalog_clause`.
  - **Object type** is by group (`TYPE_GROUPS`: Galaxy, Emission Nebula, Open
    Cluster…), as the scope says, not by raw catalog type.
  - **Rig** uses the same rigs as the card.
- **Imaged between:** From and To dates, either of which may be empty.
  - A project matches when at least one of its imaging dates is in the range,
    both ends included.
  - Once either date is set, an "Include projects without imaging dates"
    checkbox appears, off by default (scope).
- **Show retired**, and **Clear filters**.
- **Removed catalogs:** a target whose catalog object is no longer active
  still matches every filter. The target is the user's record; removing a
  catalog must not hide a project.

### Sorting

- Choices: **Latest imaging date** (the default, newest first), **First
  imaging date** and **Name**, with a direction toggle.
- Projects without imaging dates come last in both directions (scope).
- Ties are broken by name, then project id.

### The endpoint

- **`GET /api/gallery`** has its own router; a route under `/api/projects`
  would be caught by `/{project_id}`.
- **One response holds everything:**
  - every matching card, with no paging;
  - the facet counts;
  - the number of projects before any filter, retired included, which tells
    "no projects yet" apart from "nothing matches".
  - **Why no paging:** a card's data is small and images load lazily, and
    paging would complicate the grids and keyboard order.
- **Each card carries:**
  - the project's id, name, status and retired flag;
  - its main image id, or none;
  - its targets: dso id, preferred name, other names and designations;
  - its first and last imaging dates and number of nights;
  - its total integration in minutes;
  - its rigs: id and name.
- **Speed:** with the synthetic library (below), the endpoint answers within
  200 ms on the development machine. This is measured, not asserted in
  tests.

### The Projects page thumbnail fix (scope; details after Codex's review)

The Projects page builds thumbnail URLs with the project's `updated_at`. That
time doesn't change when the main image or a crop changes, so the browser keeps
the old picture for up to an hour. Also, a crop that follows the main image
keeps the old main image's picture after a new main is chosen.

- **The URL changes whenever the picture it serves changes.** That covers a
  new main image, a crop saved or removed, and the main image removed.
  - Each crop save makes a new generation, a new row with its own file, so
    the version never rests on file times.
  - Crops saved before this version keep working. *(Superseded on
    2026-11-07: migration 0068 deleted them, and the old-name fallback was
    removed.)*
- **When the main image changes, or is removed,** crops that follow the main
  image are deleted, both the row and the file. The card then shows the new
  main image whole until a new crop is saved.
  - **Why:** the old crop's fractions were chosen for a different picture.
  - Crops that name a specific image are unaffected while that image exists.
- **Removing an image deletes the crops that name it.** Today the database
  quietly turns them into crops that follow the main image, keeping
  fractions chosen for another picture (found by Codex).
- **Saving a crop is all or nothing.** If the cropped file can't be made
  (for example, its source drive is offline), nothing changes and the page
  reports why. Today the new crop is saved while the old picture stays.
- **Browsers no longer cache project images.** Today renditions are cached
  for a day under URLs of database ids only, so a workspace switch can show
  the other workspace's pictures.

## Constraints

- **No migration.** The setting needs only a default in `core/config.py`.
- The gallery's filtering logic is a pure service; the router does the
  loading and HTTP work (`CLAUDE.md` boundaries).
- Colorblind-safe colours, and text wherever colour carries meaning. Use
  theme tokens; any hex colour has six digits.
- Chip-style filters keep `readOnly` inputs, so a tablet doesn't raise its
  keyboard.
- Tablet: tap turns a card, and there are no hover-only actions. Other names
  are a hover extra; they are also on the project page.
- **The synthetic library:** a test fixture with about 500 projects, covering:
  - targets across catalogs, types and constellations;
  - every status, plus retired projects;
  - declared and session-only rigs;
  - manual and derived sessions, with valid dates, no dates and non-date
    text;
  - projects without a main image or without targets;
  - targets on inactive catalog objects.

  A matching script builds a scratch workspace with images of several shapes
  for the rendered check.

## Amendment (Fred, 2026-11-07)

After his first look at the built gallery, Fred asked for five changes. Four
are in this version; the fifth is recorded as the next version.

### Why

Fred: "I want the users to be able to define how they want their images
displayed in the gallery. That was the whole reason for defining the
customizable thumbnails." The gallery ignored them.

### Framed thumbnails (Fred)

- **One framing per size, chosen by the user.** Fred: "I want user to define
  a custom area of the image for each sized view."
- **All three sizes are 4:3** and shared by both pages (Fred chose this over
  separate square Projects framings). Which views use which size is
  Claude's call:

  | Size | Gallery | Projects page |
  |---|---|---|
  | Small | List view and small grid | Compact |
  | Medium | Medium grid | List (expanded cards) |
  | Large | Large grid | Pictures |

  The Projects page's square boxes become 4:3: compact 76×57 px and
  expanded 160×120 px.
- **A frame may extend onto a black mat** (Fred), so a portrait image can
  fill a 4:3 tile with black at its sides. The limits are Claude's call:
  - the editor's canvas is the **fit box**, the smallest 4:3 rectangle that
    holds the whole image, centred on it;
  - the frame stays inside the fit box, so its largest size is the whole
    image with its mat;
  - the frame must include part of the picture.
- **Where there is no framing for a size,** both pages show the whole image
  on black, as the gallery does now.
- **The full-size viewer** shows the image the tile was framed from: the
  framing's source image, otherwise the main image. That is Claude's call.
- **Sharp enough for the gallery** (Claude's call): files are saved at
  480×360, 800×600 and 1200×900. These cover typical tile widths at 2×
  pixel density. The old 180, 400 and 280×210 files would look soft.
- **Existing framings are cleared** (Fred), for two reasons:
  - most are distorted by the bug below;
  - small and medium were framed as squares.

  Projects show the whole image until they are framed again.

**Bug found while planning (fixed by this).** The editor kept each frame's
shape in the image's proportions instead of its pixels. The server then
resized the area to a fixed size, so most saved framings are squashed.

| Project | Image | Saved framing | What was stored |
|---|---|---|---|
| 2 | 800×403 | "square" small framing, 0.918 × 0.918 of the image | about 2:1 in pixels, squeezed into 180×180 |
| 3 | 3:2 | large framing, the whole image | 3:2 squeezed into 280×210 |

Both rows are Fred's data, read-only, on 2026-11-07.

### The editor (Claude's calls)

- A black 4:3 canvas showing the fit box, with the image in it and a faint
  outline where the mat begins.
- The frame is always 4:3 in real pixels.
- **Reset** returns to the whole image. So does choosing another source
  image, because the old frame belonged to a picture of another shape.
- **Input:**
  - mouse, touch and pen, without the page scrolling or zooming during a
    drag;
  - arrow keys move the frame, and + and − resize it.
- **Saving:**
  - only the sizes changed are saved;

### Plate-solve focal length (Fred)

- The Plate Solve tab's result shows a calculated focal length.
- **Formula:** focal length (mm) = 206.265 × pixel size (µm) ÷ pixel scale
  (″/px). Example: 3.76 µm pixels at 0.775″/px give 1,000.7 mm, shown as
  "1,001 mm".
- **Pixel size** (Fred): from the camera of each rig on the project. Those
  are the rigs set on the project plus the rigs its sessions name, the
  gallery's single list.
- **What is shown:**
  - one line per rig, with the rig's own focal length beside it for
    comparison;
  - a short note that drizzled, binned or resized images give a multiple of
    the true value;
  - nothing for a project without a rig or a solved pixel scale.
