# v0.47.0 — Rigs keep their history, project setups, project software

Fred started this version on 2026-11-07, after merging v0.46.0. The scope is
the roadmap item he placed next that day (`PLAN.md`, v0.47.0 › Scope), plus
three additions he made while discussing it: a project's own changes to a
rig, software versions with the software used on each project, and SyQon's
programs. Decisions marked **(Fred)** are his; the rest are Claude's calls,
listed at the end for his review. A fresh review of the first draft against
the code changed how earlier setups and project changes are stored; the
behaviour Fred agreed is unchanged.

## Why

Projects, nights, frames and source folders point at a rig, and a rig
points at its equipment. Nothing about the equipment is stored with the
records. Pixel scale, star sizes in arcseconds, full-scale ADU and the
plate-solve focal-length estimate are computed on every read from the rig's
*current* telescope configuration and camera (`api/ingest.py:113-117`,
`:1582`, `:1644`; `api/project_solve.py:151-199`;
`sub_frame.pixel_scale_arcsec` is never written). Swapping a rig's camera
therefore changes every older project that used it. Fred: "it should not."

Software appears in one place: a list on each rig (`rig_software`). Nothing
records what a project was processed with, or which version.

## Goals

- A rig change can be a correction, which applies everywhere, or a real
  change, which leaves older work as it was.
- A project shows the full setup it was shot with, on the project page.
- A project can change a rig for itself, without changing the rig.
- Software has versions, and a project records the software, and the
  versions, used on it.
- SyQon's four programs are in the software list.

## Non-goals

- Reading capture software or versions from file headers into records.
  Headers keep showing them as text (`services/fits_header_map.py:125-129`).
- Versions for rig software. Capture programs update often, and their files
  already record the version.
- Dates asked from the user, per-night project changes, or a timeline of a
  rig's setups outside the projects that used them.
- Detecting a rig change from file headers.

## Anti-goals (failures even if everything works)

- An old project's pixel scale, star sizes or focal estimate changing after
  a "from now on" change, including after a rescan or a folder re-tag.
- A rig appearing twice in pickers, the gallery filter or the Rigs page
  because of its history or a project's change.
- A dialog on every rig edit. Only equipment changes on a rig that has been
  used ask anything.
- Darks or flats from one camera matched to lights from another, on a
  tagged rig. *(Amended at candidate preparation, 2026-11-08: frames from
  untagged folders have no rig, so their camera can't be told apart and
  they still match by settings alone, as before; tracked as v0.47.0-R2.)*

## Decisions (Fred, 2026-11-07)

1. **Changing a rig in use asks one question, with no date:** apply the
   change to existing projects, or only from now on.
   - *Existing projects too*, for a mistake such as wrong filters or a wrong
     image train: the change applies everywhere, after showing how many
     projects and nights it affects.
   - *From now on*, for a real change such as a new camera: what's already
     in NightCrate keeps the old setup, and what's cataloged later gets the
     new one. A project imaged across the change shows both setups, each
     with its nights.
   - Accepted cost: old files cataloged after the change get the new setup
     and are fixed by hand.
   - Name and notes edits never ask.
   - Fred rejected asking for a cutoff date: "probably too complicated…
     let's keep it simple."
2. **The project page shows each rig's full setup**, not just its name,
   without going to the Rigs page.
3. **A project can change a rig for itself only.** Fred's example: a guide
   scope tried instead of the rig's usual OAG. Only the swapped parts differ;
   later changes to the rig still reach the project, except those parts.
4. **Editing an equipment record's own specs**, such as a camera's pixel
   size, is a correction. It applies everywhere and says which rigs and
   projects it affects.
5. **Software versions.** Each program can hold zero or more versions,
   entered by the user.
6. **Software on projects.** A project lists the software used on it, each
   optionally with one of that program's versions.
7. **Rig software is typically capture and control software** (N.I.N.A.,
   SharpCap). Processing software (PixInsight, SyQon Studio) belongs to the
   project. Both pickers offer every program: the rig picker lists capture
   and control software first, the project picker processing first.
8. **SyQon's programs:** SyQon Studio, Parallax, Axiom and DeepPrism.
9. **Rejected earlier** (2026-11-07): copying rig values into each project.
   It covers projects but not nights or frames, and repeats equipment
   details, so corrected specs never reach them.
10. **Design for users in general.** Fred: "this is for users in general -
    my specific usage and quirks are irrelevant."

## Design

### The principle

A rig keeps one identity: its id, name, default flag and order. Everything
that points at a rig keeps pointing at it. Calibration matching, the gallery
rig filter, every rig picker and rig names therefore work as today. A rig's
history is a list of **earlier setups** attached to it. A project's own
changes are **swapped parts** attached to that project and rig.

### When a rig counts as in use

Any `project_rig`, `project_session`, `session`, `sub_frame` or
`project_source_folder` row points at it. Wishlist plans (`target_plan`) and
the planner's rig settings look forward, so they don't count, and they always
use the current setup.

### What asks

A change to the telescope configuration, camera, filter wheel or its slots,
single filter, mount, focuser, OAG, guide scope, guide camera, computer or
software, on a rig in use. Name, description, notes, default and order save
directly, as does any change to a rig not in use.

### The prompt

After Save in `RigFormDialog`, when the change asks:

> **This rig has been used on 4 projects (37 nights).**
> Apply the change to them too, or only from now on?
>
> [Apply to existing projects] [From now on] [Cancel]

Each button says what it does in one line beneath it: "For a mistake: the
existing projects change too." and "For a real change: existing projects
keep the old setup." Cancel returns to the form with the edit intact.

### From now on

In one transaction:
1. Copy the rig's current parts, filter slots and software into a new
   **earlier setup** (`rig_setup`), with `until_at` = now.
2. Stamp it on every frame and capture batch of the rig that has no
   setup for this rig yet. Rows already stamped with an older setup keep
   it. A frame from an untagged folder counts as on the rig when the
   project has only that rig, as capture batches already assume.
3. Apply the edit to the rig.

Frames cataloged later get no stamp, which means the rig's current setup.
Projects, folder tags, wishlist plans and settings are untouched.
*(Amended after Codex's plan review, 2026-11-07: a frame keeps one stamp
per rig, so a frame moved to another rig, which is then changed, and moved
back keeps its first rig's setup; untagged frames in a one-rig project are
stamped so their batches keep the setup through re-derives.)*

### Existing projects too

Apply the edit to the rig. In each of the rig's earlier setups, replace a
part only where it still has the rig's old value. Example: the filter slots
were wrong all along, and the camera was swapped "from now on" last month.
Fixing the slots fixes them in last month's earlier setup too; fixing the
new camera leaves the old camera in that setup alone. The prompt's counts
include nights on earlier setups.

### Ingest and rescans

`assign_rigs_and_sessions` (`services/ingest_sessions.py:181-254`) keeps
assigning `sub_frame.rig_id` from folder tags, longest prefix first, as
today. Setup stamps are never cleared by it. A stamp applies only while the
frame is on that setup's rig: re-tagging a folder to another rig moves its
frames to that rig's current setup, and re-tagging it back restores their
stamps.

Derived capture batches (`services/session_derivation.py`) group by setup
as well as rig, and carry the stamp.

### The effective setup

For a frame or capture batch, each part comes from:
1. the project's swapped part for that rig, if any;
2. else the stamped earlier setup's part, if the frame is on that setup's
   rig;
3. else the rig's current part.

This applies wherever records use equipment:
- pixel scale and star sizes in arcseconds (`api/ingest.py:113-117`,
  `:133-138`, `:1644`);
- full-scale ADU (`api/ingest.py:1582`);
- the plate-solve focal estimates, one row per setup the project used
  (`api/project_solve.py:151-199`);
- the project setup panel;
- the calibration views (`DB_SCHEMA_DDL.sql:2178-2234`). Darks and bias also
  compare the effective camera; flats compare the effective camera and
  telescope configuration. Matching stays per project and rig.

The rig calculators, planner, star-catalog coverage and wishlist use the
rig's current setup, as today.

### Fixing by hand

In the project's Sessions tab, a night whose rig has earlier setups shows
which setup it is on and can be moved to another. Moving it re-stamps its
frames. A manual capture batch has the same choice in its dialog. This is
how old files cataloged after a change are put right.

### Earlier setups

- They never appear in rig pickers or as rigs on the Rigs page. The Rigs
  page detail panel lists them under the rig, with their dates and how many
  nights use each.
- They read "until 7 Nov 2026".
- **Correct this setup**, from the project panel or the Rigs page, edits an
  earlier setup directly. It applies to every project on that setup, with
  no prompt.
- Seed updates to a pre-defined smart-telescope rig change only its current
  setup.

### The project setup panel

On the project Overview, each rig chip opens a panel below the content,
with a close button (the pattern at `RigsPage.tsx:354-368`). It shows each
setup of that rig the project used, newest first, with its nights:
- telescope and configuration, with focal length and f-ratio;
- camera and sensor, with pixel size;
- image scale and field of view;
- filters: the wheel's slots or the single filter;
- mount, focuser, guiding (OAG, or guide scope and guide camera), computer;
  the guider (OAG or guide scope) and the guide camera are separate parts,
  so swapping the OAG for a guide scope leaves the guide camera following
  the rig (mockup screen 3);
- the rig's software.

Swapped parts are marked "for this project", for example "Guide scope
instead of OAG, for this project". A rig the project lists but has no
nights on yet shows its current setup. Rigs the project's nights used but
the project doesn't list appear under the Rigs field as "Also used on this
project's nights:" chips, which open the same panel *(amended after
Codex's plan review)*.

Actions:
- **Change for this project only**: the rig's parts, editable, with changed
  parts marked;
- **Edit rig**: the normal rig form, with the prompt;
- **Undo the project change**, when the project has swapped parts;
- **Correct this setup**, on an earlier setup.

One new read endpoint returns every setup a project uses, with its parts
resolved and its night count, instead of one request per part as
`EquipmentTab` makes.

### Swapped parts

- Stored per (project, rig): typed, foreign-key-checked rows for single
  parts, and child rows for swapped filter slots and software. A part
  counts as swapped only while it has a row.
- Setting a part back to the rig's value removes its row; removing every
  row is the undo.
- They apply to all of the project's nights on that rig, whatever their
  setup. Rig corrections and "from now on" changes never touch them.
- Deleting the project deletes them.

### Equipment record edits

The edit dialogs for cameras, sensors, telescopes, telescope configurations,
filter wheels, filters, mounts, focusers, OAGs, guide scopes and computers
show, when the record is in use: "Used by 2 rigs and 5 projects. The change
applies to all of them." There's no prompt and no split.

### Software versions

- A program's entry in Equipment gets a **Versions** list: add, rename,
  remove. Versions are free text, unique per program, listed newest added
  first. `SoftwareList`'s detail panel shows them.
- They are saved outside the equipment factory's column lists
  (`api/equipment_factory.py:178`, `:261-276`), with their own save, like
  `interface_junction`.
- A version used by a project can't be removed; the message names the
  projects.

### Software on projects

- A **Software** picker beside Rigs on the project Overview
  (`ProjectMetadataSection`). Each chosen program can then take one of its
  versions, or none.
- The same program may appear more than once with different versions, but
  not twice with the same version (or twice with none).
- Retired programs and versions stay visible on projects that use them.
- A version can be added from the project picker without leaving the page.

### Picker order

Both pickers group by category, ordered by a category rank and then by
name. This also fixes the repeated group headers caused by `ORDER BY name`
(`api/rigs.py:556-564`).
- Rig: capture, guiding, plate solving, planetarium, utility, other,
  processing.
- Project: processing first, then the rig's order.

### Bugs found while designing

Fixed in this version (Fred, 2026-11-01: bugs found during a version are
fixed in it):
- **A cloned rig is invisible.** `clone_rig` leaves `is_mine = 0`
  (`api/rigs.py:856-879`; `create_rig` sets it, `:660`), and every picker and
  the Rigs page list only owned rigs.
- **The project rig picker drops retired rigs.** It shows only active, owned
  rigs and saves only those (`ProjectMetadataSection.tsx:48`, `:76`). The
  folder-tag select and the Sessions tab's rig list have the same blind spot
  (`ProjectCatalogTab.tsx:408`, `ProjectSessionsTab.tsx:76-79`). Retired
  rigs a project already uses stay listed, marked "(retired)", as the
  Location picker beside it does.
- **Editing a manual session on a retired rig clears its rig**
  (`SessionFormDialog.tsx:109-112`, `:140`).
- **The software picker repeats category headers** (above).
- **A seed row named like a user's own row stops startup.** The insert
  fails on the unique name and the loader raises
  (`seed_loader/loader.py:292-298`), which startup doesn't catch
  (`main.py:61-65`). Skipping the row isn't enough: its children then fail
  their lookup (`loader.py:101-108`). The seed's children link to the user's
  row instead, which is left unchanged, and the loader logs it. This covers
  manufacturers and programs, the tables this version seeds. Other tables
  keep failing loudly: linking a user's own telescope would collide with
  its configurations, which needs its own design *(amended after Codex's
  plan review)*.
- **The Rigs page reorder** writes to the wrong cache key, so the new order
  shows only after a refetch (`RigsPage.tsx:125`).

### Filter colours (Fred, 2026-11-08)

*Amendment before the acceptance test.* Fred asked why only Hα, OIII and SII
had colours (SII in blue, though it is the reddest) and for a palette for
every filter he can tell apart, using the Okabe-Ito palette. He approved the
mockup `filter-colours.html` (local): "colors look good, please implement".

- Colour follows wavelength. Light / dark: B `#0072B2` / `#1A7EBE`, OIII
  `#56B4E9`, G `#009E73`, R `#E69F00`, Hα `#D55E00`, SII `#CC79A7` (the
  last four the same in both themes); L `#2C2C2C` / `#E2E0DD` (a mid grey
  was indistinguishable from G for green-weak vision).
- Hβ, OI and NII take their neighbour's colour (OIII, R, Hα) with stripes;
  no filter, UV/IR cut and light-pollution filters take L's colour with
  stripes; anything unknown is a grey outline (`#8E8C88`).
- A filter with several lines (from its equipment record) is split between
  its lines' colours, red first (Fred, 2026-11-08, to match the
  red-to-blue listing): two lines diagonally, three or more in equal
  parts.
- Filters are listed L and the other whole-spectrum filters first, then
  R, G, B, then narrowband lines from red to blue (SII, NII, Hα, OI, OIII,
  Hβ), then unknown names alphabetically; a filter with several lines sits
  with its reddest line (Fred, 2026-11-08, after seeing it built). The
  "Captured subs by filter and exposure" table uses the same order.
- The colours appear wherever a filter is named with a mark: the Sessions
  chips, rows and filter-mix bars, the Overview's Integration bars, and
  the Files tab's filter chips and Filter column. The name is
  always shown beside the colour.
