# v0.50.0 — XISF specification update

Fred started this version on 2026-11-11. The scope comes from `PLAN.md`
(v0.50.0 › Scope, decided 2026-10-30): review PixInsight's updated XISF
specification against NightCrate's clean-room reader
(`services/xisf_io.py`), and fix what it affects. Fred decided two questions
on 2026-11-11. Claude made the remaining choices; they are listed at the end
for his review.

The source is the published *XISF Version 1.0 Specification*, revision 2
(document version 1.02, October 2026). Section numbers below refer to it.

## Why

PixInsight revised the XISF 1.0 document twice in 2026 and kept the format
version. Revision 1 (1.01, September) added the `AstrometricSolution`
namespace, the Zstandard codecs and mandatory checksum verification, and
fully specified the compressed-block format. Revision 2 (1.02, October)
stores incompressible subblocks unmodified. PixInsight 1.9.5 and 1.9.6
already write files this way.

Fred, 2026-11-11: "Some of them I saved just now with the latest version of
PixInsight. No idea if this means they are now in the latest version of xisf
or not." They are. Every file still declares `version="1.0"`, which is
correct.

What Fred's test files showed (2026-11-11):
- **Compressed files from PixInsight 1.9.6 don't open.** Fred saved a mono
  master and an RGB final with Zstandard, byte shuffling and SHA-256
  checksums. Both fail with a Zstandard error. A decoder written from the
  spec reads both, both checksums match, and the mono master is
  bit-identical to Fred's uncompressed copy.
- **Stored solutions from PixInsight 1.9.5 and later are not found.** These
  files name the solution `AstrometricSolution:*`. The reader knows only
  `PCL:AstrometricSolution:*`, so the Image Analyzer shows no overlays until
  the user solves the image again.
- **An older bug: plain-text properties are base64-decoded.** Text that
  happens to be valid base64 turns into garbage: "M101" becomes "3]5", and
  "ICRS" becomes " $R". Ingest reads headers through the same function.

## Goals

1. Read every XISF file a baseline decoder must read (§7.2):
   - data blocks: inline (base64 and hex), embedded and attached;
   - compression: zlib, LZ4, LZ4HC and Zstandard, each with or without byte
     shuffling, with or without a `subblocks` attribute, including
     uncompressed subblocks;
   - SHA-1, SHA-256 and SHA-512 checksums, verified before use;
   - big-endian and little-endian data;
   - planar and normal pixel storage;
   - the existing sample formats and the grey and RGB colour spaces.
2. Read stored plate solutions under the spec's `AstrometricSolution:`
   names (§11.5.3.7), and keep reading the older `PCL:` names.
3. Read property values as the spec defines them.
4. Place stored solutions at the right pixel: CRPIX = reference + 0.5.

## Non-goals

- Writing XISF.
- Distributed units (`url(...)` and `path(...)` blocks). These are treated
  as unavailable, as §7 allows.
- The solution's projective (2), distortion (3) and provenance (4) layers.
  Overlays use the linear layer, as they do today.
- Projections other than gnomonic (Fred, below).
- Colour management (ICC profiles, RGB working space, Annex B), display
  functions, `orientation`, `offset`, colour filter arrays, XML signatures.
- Using PixInsight's embedded thumbnails for NightCrate's own thumbnails.
- Rewriting metadata already in the catalog.

## Anti-goals (failures even if everything works)

- A file that opens today stops opening, or opens with different pixels.
- A damaged compressed block is decompressed before its checksum is checked.
- A solution NightCrate can't evaluate is replaced by FITS keywords, so the
  overlays come from a different solution than the one PixInsight stored.
- Reading a header (ingest, the Header tab) reads large attached blocks.

## Decisions

### Fred's decisions (2026-11-11)

  Analyzer, the Gallery, catalog thumbnails, ingest and plate solving. The
  message says the file is damaged and suggests re-saving it from
  PixInsight or restoring a backup.
- **Projections:** gnomonic only.
  - A solution in another projection is not shown, with a short note saying
    why.
  - Solving the image in NightCrate still works.
- **Damaged files stay out of the catalog, and a tab lists them** (after

  and a damaged file is not cataloged.

  - The tab lists **every file a scan couldn't catalog**, each with its

### Files a scan couldn't catalog (Fred, 2026-11-11)

**Where:** the project's Catalog tab gains a last sub-tab, "Not cataloged
{n}".
- It is always shown, like the other sub-tabs, so 0 is visible.
- When n > 0, a banner like today's unclassified-frames one appears above
  the sub-tabs: "{n} files weren't cataloged — a scan couldn't read them."
  Its Review button opens the sub-tab. The wording follows the existing
  banner's pattern; "1 file wasn't cataloged" for one.

**One row per file** that the latest scan of its folder couldn't catalog:
- the file name, with its path beneath;
- the reason, in words:
  - **Damaged:** the checksum doesn't match;
  - **Unsupported:** a valid file NightCrate can't read, such as an
    unknown compression method or data stored outside the file;
  - **Unreadable:** anything else, such as a header that can't be parsed
    or an unexpected error;
- the message;
- the date of the scan that found it;
- the "Open in the Image Analyzer" button that frame rows have. The header
  and the message can be read there;
- when the catalog still holds that path from an earlier scan, the note
  "An earlier scan cataloged this file."

**Lifecycle** (Codex round 3):
- A scan reconciles the files it could list. A row whose path lies under a
  scanned folder is replaced by that scan's result: a fixed file
  disappears, and a still-failing one is updated.
- Nested folders share rows by path, so repairing a file and scanning
  either folder clears it.
- A folder that can't be listed (an offline volume, a missing or unreadable
  directory) keeps its earlier rows. The scan message says the folder
  couldn't be read, and the tab never claims that everything was
  cataloged for it.
- A FITS or XISF file the scan can see but not open or stat is listed as
  Unreadable. An archive whose contents can't be listed is treated like a
  folder that can't be read.
- A folder scan doesn't look inside archives, so it leaves archive-entry
  rows alone. Those are updated by scanning the archive's own bound
  folder.
- The same holds for hidden folders and PixInsight project bundles, which a
  scan doesn't enter. Their rows are updated only by scanning a bound
  folder inside them.
- Removing a folder removes the rows under it, unless another bound folder
  still covers them. Deleting the project removes all its rows.
- Only FITS and XISF files can appear, including entries inside archives.
- A file cataloged by an earlier scan that now fails keeps its catalog
  entry. Its row says "An earlier scan cataloged this file."

**Storage:** a new table, `uncataloged_file`, so the list is typed data and
not text pulled from the scan log:
- `project_id`, referencing `project`, cascade on delete;
- `path`;
- `reason`, CHECK `damaged`/`unsupported`/`unreadable`;
- `message`;
- `run_id`, referencing `ingestion_run`, set null on delete;
- `detected_at`, UTC;
- unique (`project_id`, `path`).

**Not in scope:** a retry button (rescanning the folder retries), deleting
or moving files, and scanning on a schedule.

### Data blocks: one shared reader

Every data block, whether pixels, a property or a solution vector, is read
by one function. The steps, in order:

1. **Locate.**
   - `inline:base64` or `inline:hex`: the element's text, ignoring white
     space.
   - `embedded`: the child `Data` element. Its `encoding` and
     `compression` attributes are on `Data` (§10.6). The spec doesn't say
     where `subblocks` and `checksum` go, so each is read from `Data`, or
     from the parent if `Data` doesn't have it.
   - `attachment:position:size`: bytes in the file.
   - Any other location makes the block unavailable.
2. **Verify the checksum**, if any (§10.5).
   - The digest covers the bytes as stored, including uncompressed
     subblocks, or the decoded bytes for inline and embedded blocks.
   - Accepted names are `sha-1`, `sha1`, `sha-256`, `sha256`, `sha-512`,
     `sha512`, `sha3-256` and `sha3-512`.
   - A mismatch raises a checksum error. Nothing is decompressed.
3. **Decompress** (§10.6, §10.6.1):
   - Without `subblocks`, the whole block is one subblock of the size the
     `compression` attribute gives.
   - With `subblocks`, the subblocks are stored contiguously in the listed
     order. Their total must equal the block size.
   - A subblock whose compressed and uncompressed lengths are equal is
     copied unmodified. Every other subblock is decompressed and must
     produce exactly its uncompressed length; otherwise the block is
     invalid.
   - The concatenated result must equal the size in `compression`.
   - Codec names: `zlib`, `lz4`, `lz4hc` (also accepting `lz4-hc`), `zstd`,
     each with `+sh`. LZ4 data is the LZ4 block format. Zstandard is one
     frame per subblock.
   - An unknown codec makes the block unavailable.
4. **Unshuffle** after decompression, over the whole block (§10.6.3). Bytes
   after the last complete item stay as they are.
5. **Byte order:** `byteOrder="big"` is converted to native order. It
   applies to the uncompressed data (§10.4).

The guess that looks for subblock sizes inside the data is removed. It has
no basis in the spec: it was the original April 2026 implementation, and
the single-stream path was added later for real files.

**Unavailable is not fatal** (§7). An unsupported codec, location or sample
format makes that block unavailable, with a clear error when its pixels are
requested. The header, properties and other images still read.

### Pixels

- `pixelStorage="Normal"` (interleaved) is converted to NightCrate's planar
  layout. The default and `Planar` are read as today.
- Images are the `Image` children of the root element. Their properties and
  FITS keywords are their direct children only, so a `Thumbnail`'s own
  children are never mixed in.

### Properties

- **Scalars and TimePoints** come from the `value` attribute (§11.1.4,
  §11.1.7).
- **String:**
  - Without `location`, the value is the element's text, unchanged
    (§11.1.6).
  - With `location`, the value is the data block decoded as UTF-8.
- **Vectors and matrices** (§11.1.8, §11.1.9) are data blocks, typed by
  `type`, `length`, `rows` and `columns`.
- **What header reads may load:** `read_header`, the Header tab and ingest
  read inline and embedded blocks only. An attached block appears as a
  short summary, such as "F64Matrix 412×2 (stored in the file, not shown)".
  It is never read.
- **Display:** vectors and matrices of up to 9 values are shown as numbers.
  Longer ones are shown as type and size.
- **Errors:** a property block that fails its checksum or can't be decoded
  is shown as unavailable. The header read does not fail.

### Stored plate solutions

**Lookup order:**
1. `AstrometricSolution:*` properties (§11.5.3.7);
2. if none, `PCL:AstrometricSolution:*`;
3. if neither, the FITS keyword WCS, flipped to top-down rows as today.

**Rules for the `AstrometricSolution:` namespace:**
- **Version:** required. Major version 1 is accepted, with any minor
  version, and unknown properties in the namespace are ignored. Any other
  major version means NightCrate doesn't interpret the solution.
- **Layer 1:** NightCrate reads `ProjectionSystem`,
  `ReferenceCelestialCoordinates` (F64Vector, length 2),
  `ReferenceImageCoordinates` (F64Vector, length 2) and
  `LinearTransformationMatrix` (F64Matrix, 2×2, row-major, degrees per
  pixel), wherever their blocks are stored.
- **Unusable solution:** a missing property, wrong dimensions, an unknown
  projection, an unsupported major version, or a projection other than
  `Gnomonic` makes the solution unavailable.
- **No fallback:** an unavailable solution does not fall back to the
  `PCL:` names or to FITS keywords (§11.5.3.7: "not even as a fallback").
  The reader returns the reason, and the Image Analyzer shows it where it
  now says the image has no solution.
- **Reference system:** `CelestialReferenceSystem` is not used. An
  unrecognized value does not make the solution unavailable.

**Conversion to NightCrate's WCS** (§11.5.3.7.1, equation 23):
- Image coordinates put pixel (i, j) at [i, i+1) × [j, j+1). The pixel's
  centre is (i+0.5, j+0.5), and y grows downward, as NightCrate's displayed
  rows do. FITS pixel centres are whole numbers counted from 1.
- So: CRVAL = the reference sky coordinates; CRPIX = the reference image
  coordinates + 0.5; CD = the matrix as stored. No transpose, no flip.
- The `PCL:` names get the same +0.5. PixInsight's library writes both, and
  the checks below confirm it on real files.
- Effect: every stored PixInsight solution moves by half a pixel in x and y.
  This can't be seen on overlays, but it is now correct.

**Where it shows:**
- The Image Analyzer reads a file's own solution on demand (`detect-wcs`,
  `annotate`). Files solved by PixInsight 1.9.5 or later show overlays
  without solving.
- Project plate solves come from NightCrate's solvers and are unaffected.

### Messages

- A checksum failure and an unusable solution each get one message, written
  in the app's plain style.
- Codex drafts the wording, and Claude checks it against the behaviour.

## Constraints

- Clean-room: written from the published specification only, with no GPL
  library code (development decisions).
- XML parsing stays on `defusedxml`.
- No new dependencies: `hashlib`, `zlib`, `lz4` and `zstandard` are already
  available.
- Services raise domain errors (`XISFError` subclasses), not HTTP errors.
  Routers translate them.
- The reader stays worker-safe and numpy-only, because thumbnails and frame
  quality run it in worker processes.
- Decoding Fred's 380 MB mono master must stay under about 1 s. The spec
  probe took 0.5 s, including the checksum.

## Decisions for review (Claude's calls)

1. **Remove the in-data subblock guess.** It has no basis in the spec, and
   no known file needs it.
2. **Copy equal-length subblocks as-is.** The spec also allows trying to
   decompress them, for encoders that compressed every subblock. Skipped:
   such a coincidence is very unlikely, and LZ4 has no integrity check, so a
   raw subblock could decompress into garbage that looks valid.
3. **Accept SHA3-256 and SHA3-512 as well.** They are in the standard
   library and cost nothing.
4. **An unusable new-style solution never falls back** to the old names or
   FITS keywords, as the spec requires.
5. **The +0.5 applies to the old `PCL:` names too.** The checks confirm it.
6. **Header reads summarise attached blocks** and don't read them.
7. **Catalog metadata is not rewritten.** The check reports any affected
   files to Fred.
8. **Presentation elements are ignored:** thumbnails, resolution, display
   function, ICC profile, orientation and offset.
9. **Overlays keep using the linear layer.** The distortion layers stay out
   of scope.
10. **Embedded blocks' `subblocks` and `checksum`** are accepted on `Data`
    or its parent, because the spec places only `compression`.
