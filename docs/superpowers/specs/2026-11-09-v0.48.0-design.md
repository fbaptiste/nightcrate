# v0.48.0 — Messier checklist and project pills in the Planner

Fred started this version on 2026-11-09 and skipped the spec questions
("please write the specs - discuss it with Codex, use design skill"). The
scope is the roadmap's Messier checklist (`PLAN.md`, v0.48.0 › Scope,
decided 2026-10-24), plus two goals Fred gave on 2026-11-09. Claude made
the remaining choices; they are listed at the end for his review. Codex
reviewed the first draft against the code (records
`.superpowers/codex/v0.48.0/`, local); its findings are folded in. Mockups:
`.superpowers/mockups/v0.48.0/messier.html` (local), both themes.

## Why

Fred's words (2026-11-09):
- "a way to see the Messier catalog, with my images for those I have shot
  myself, and maybe in a different style (slightly grayed out, or blank,
  give user the option) the ones remaining."
- "add a pill (as a link to one or more projects) inside the Planner views
  (Plan Night, Full Catalog, not wishlist) that shows whether the object is
  contained in a project. Pill can link to the project (or offer a
  picklist if more than one) and jump to it."

The Messier list is the classic first goal for imagers. Today nothing in
NightCrate shows which of the 110 a user has imaged, and the Planner
doesn't say whether an object already has a project. Both answer one
imaging decision: what to shoot next, or what to continue.

## Goals

- One page with all 110 Messier objects in number order. Objects the user
  has imaged show their own image. The rest show a sky survey image
  crossed by a light X, or a blank numbered slot, the user's choice.
- At a glance: how many are imaged, and which have a project but no image
  yet.
- From any slot, reach its projects, or open the object in the Planner to
  plan it.
- In the Planner's Plan a Night and Full Catalog lists, a pill on every
  object that is a main target of a project. It opens that project, or
  offers a list when there are several.

## Non-goals

- **Objects found only in a plate-solved image.** M 32 in an M 31 image
  doesn't fill M 32's slot or get a pill. The roadmap's object search
  (next on the roadmap) adds an "in a solved field" marker, computed from
  the solve at query time. Today a user can tick M 32 as a main target in
  the project's Plate Solve tab, and the slot fills.
- **Other checklists** (Caldwell, Herschel 400). The page is built for
  Messier only.
- **Choosing which project's image represents a slot.** The roadmap rule
  decides (see "Which project fills a slot").
- **Ticking an object off without a project** (visual observing, imaged
  before NightCrate). Only projects count.
- **The Wishlist tab and the Planner's detail panel.** Fred excluded the
  Wishlist. The detail panel could show the pill for the other two tabs
  only, but it opens from all three; leaving it out keeps one rule.
- **Printing or exporting the checklist.**
- **The Planner's existing thumbnails.** Their browser caching has the
  workspace issue described under "The sky survey image"; this version
  fixes it only for the checklist's new images.

## Anti-goals (failures even if everything works)

- A survey image that can be mistaken for the user's own picture.
- A slot shown as imaged without one of the user's own images.
- A retired project counting, in the checklist or in a pill.
- M 102 shown as M 101, or missing, while the catalog has it.
- "0 of 110" when the catalog simply isn't downloaded.
- Opening the page downloading 110 survey images at once, or tiles that
  keep polling forever while the page is hidden or offline.
- "Open in Planner" opening the Planner on some other object.
- A pill missing because its data didn't load, read as "no project".
- The Planner list getting noticeably slower.
- Colour alone telling imaged from not imaged.
- Any change to how the Gallery looks or behaves.

## Decisions

### The page

- **A new Messier page** at `/messier`, nav item "Messier" after Gallery
  (Claude's call). It is object-centred, one slot per Messier number,
  where the Gallery is project-centred; putting it inside the Gallery
  would mix two kinds of card and two sets of filters.
- **It stays mounted** after its first visit, like the Gallery: scroll
  position, the filter and turned tiles survive opening a project and
  coming back. It refetches each time it becomes visible.
- **The header stays on screen** (Fred, 2026-11-09, at his first look:
  "when I scroll the images, it should leave that top area on screen").
  It is pinned to the top of the page while the tiles scroll underneath,
  on the page's background with a thin line along its bottom. Tiles
  brought into view by the keyboard or by closing the full-size viewer
  are never left hidden under it.
- **Three areas side by side** (Fred, same day: the filters and options
  move into the area beside the map): the title column on the left, the
  controls in the middle, the map on the right. A little narrower
  (about 950–1,100 px of page width: a laptop with the navigation open,
  an iPad in landscape), the three stay side by side with a smaller map.
  Narrower still, the title column and the map share the first row and
  the controls wrap in a second row.
- **Title column:** "Messier checklist", then the **Location** picker
  (Fred: under the title, because it changes the line below it), then
  one line of progress:
  - "23 of 110 imaged." always;
  - "3 more have a project but no image yet." when any do;
  - "Of those not yet imaged, 3 never rise at Home." when a default
    location exists and any do (see "Never rises").
  - Retiring a project can lower the count; that is intended.
- **A map of the 110 at the header's right** (Claude's call; Claude
  calls it the progress map): small boxes in rows of 20, split into two
  groups of ten, each row labelled with its first number (1, 21, 41 …). A filled teal box is imaged, a
  hatched one has a project but no image, an empty one is not imaged,
  and a crossed one never rises. A legend sits above the map, aligned
  to its right edge (Fred).
  - **Hovering a box with a project shows a tooltip** (Fred, 2026-11-09:
    "a hover tooltip over each cell that lists the projects/date of each
    project"): the designation and common name, the slot's state
    (Imaged, or Project, no image yet), then each project in the slot's
    order with its imaging dates, and "No image yet" on its own line
    under a project without an image. Boxes that aren't imaged and have
    no project show no tooltip (Fred: "do not show a hover tooltip if the
    cell was not imaged"). The tooltip uses the app's standard look, and
    a long press shows it on touch screens, as the app's other tooltips
    do.
  - Nothing in the map is clickable. Screen readers skip it: the
    progress line carries the counts, and each tile's back lists the
    same projects. (Codex's review found a click-to-jump map
    pointer-only; a keyboard-equivalent jump control is more than this
    summary needs.)
- **Controls,** two columns, each with its caption above it (Show and
  Tile size; Imaged as and Not imaged as; Rig field and Projects under
  images):
  - **Show:** All · Imaged · Not imaged (a toggle group; default All).
    Not imaged includes slots whose project has no image yet. Kept for the
    app session, not saved.
  - **Imaged as** (Fred, 2026-11-09): Own image · Sky image (a toggle
    group), before "Not imaged as". Saved in `messier_imaged_style`
    (`own` or `sky`; default `own`). See "Imaged as and project arrows".
  - **Not imaged as:** Sky image · Blank (a toggle group). Saved in the
    setting `messier_unimaged_style` (`sky` or `blank`; default `sky`,
    the first option in Fred's words).
  - **Projects under images** (Fred, 2026-11-09), a switch, off by
    default. Saved in `messier_show_projects`. See "Projects under
    images".
  - **Tile size:** the Gallery's icon view picker without the list
    option: small, medium, large. Saved in `messier_view` (default
    `medium`).

  - **Rig field** (Fred, 2026-11-09): No rig, or one of the user's
    rigs, in their rig order. It draws the rig's field on each picture
    (see "Rig field"). Saved in `messier_rig_id`; default No rig. Under
    it, in small text: "Field 2.8° × 1.9°, centred on each picture";
    both sides in the same unit, degrees from 1° and arcminutes below
    ("41′ × 28′"). A rig whose field can't be worked out says so in the
    same place.

  The **Location** picker (Fred, 2026-11-09), in the title column:
  None, or one of the user's locations. It decides "Never rises". Saved
  in `messier_location`; until the user picks one, it is the default
  location, if any. A deleted location falls back the same way.
- **The grid** reuses the Gallery's layout: minimum tile widths 180, 300
  and 480 px, rows that fill the width with 16 px gaps, content at most
  1,600 px wide. Slots are in Messier number order; no other sort.

### The 110 slots

- **The checklist is a fixed list of the numbers 1–110 in code.** Each
  number is looked up by its designation key `("messier", "N")`. This is
  the roadmap's "explicit checklist mapping, separate from catalog
  designations": the slots never come from whatever designations exist.
  The identity of a number is decided where the catalog decides it, so
  a second table can't disagree with the catalog; since v0.45.0 the
  reviewed override gives M 102 to NGC 5866.
- **The lookup includes inactive objects,** so a slot keeps its projects
  if a catalog update retires the object while it still carries the
  designation.
- **A number with no object** (the designation is missing): the slot is
  a blank tile whose back says "Not in your catalog data". It is never
  shown as "no project": it has no projects, no sky image and no Planner
  link, and it doesn't count as not imaged in the header.
- **OpenNGC not downloaded:** the page shows only "Download OpenNGC in
  Admin › Catalogs to show the Messier checklist.", with a link, when both
  hold: no Messier number resolves, and OpenNGC's files are absent on
  disk. The test is local; it never asks GitHub, so it works offline.
  When the database already holds objects (for example, the files were
  deleted after loading), the checklist shows as usual, with any number
  that doesn't resolve marked "Not in your catalog data".
- **If one object carries two Messier numbers** (possible only if the
  M 102 override were removed), both slots show it. The M 102 note
  covers the historical reason.

### Which project fills a slot

The roadmap rule, made exact:
- **Candidates:** non-retired projects (`project.active = 1`) with the
  object among their main targets (`project_target`).
- **Order** (the first is the slot's project):
  1. projects with a main image before those without;
  2. latest imaging date, newest first, using only valid session dates
     (`valid_session_date`), as the Gallery does;
  3. projects with no imaging dates after dated ones;
  4. newest `project.created_at` first, then highest id.
- **Slot states:**
  - **Imaged:** the first project has a main image.
  - **Project, no image yet:** candidates exist, none has a main image.
    (A project with any image has a main image: the first image added
    becomes main, and removing it promotes another.)
  - **Not imaged:** no candidates.
- **A main image whose files are missing** still counts as imaged. The
  tile shows the Gallery's "No preview" on black, never a survey image or
  another project's picture.
- One project with several main targets fills several slots with the same
  image (an M 31 project that also lists M 32 and M 110 fills three).

### What a tile shows

Each tile is the Gallery's 4:3 image box, with a caption below.

- **Imaged:** the project's image, exactly as the Gallery shows it at
  that size: the user's framing for the size, otherwise the whole main
  image on a black mat. It is in full colour.
  - A teal check mark in a dark circle at the top left, labelled
    "Imaged" for screen readers. It is a shape, not just a colour.
  - The Gallery's expand button at the top right opens the full-size
    viewer.
- **Not imaged, sky style:** a survey image of the object at full
  strength, like the user's own images, crossed by a light X from corner
  to corner (Fred, 2026-11-09, after seeing a greyed version: "make them
  full strength … but put a light strikethrough"). The X is two white
  lines at 45 % opacity, 1.5 px wide at any tile size. A small "Sky
  survey" label with a soft dark shadow sits at the bottom right at every
  size. The X and the label keep it from being taken for the user's own
  picture.
- **Not imaged, blank style:** no image. The box shows the Messier number
  large and faint on the page colour, inside a dashed outline: an empty
  slot waiting to be filled. The blank style requests no survey image.
- **Project, no image yet:** the not-imaged style the user chose, plus a
  badge at the bottom left: "Project, no image yet".
- **While a survey image loads, and if it can't load,** the tile shows
  the blank style (see "The sky survey image").
- **Caption,** two lines, each ending in an ellipsis if too long:
  - line 1: the designation ("M 31") in bold, then the common name when
    there is one, with other names on hover (`NameWithAlternates`). 66 of
    the 110 have no common name;
  - line 2: the type and constellation, "Galaxy in Andromeda"; for a slot
    that never rises at the chosen location, "Never rises at Home"
    instead.

### Projects under images (Fred)

Fred, 2026-11-09: "an option user can turn on that shows, below each
image, the project link and date range for the projects that imaged the
object."

- With the switch on, each caption gains a thin divider and then one line
  per project, in the slot's order: the project name as a link that
  opens it, and its date range at the right in muted text.
- **Date range:** first to last session, in the Gallery's date style:
  "Sep–Oct 2025", "Dec 2024 – Jan 2025"; within one month the exact days,
  "Oct 3 – 21, 2025", or "Oct 3, 2025" for one night; "No dates" without
  valid session dates. Nights are left out to keep one line.
- Every project is listed (the mockup shows one, two and three); a long
  name ends in an ellipsis, the date never does.
- **In the small size** the date goes on its own line under the name, so
  a long range doesn't squeeze the name.
- **No project:** nothing is added, not even the divider (Fred: "only
  show projects that exist - keeps things a bit cleaner").
- Whether a project has an image isn't repeated here; the tile's badge,
  its back and the map's tooltip say so.
- Rows of tiles grow to their tallest caption, so tiles in a row keep
  their images aligned.

### Turning a tile over

The Gallery's mechanics: the image is a button ("Show details for M 31");
a 400 ms turn, reduced motion swaps without turning; Enter, Space and Esc;
the hidden side is `inert`; focus moves to the side now showing; clicking
anywhere on the back turns it back, except its links and buttons. Several
tiles can be turned at once; changing the filter or tile size turns them
all back.

The back shows, top to bottom:
- **Facts:** type and constellation, then magnitude and size ("mag 3.4 ·
  190′ × 60′"), and "Never rises at Home" when it applies. Missing values
  are left out, never shown as zero.
- **Projects:** every candidate in the order above, the slot's project
  first. Each name is a link that opens the project, followed by its
  imaging dates in the Gallery's format and "No image yet" when it has
  none. With no candidates: "No project yet". There is no hover-only
  overflow: when the list is long, the back's content scrolls, with the
  Gallery's fading bottom edge, so every project is reachable by
  keyboard and touch.
- **For M 102 only,** a note: "NightCrate uses NGC 5866 for M 102. Its
  historical identity is disputed; some lists identify it with M 101."
  (Codex's wording.)
- **Footer:** "Open in Planner" (see below).

In the small size the back shows the projects and the footer only.

### Shared components

The tiles reuse the Gallery's flip, image, expand button and full-size
viewer, which today identify an entry by its project id. Here one project
can fill several slots, so shared parts take a separate entry identity:
the Messier number on this page, the project id in the Gallery. Turned
state, element references, keys and the viewer's position use that
identity. Everything else stays as the Gallery does it: framing choice,
workspace-keyed image URLs, reduced motion, focus return, closing when
the page is left.

### Full-size viewer

The Gallery's: the expand button opens it; arrows and ← → step through
the imaged slots in number order, so a project filling three slots
appears three times; the caption reads "M 31 Andromeda Galaxy" and the
project name.

### Open in Planner

- It opens the Planner with this object's detail panel, on whichever tab
  the Planner last showed.
- It must work whether or not the Planner has been opened yet in this
  session. The Planner loads its saved settings when it first mounts,
  including the detail panel it last had open
  (`usePlannerSettingsSync.ts`), so setting the store before navigating
  would be overwritten. The request travels with the navigation and is
  applied once, after the settings have loaded, so closing the panel
  doesn't reopen it.
- Absent from slots with no object.

### Never rises (Claude's call; the location picker is Fred's)

For a user in the far south, several Messier objects never clear the
horizon: from latitude 35° S, M 81 and M 82 stay below it. The checklist
says so instead of leaving those slots looking like unfinished work.

- **Location:** the one chosen in the header's Location picker (Fred:
  "change it so I can select one of my locations"). With None, nothing is
  marked.
- **Rule:** a conservative geometric test. The object's highest possible
  altitude, 90° − |latitude − declination| from the catalog's J2000
  declination, is below −1°. The margin keeps borderline objects
  unmarked; refraction, the observer's elevation and the local horizon
  all shift the real horizon, and none is modelled. Objects without
  coordinates are never marked. An unmarked object is not a promise that
  it is visible.
  - Example: from 35° S, M 40, M 52, M 81, M 82 and M 103 are marked;
    M 97, M 101, M 102 and M 108 (highest altitude between −0.8° and
    +0.7°) are not. From 33° N nothing is marked.
- **Shown** only on slots that aren't imaged (an imaged slot may come from
  a remote site): caption line 2, the back's facts, the map and the
  header's count.

### Rig field (Fred)

Fred, 2026-11-09: "allow user to select a rig (or no rig). when selected,
draw a bounding box on each image to show how the object would fit in the
rig's FOV. (gives me an idea of the scale) … just center the rig's FOV on
the image, no need to try and calculate the exact position of the FOV on
the object."

It answers a planning question: does this object fill my rig's frame, or
is it a speck in it?

- **The box:** the rig's field, from its current setup as the Planner
  computes it, drawn as a rectangle centred on the picture, long side
  horizontal. A 2 px orange line (#ed6c02, the Planner's rig-frame
  colour) with a thin dark edge so it shows on bright and dark pictures.
  No rotation, and no attempt to place it where the object really sits
  in the picture.
- **The scale of each picture:**
  - a sky survey picture: known exactly from its framing rule;
  - the user's own image: from the project's plate solve (its field in
    arcminutes), when the main image is the solved file, or has the
    solved image's proportions within 0.5 % (a finished export of the
    solved master, as in a project whose main image is a PNG made from
    the PixInsight master it was solved from). This is an assumption: a
    different crop with the same proportions would get the wrong scale.
    The box is a guide to scale, not a measurement;
  - a framed thumbnail: the plate-solved field times its framing's
    fraction of the source image, when that source is the image above;
  - otherwise the scale is unknown: no box, and a "Scale unknown" badge
    at the bottom left.
- **When the rig's field is larger than the picture,** the picture
  shrinks, centred on black, until the box fits inside the tile with a
  small margin. With a wide refractor, M 57 becomes a dot in a large
  frame: that is the scale the user wanted to see. When the field is
  smaller, the box sits on the picture at its true size.
- **The survey picture's X always runs corner to corner of the tile,**
  not of a shrunken picture (Fred: "keep the crosses full cell").
- **Blank tiles** have no picture, so no box. The full-size viewer, the
  map and the tooltip don't change.
- Choosing a rig doesn't change any image request; the survey pictures
  stay those of "The sky survey image".

### The sky survey image

- **Source:** the Planner's per-object thumbnails endpoint
  (`/api/planner/thumbnails/{dso_id}`): DSS2 colour from CDS, with ESA as
  the fallback, cached on disk under the shared LRU budget.
- **A new 4:3 variant,** 800 × 600 px. The field is 1.5 × the object's
  major axis across, and at least 0.15° (5′ assumed when the catalog has
  no size, as for M 40 and M 73). 800 pixels covers a 400-pixel-wide
  tile at 2× pixel density; wider tiles may look softer. DSS2 itself
  limits the detail of small objects. The planner's square `list`
  (180 px) is too small, and the `detail` field (at least 1°) makes
  planetary nebulae specks.
  - **Measured for the mockup (2026-11-09),** through the existing tile
    code, from ESA with CDS down: all 110 at a 0.25° minimum in 50 s;
    the 62 smaller objects again at 0.15° in 16 s (median 80 KB). The
    110 images take about 12 MB, well inside the 500 MB cache budget.
- **The cache's rules for this variant:**
  - the `variant` column is a closed CHECK, so one forward migration adds
    the value, keeping every existing row and its failure time;
  - the cache's filename pattern and its startup reindex learn the new
    variant together;
  - one render identity, made of the object's coordinates, the field
    actually used and a framing version, is used the same way by the
    database lookup, the file name, the startup reindex and the browser
    URL. A changed catalog size or framing rule therefore never serves an
    old image from either cache. (Today's non-rig variants drop the field
    from the key, and successful responses are cached by the browser for
    a day.)
  - files of inactive objects aren't reindexed at startup (as today), so
    they are fetched again if needed;
  - its browser URL also carries the workspace key, as the Gallery's
    images do, so a different workspace's object with the same id never
    shows from the browser's cache.
- **Loading:**
  - only near the visible part of the page (within 400 px of it); the
    blank style shows until the image arrives;
  - at most three requests at a time for the whole page, nearest the
    visible part first, so the full-size viewer and the page's other
    requests always have free connections (Fred, 2026-11-09: opening
    M 101 full size waited about a minute behind some 100 survey
    requests after he scrolled down; browsers open at most six
    connections to one server). A tile scrolled away cancels its
    request and asks again when it comes back;
  - a bounded number of polls while the server fetches it. After a
    failure, or the server's 10-minute backoff, the tile stays blank and
    tries again only on a later visit or refetch;
  - polling stops while the page is hidden.

### Planner project pill

- **Where:** in Plan a Night and Full Catalog cards only. It sits in its
  own column at the card's right edge, top-aligned, outside the card's
  click area (the star sits outside it on the left for the same reason: a
  button can't be nested inside another). The pills line up down the
  list, so a user can scan which objects already have projects.
- **When:** the object is a main target of at least one non-retired
  project.
- **Looks:** an outlined pill in the theme's slate blue with the Projects
  nav icon.
  - One project: its name, ending in an ellipsis past 200 px; hover shows
    "Open project: {name}". Clicking opens the project.
  - Several: "3 projects ▾"; hover shows "3 projects have M 81 as a main
    target". Clicking opens a menu, one row per project in the
    checklist's order without the image rule: the name, its imaging
    dates in the Gallery's format, and its status when it isn't Active.
    Choosing a row opens that project.
- **Data:** one compact request for every non-retired project's
  main-target links (project, object, name, status, imaging dates), not a
  field on every planner row and not the Gallery's full loader. Built
  into a lookup by object once per response.
  - **Refreshed** when the Planner becomes visible, and after any change
    to a project's targets, sessions, name, status, retirement or
    restoration. Today's target edits refresh only the project's own
    queries, so the link query gets its own key and those changes
    refresh it.
  - **While it loads,** the list doesn't wait. A refresh keeps the pills
    already shown. With no link data yet, "Checking projects…" appears
    above the list after half a second, so a fast answer never flashes
    it. **If it fails,** that line says "Couldn't check which objects
    have projects.", so missing pills never read as "no project".
  - Its payload and the Planner's render time are measured on a library
    of several hundred projects.

### Settings

`messier_view`, `messier_imaged_style`, `messier_unimaged_style`,
`messier_show_projects`,
`messier_location` and `messier_rig_id` are new settings in
`core/config.py` and the frontend settings type. No migration. A stored
id that no longer exists falls back to the default (the default location;
No rig).

## Constraints

- Imaging dates, framed images, renditions, image URLs and caching follow
  the Gallery's rules (development decisions › Gallery and project
  images). The Gallery's behaviour doesn't change.
- Main targets come only from `project_target`. A solve's in-frame list is
  not a link.
- Designations resolve through the existing tables; no second Messier
  mapping that could disagree with the catalog.
- Colour-blind safe: teal and slate blue on neutral; every state also has
  a shape or words.
- No new dependency.
- One forward migration (the cache variant), tested on a copy of a
  database at 0070 and on a fresh one.

## Checks the plan must include

Beyond counts and screenshots:
- slot resolution: a missing designation, an inactive object, two
  numbers on one object, OpenNGC not downloaded, offline, and OpenNGC's
  files deleted from a database that still holds its objects;
- every ordering tie (image, date, undated, `created_at`, id), and
  retiring and restoring a project;
- a main image with missing renditions;
- a project filling three slots: keys, turned state, viewer stepping and
